## 逐条细节

### 1. `cullOverlay` 漏拷两个字段（渲染/交互双杀）

- 证据：`src/render/token-layer.ts:465` `cullOverlay` 逐字段手写返回值，**没有** `expandedStack`（类型定义在 `:148`）、
  也**没有** `zoc`（`:242`）；消费端 `:841` `visible.expandedStack ?? null`、`:931` `visible.zoc !== undefined`。
  调用方 `src/render/map-render.ts:540` **永远**带 `visibleKeys` 调 `drawMovementOverlay` ⇒ 必然走裁剪。
- 根因：裁剪函数是"手写白名单"，新增 overlay 字段时没人补 ⇒ 静默丢字段。
- 修法：返回字面量补 `expandedStack`（整格属性，直接透传）与 `zoc`（两组按可见格裁剪）。
- 影响面：这是"摊开点不动/看不到"的直接成因——摊开状态只进了 store，没进渲染。

### 2. 盒卡动作过滤用了两套盒名

- 证据：`src/stores/containers.ts:585` 返回 `card.regions.map(r => r.kind)`，而 `kind` 是**数据侧分区名**
  （`aux-cards.json`：`dead_pile` / `air_box_active` / `markers` …，见 `:655`）；面板
  `src/components/containers/ContainersPanel.vue:271` 收到的却是**引擎盒名**（`deadPile` / `airBox` …），
  调用处 `:418/440/458/479/520/537/571/608/624/735`。
- 根因：`['dead_pile'].includes('deadPile') === false` ⇒ 只要展开着一张卡（对局台 `containers` 会话的**唯一**触发条件，
  `src/stores/map-view.ts:1413`），所有盒动作都被滤掉，只剩只读清单。
- 修法：`openCardBoxKinds` 同时收**原始分区名**与 `boxOfRegion()` 归一出的**引擎盒名**
  （`markers` 必须保留原名：它在 `REGION_OF_BOX` 里映射到 `deadPile`，只取引擎名会认错）。

### 3. 到达两本账都只按"下标"存，换日不清

- 证据：`src/stores/workbench.ts:15719`（原）`markArrivalPlaced` 先改 `arrivalPlacedKey`、再把**旧 raw** 合并进去；
  `arrivalHexOverrides`（`:15361`）只在换剧本时清（`:18660`），`arrivalPlacements`（`:15673`）只按键=下标取。
- 根因：账本"惰性作废"只做了**读侧**（`arrivalPlaced` 比 key），写侧仍把旧值搬进新 key ⇒ 换日后第一次投放
  就把上一天 `{0..N:true}` 全部激活，新一天其余条目永久投不出去；手改落点则会**套到别的条目**上。
- 修法：新增 `syncArrivalLedger()`（写前判键、不同则整本作废），`markArrivalPlaced` 与手改落点共用；
  读侧新增 `arrivalOverrides`（同样按计划键门控）。**不改存档字段名/版本**（`arrivalPlacedKey` 语义扩为两本账共用的键）。

### 4. 合并替引擎编造"现在是增援阶段"

- 证据：`src/stores/workbench.ts:17193` `consolidateUnitsNow` 传 `phaseIsReinforcement: true`（硬编码），
  而引擎 `src/engine/rules/consolidation.ts:180` 正是靠它拒。
- 根因：store 主动喂假事实 ⇒ 13.9-1/2/3 的"本方增援阶段"永远判不到。今天被 `requireAction('rein.rebuild')`
  的环节闸（只在 `reinforcement.rebuild`）兜住，属**隐患**；闸门表一改就变成可绕过的免费合兵。
- 修法：改传 `phase.value === 'reinforcement'`；面板上"合并地面单位"只在增援阶段出现
  （**飞机合并 13.9-4 不限阶段，按钮保留**——不能整行收）。

### 5. 3.5 / 13.7 被套进 `showsReferee` 的剧本抽取模板

- 证据：`ContainersPanel.vue:624` 的 `<template v-if="showsReferee && showsBoxActions('scenarioDrawBox')">`
  一直包到 `:852`，里面含 `:735` 的 13.7 编队收纳与 `:820` 的 3.5 建造标记。
- 根因：2026-10-25 给"抽签改成初设自动执行后的裁判重抽退路"加 `showsReferee` 时，**包的范围大于那一块**。
  两层门互相排斥：正式对局台 `showsReferee === false`；验证页换了卡则 `scenarioDrawBox` 不匹配。
- 修法：把 ④/④b 拆出该模板，各自按"该卡覆盖的盒"判据（`markers` / `scenarioDrawBox||formationBox`）；
  裁判重抽那半仍留在 `showsReferee` 里。

### 6. 点击分派次序：展开态 / 燃料会话越权

- 证据：`src/stores/map-view.ts:1758` ⓪"展开态优先"排在 `setup.placeAtHex`、`pickHexFor` 之前，而
  `expandedStack` 只在换回合/换段/换方收起（`:845`）；`:1348` 的 `fuelPaymentDue` 分支没有环节门
  （紧邻的上一条 `:1325` 明确带 `phase === 'movement'`）。
- 修法：⓪ 前置 `modalPickLive`（初设落位 / 卡车点选 / 通用待点格 / 选项草稿）让路；
  燃料分支补 `actionAllowedNow('supply.fuel')`（12.5 的付款时机本就是 C/E/G 三个移动环节）。

### 7. `hitTestHex` 无距离上界

- 证据：`src/render/map-layout.ts:149` 只判 `isBoardHex(best.hex)`，没有半径上限；
  `MapCanvas.vue:354` 拿到 hex 就派发点击。
- 根因：「密铺 ⇒ 最近格心即在格内」只对**板内**成立；板外 Voronoi 胞无界 ⇒ `MIN_SCALE` 下图廓留白全被算成"点了某格"。
- 修法：补 `best.distance > HEX_RADIUS_PX * (1 + 1e-6)` ⇒ null（**外接半径**为界：格内任一点 ≤ R，
  顶点恰为 R 仍可点，不退回内切半径那套误判）。

### 8. 视口矩形取的是容器外框（1px 边框）

- 证据：`src/components/map/MapCanvas.vue:237` `viewSize` 取 `.mapcanvas__viewport` 的 `getBoundingClientRect()`，
  而该容器是 `border-box` + `border: 1px`（样式 `:560`）；`toLocal` 同样用它的 `left/top`。
  后备存储按 `viewSize × dpr` 分配（`:188`），画布 CSS 尺寸却是内容盒（`width:100%`，`:577`）⇒ 差 2px。
- 根因：绘制面（canvas）与测量面（容器外框）不是同一块矩形，DPR 换算的前提被 1px 边框破坏；
  1:1 倍率下格高 109px，1–3px 的偏移已经够跨到隔壁格。
- 修法：新增 `surfaceRect()`（画布自身的矩形），`syncSize` / `toLocal` / `hexToWindow` 三处统一用它。

### 9. 拖动状态机不记指针 id

- 证据：`src/render/drag-gesture.ts:17` 的 `DragGesture` 只有 `dragging/moved/last`；
  `MapCanvas.vue:328` 的 `pointerdown` 无条件 `beginDrag(...)`，`pointerup/cancel` 也不校验 id。
- 根因：第二根手指按下会替换整段手势（第一根的 `moved` 丢失）；随后第一根抬起被当作"本次手势结束"
  ⇒ `dragEnd` 判 `clicked = !moved` ⇒ 一次**用户没做的点击**；第二根仍在屏上但 `dragging === false` ⇒ 拖不动。
- 修法：`DragGesture` 增 `pointerId`，`beginDrag` 记入、`dragMove` 一路带下去；
  组件三个 handler 首行按 id 过滤，`pointerdown` 在已在拖动时直接忽略后续指针。
  守卫 `map-input.test.ts` 里那句 `not.toContain('drag.dragging')` 收窄为
  `not.toContain('isMapGesture(event, drag.dragging)')`（原意是"手势起点不把拖动位交给闸门"，多指忽略是另一件事）。

### 10. 拆分取用把 20.0a 的时机写死成「开始移动」

- 证据：`src/components/containers/ContainersPanel.vue:511`（原）`timing: 'startMove'` 写死在按钮里，
  一路传进 `src/stores/containers.ts:927` 的 `takeBreakdown(input.timing)`，再到引擎
  `src/engine/rules/breakdown.ts:132`（只做 `BREAKDOWN_CREATE_TIMINGS` 枚举校验）；
  且 `takeBreakdown` **没有** `requireAction`（同类入口 `createBreakdownNow` 有 `move.breakdown`）。
- 原文（20.0a）：「多军力单位在**开始移动、战后推进或战后撤退**时，可以创建一个或多个拆分单位。
  **只有在这些时机**才能创建拆分单位。」
- 根因：界面替规则宣称"此刻正是开始移动"⇒ 枚举校验恒通过 ⇒ 任何环节、任何未开拔的单位都能取用。
  这也解释了为什么 `breakdownRequest.timing`（引擎侧）一直"看起来对"。
- 修法：① 加环节闸 `move.breakdown`（与 `createBreakdownNow` 同一道）；② 时机改由 store 的**事件账本**
  `breakdownTimingOf(unitId)` 给（`openBreakdownWindow` 只在"开始移动 / 战后推进 / 战后撤退"真实事件里开窗），
  不在账本里即拒（回 `20.0a` 并给一句人话）；③ 该函数签名不再接受 `timing`，面板按钮改为
  "时机不成立就灰掉并写明此刻该先做什么"。
- 用例：`containers-flow.test.ts` 新增「环节对了但没开始移动 ⇒ 拒；真的开始移动 ⇒ 放行」；
  原有 4 个用例改为**真的走一次开始移动**（`startMoving` 夹具，用 `beginMoveFor` 开窗）。

### 11. 死亡堆「免费返场」按钮铺在玩家面上

- 证据：`ContainersPanel.vue:448`（原）直接 `workbench.returnFromDeadPileNow({ instanceId, hexText })`。
  该函数（`workbench.ts:16963`）只做"从死亡堆取出 → 落到给定格（可改军力）"，注释明写
  「费用与合法性由调用方先用引擎计划判好」——而 `containers.ts:898`（1.6c 抽取）与 `:1300`（13.7 抽签互换）
  确实都先过引擎计划，**只有这个按钮没有**。
- 原文（13.5a）：「所需的补员必须都在一个格中，且要在一个友方指挥部的 2 格内……该格不可在敌方 ZOC 内。」
- 根因：盒子动作此前被缺陷 2 全部滤掉，按钮其实点不到；缺陷 2 修好后它立刻变成"玩家面上的免费重建"。
- 修法：按钮加 `showsReferee`（裁判订正工具），玩家路径保留 13.5 付补员重建 / 1.6c 特殊补员抽取 / 13.7 抽签互换；
  按钮 `title` 写明该走哪条。
- 用例：`containers-session.test.ts` 新增源码守卫（该调用点最近的 `<BaseButton` 必须含 `showsReferee`）。
