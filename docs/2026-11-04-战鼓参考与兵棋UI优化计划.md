# 战鼓参考与兵棋 UI 优化计划

日期：2026-11-04。状态：实施计划，尚未修改业务代码。代码核对基线：`e079820`（`fix mandatory setup decisions and completed movement saves`）。

执行关系：本计划是[重构计划](重构计划.md)的 UI 配套，沿用 **S1 → S2 → A1–A6** 的主线顺序。界面改造随对应行动链交付，不另起一轮脱离规则修复的大重写。空运专用功能、任意中途续局继续后置。

下载源码后的进一步分析见[兵棋UI设计规律与战鼓源码分析](2026-11-04-兵棋UI设计规律与战鼓源码分析.md)，区分已证实的源码行为、设计推论和玩家验证方法。

## 1. 建议先做什么

保留地图、扫描算子、Vue/Pinia/Canvas 和已拆出的规则域，优先把界面改为：**流程条说清当前操作者与下一步；地图呈现候选、路线和结果；唯一会话承接选择与结算；侧栏提供可追查的信息。**

第一批应覆盖“初设必做事项 → 点图完成 → 双方确认 → 首次移动 → 结束移动后存档”。这是当前 S1 修复已经有自动回归、但尚缺人工界面签收的一条真实链。先让这条链清楚、可靠，再随 S2/A1–A5 扩展。

本次看代码确认：项目已经有地图优先、就地展开堆叠、唯一 MapDock、顶部流程条、右栏只读和底部盒卡。需要优化的是这些入口如何协同，以及状态说明是否准确；不能再把这些既有能力当作尚未实现的工作重新开发。

## 2. 战鼓站实际查到了什么

### 2.1 证据与限制

检查了[战鼓首页](https://zhangu.asia/)、[公开作品目录](https://zhangu.asia/public-catalog)及《朔风扬旌：平津战役1948》的公开试玩前端。目录将平津标为 `publicTrial: true`，试玩限 `small` 剧本。授权页的脚本也明确将小剧本改为无需进入码。

### 2.2 它的兵棋界面如何组织

| 观察到的做法                 | 公开实现证据                                                             | 对我们有用的部分                                            |
| ---------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------- |
| 回合、阶段、单位行动分区     | HTML 有 `turn-sidebar`、`phase-panel`、`selection`；样式末段明确桌面三栏 | 保持稳定的信息位置，主按钮能直接回答下一步                  |
| 原图配可交互算子和覆盖层     | `world` 下有地图 `img`、六角格 SVG、`pieces`、移动/战斗效果及撤退拓扑层  | 复用扫描素材，在其上叠加清晰的选择和反馈；我们继续用 Canvas |
| 辅助内容按需打开             | 算子库、战术、记录独立抽屉/浮窗；窄屏有底部导航                          | 表格、盒区、日志按需查看，减少常驻占用                      |
| 移动前后有具体说明           | 预览与执行结果分别显示路线、耗点、停点和原因                             | “点了没反应”应变成可定位、可解释的反馈                      |
| 阶段结果能定位回地图         | 聚焦模块只遍历可见的增援、断补、恢复事件，按阶段和事件标识保持稳定       | 待办或结算结果点击后定位相关格，避免玩家自己满图找          |
| 增援使用图像条目与地图引导   | 平津样式定义算子图、条目、收起/重开按钮和不接收指针的箭头层              | 让待放单位、合法入口与剩余数量有明确对应                    |
| 深绿背景、米白文字、金色重点 | 样式变量与回合主按钮                                                     | 借鉴主次层级；本项目仍遵守暖纸底、暗红、橄榄绿的现有令牌    |

技术上，该试玩的公开页面采用 DOM 算子和 SVG 覆盖层，入口组合多个原生 JS 模块。它说明了如何组织这套前端，不能据此认定其规则引擎、存档或服务端比本项目更成熟。

### 2.3 迁移时的取舍

1. 保留本项目已确认的“顶部单行流程条”，不照搬左侧第二条流程；不恢复常驻“移动/战斗”工具按钮。
2. 右栏继续只读，规则选择仍在地图和唯一会话里完成；不把参考站的单位行动栏整体搬进来。
3. 正式界面不开放通用算子库拖入地图。单位入场只能来自初设、增援、重建等合法流程。深入读取后确认，参考站正式入口也主动裁剪手工改值动作，不能因HTML或旧代码残留就认为其允许自由改盘面。
4. 参考站撤销也有提交边界：移动、进驻、撤退步及骰子等变化会清空撤销历史。借鉴其保护承诺的方向；付款、掷骰、遭遇和战果后的具体可撤销边界仍由本项目规则域裁定。
5. 不复制参考站具体规则效果。例如其停步说明与费用不能当作 OCS 的 ZOC、MP 或堆叠规则。
6. 不迁入其后端、联网、AI 或 DOM 地图方案；当前目标仍是本机热坐的 OCS 电子裁判台。

## 3. 当前代码的落点与需要核查的问题

下表区分已经观察到的结构问题和仍需复现的交互风险，不能把代码风险直接登记成新 BUG。

| 当前落点                                       | 已观察事实                                                                              | 改造方向                                                     |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `views/GameTableView.vue`                      | 同时组装工具条、地图、初设队列、补给面板、会话、侧栏与日志；正式页仍显示“对局台（C16）” | 保留布局职责，拆展示壳；移除正式界面的批次标识               |
| `stores/map-view.ts`                           | 汇集选中、提示、覆盖层、点图分派和长分支会话优先级                                      | 按呈现、输入分派、会话投影拆纯模块；先不迁正式状态所有权     |
| `MapDock` / `cancelSession()`                  | 标题栏固定叫“取消本次操作”，但分支实际包含取消、收起和结算域拒绝取消                    | 由域能力驱动关闭语义，界面明确提示；不能只改按钮绕过守卫     |
| `DecisionQueue`、`SupplyPhasePanel`、`MapDock` | 前两者独立于唯一会话挂载                                                                | 复现是否同时争抢地图输入；保证同一时刻只有一个主动选择流程   |

| `FlowStrip`                                    | 已有单一推进入口，但显示读取 session、workbench、map-view 多个来源                      | 抽取只读流程投影，统一行动方、操作者、阻断原因和下一步文案   |
| `SaveLoadDialog`                               | 开头注释仍写“任意环节都可存档”，与当前结算点保存策略不符                                | 核对实际提示和可用状态，统一为当前真实能力，清理过时说明     |
| `render/map-input.ts`                          | 已修过浮层冒泡与指针捕获重定向                                                          | 保留既有守卫；新增浮层必须覆盖穿透、拖出、滚动和取消手势回归 |

## 4. 目标布局与交互

### 4.1 桌面布局

```text
对局信息 / 文件入口 / 热坐交接 / 图层与快捷键
阶段 · 环节 · 当前操作者 · 下一步提示       [唯一推进按钮]
┌──────────────────────────────┬──────────────┐
│ 地图                         │ 只读信息栏   │
│ 候选格 / 路线 / 结果标记      │ 所选对象摘要 │
│                              │ 费用和结果   │
│ 唯一可拖动操作会话            │ 规则解释     │
│ 就地堆叠 / 只读格号浮签       │ 待办与日志索引│
├──────────────────────────────┤              │
│ 盒区 / 辅助表格（默认收起）   │              │
└──────────────────────────────┴──────────────┘
```

侧栏的“定位/查看”只改变视口或打开既有会话，不直接结算、付款或换阶段。地图上方不新增独立消息栏，动作提示留在现有流程条，详细反馈留在会话/信息栏。

建议桌面侧栏约 280–320px；1366×768 下展开一个操作会话后，当前目标格和主要按钮仍可见。1024px 左右采用可收起信息栏；更窄屏采用单抽屉承载辅助内容，避免同时挤压地图。数值作为设计起点，须在现有字体、地图和真实面板上验证。手机完整适配后置，不阻塞桌面主线。

### 4.2 流程条：先说清谁在决定

同时区分：阶段所属方、当前操作者、当前决策角色。E 反应阶段和战斗防方应答必须突出实际操作者，不能只显示 `activeSide`。

流程条保留一个推进按钮：初设时引导完成初设；有强制待办时禁用并显示原因；可进入下一环节时调用现有正式入口；自动段显示处理中；终局显示终止状态。具体判断来自 store/引擎，组件不按阶段名重新拼规则。

待办文字须具体，例如“仍有 2 个编队待西移”“请苏方选择损失承担单位”。可选行动与强制事项分开；“没有合法候选”和“功能缺入口/加载失败”不能都显示成“无事可做”。

### 4.3 初设与增援：一个对象，一项决定

- 初设按“必做事项、可自主放弃项、已完成项”分组；完成数来自实际名单和盘面，不新增 UI 完成标记。
- 卡片展示算子图、名称、所属方、数量、当前状态、落位限制和下一步；使用单位/编队稳定 ID 作 key。
- 点卡片进入点图模式，合法候选格高亮；选定后只由原提交入口落账，失败保留卡片和修正机会。
- 满载车改选、编队处置重试、双方确认分别读取最新进度；成功换手清掉前一方点选，失败时保留当前修正入口。
- S2 的当期增援、移除、转换、动员用同样的展示结构，但其账本与触发仍属 S2 规则域；不要复用初设抽签去实现逐回合事件。

### 4.4 移动：明确区分准备、预览和执行结果

沿用当前“选枚 → 改模式/付燃料 → 开始移动 → 点图行动 → 结束移动”的口径。

会话内展示选中枚数、逐枚资格与燃料状态；地图显示合法范围、当前路径、预期终点和停步标记；操作后显示实际落点、实际费用、剩余 MP 与停止原因。信息全部读取真实移动评估/提交结果。

禁行与强制停步不能只靠颜色区分，要有符号和短说明。预览不扣 MP、不付款、不掷骰、不写 ZOC 承诺。盘面、选择或阶段变化后旧预览失效；提交仍由当前规则域重新检查。悬停不得触发全盘补给追溯。

### 4.5 会话：把可取消、可收起、必须完成分清

| 领域状态                    | 会话表现                             | Esc / 标题栏行为                                           |
| --------------------------- | ------------------------------------ | ---------------------------------------------------------- |
| 尚未提交的选择草稿          | 提示下一步，可取消选择               | 调现有草稿取消入口                                         |
| 未提交的行动                | 只有域明确允许才提供“取消行动”       | 调域取消；失败解释原因                                     |
| 已付款/已掷骰且存在后续义务 | 显示“须完成结算”及当前操作者         | 不清场、不退款、不隐藏必做步骤；可退子级选格时按域能力执行 |
| 增援/专规等可暂时收起的面板 | 标题动作叫“收起”，有明确重新打开入口 | 仅收起展示，待办保留                                       |
| 完成态                      | 显示结果摘要，按既有流程退出         | 不重复落账                                                 |

优先级应由明确的活动流程和待决义务决定，不靠新增一条 `if` 抢在别的面板前面。移动→突袭→战斗收尾→恢复移动由现有域状态驱动，UI 只显示当前可继续的步骤。

初设队列、补给阶段面板可保留摘要，但进入主动选格/选择承担者时，必须取得同一个输入所有权。地图点击、快捷键和弹窗按钮对同一意图使用同一命令入口。

### 4.6 补给、结果与存档

补给会话显示“受益单位 → 合法来源 → 路径/覆盖 → 费用 → 付款后余额”，支持点来源定位地图；来源失效时返回可修正选择。追溯状态、战斗补给、燃料与部队储备保持不同标签，不混成一个“有补给”。

自动结算后提供可查看的摘要及“定位相关格”。只有点击定位或进入必须选格的步骤才移动视口，不在每次刷新时抢走玩家视角。热坐遮屏期间不显示上一方的单位详情、来源或聚焦列表；所有摘要沿用战雾裁剪，不暴露隐藏枚数或未知 ZOC。

存档入口明确显示“可保存”或“先完成当前移动/战斗结算”等原因，成功提示带实际保存的回合与环节。未开局初设暂不支持保存；已结束移动不能继续被当作阻断。读档失败保持当前局不变；不承诺战斗中途续局。参考站的“本地自动保存”不作为本轮要增加的功能。

## 5. 怎样配合解耦

以下名称为拟议模块，实施时可依仓库命名微调；不要求先造一套框架再接功能。

| 落点                                    | 责任与边界                                                                  |
| --------------------------------------- | --------------------------------------------------------------------------- |
| `stores/table-flow-model.ts`（拟新增）  | 从正式流程、待决事项及角色事实生成只读流程模型；不推进、不另存阶段          |
| `stores/map-session-model.ts`（拟新增） | 将活动域状态映射为会话身份、步骤、操作者、关闭能力；不持第二份战斗/空军状态 |
| `stores/map-click-router.ts`（拟新增）  | 按唯一活动输入意图分派地图点击；通过显式端口调用既有命令，不扣款/掷骰       |
| `stores/map-presentation.ts`（拟新增）  | 生成经过战雾裁剪的显示投影，复用现有渲染 DTO；不成为新状态总库              |
| `stores/map-view.ts`                    | 先保留公开接口，逐步转为上述模块的装配与兼容层，每次只迁一类职责            |
| `components/session/FlowStrip.vue`      | 渲染统一流程模型，发出推进/查看意图，不从文案推导是否允许推进               |
| `components/map/MapDock.vue`            | 拖动、边界夹取、焦点、关闭按钮文案与无障碍；具体业务取消由调用方执行        |
| `GameTableView` 与各行动面板            | 布局与 props/emits；已有领域面板逐个迁移，不一次重写全部                    |

投影建议包含 `phaseOwner`、`actingSide`、`decisionRole`、`primaryAction`、`blockers`、`sessionId`、`closePolicy`、`ruleRefs`。这些是显示契约，正式事实仍只有一份。

优先复用 `engagementDecisionRole`、`combatIsCommitted`、`barrageIsCommitted`、初设 obligations、已有动作许可表与快照守卫。缺少统一可查询能力时，随对应域补只读查询接口，查询与提交复用相同判据；不能让 UI 自己推断“付过款就等于哪一步”。

显示会话身份优先取领域已有稳定 ID；没有时只在会话创建时分配显示 ID，重绘不变、更换动作才变，不改领域身份与存档格式。临时视口、展开态、拖动位置不冒充必须持久化的规则状态。

## 7. 验证与量化标准

### 7.1 自动验证

复用既有测试，优先补真实缺陷和跨入口差异，不为纯 CSS 机械新增测试：

- 初设：`setup-obligations-flow`、`setup-completion-flow`、`setup-start-entry`、`setup-save-lifecycle`。
- 流程/会话：`map-view-session`、`map-view-flow`、`hotseat-flow`；补 E 反应角色、同类新会话草稿隔离、收起重开和已提交取消拒绝。
- 输入：`render/map-input`、`components/dock-position`；保留浮层归属与边界逻辑。
- 连续链：现有 `tests/flows/setup-harness.ts` 及首行动流程，覆盖正式开始、移动、结束、保存和冷恢复，不靠手改阶段/坐标绕前置。

代码批按主计划执行 `npm run check` 与必要的 `npm run build`；跨域提交跑全量回归。本文为纯计划，本次只检查文档格式和差异，没有重跑业务测试，也没有将历史测试数量当作本次结果。

### 7.2 必须用真实界面验收

| 场景                        | 通过标准                                                   |
| --------------------------- | ---------------------------------------------------------- |
| 必做初设未完点击确认        | 明确列出未完对象和修正入口，既不换手也不丢当前操作         |
| 满载名单完成后改选          | 清单和实际载货重新核对，不显示旧的“已完成”                 |
| 合法点图、非法点图          | 合法动作可继续；非法动作有具体原因，盘面与骰序不变         |
| 会话拖动/滚动/按钮/双击     | 不穿透地图、不引发额外点格；面板不丢出可操作范围           |
| 指针拖出画布或被取消        | 平移/选格能结束，无粘住的拖动状态                          |
| 热键、按钮、地图三入口      | 同一动作得到同一拒绝原因和提交结果                         |
| 付款/掷骰后点 ×、Esc 或换段 | 义务和现场保留，不重复扣款、不重新掷骰                     |
| E 反应与战斗防方应答        | 操作者提示、遮屏与可选对象一致，无越权和信息泄露           |
| 移动中与结束后保存          | 进行中明确拒绝；结束后成功，冷恢复位置、MP和已结束状态一致 |
| 侧栏折叠/托盘展开/窗口缩小  | 当前目标与主操作可见，强制待办有重开入口，不被隐藏后遗忘   |

可用性目标：选中对象后最多一次显式选择即可进入相应合法行动会话；需要声明/付款的步骤保留。待办从条目到地图定位至多两次操作。任何被拒动作都显示原因及可执行的下一步，不能静默无反应。

性能先留测量基线：固定剧本/单位数量/分辨率，记录连续拖图、缩放、悬停预览及打开会话的响应。目标是在稳定测试设备上，普通交互反馈 p95 不超过 100ms，连续拖图尽量保持至少 30fps；这是验收目标，尚无本次实测值。重计算按依赖失效并显示处理中，不允许通过缓存沿用错误盘面。没有测量收益前不更换渲染技术或做全面重绘优化。

## 8. 风险、回滚与交付记录

- 规则资格和显示可用性出现两份实现：以既有域判据为唯一来源，同时保留提交入口最终守卫。
- 新旧会话模型并存：采用“同一输入对照输出→接一个域→移除该域旧分支”，不让两套模型同时决定当前会话。
- 隐藏按钮被误当作修复权限：用 store 正式入口补越权/重复提交回归，组件禁用仅负责反馈。
- 预览或视口定位泄露隐藏信息：复用当前可见性裁剪，测试隐藏枚数、未知控制区和交接遮屏。
- 界面重排影响地图坐标：沿用 `hexToWindow`/现有坐标换算，检查浏览器缩放、设备像素比和侧栏切换后的锚点。
- 覆盖旧文档引起排期分叉：本文只追加 UI 配套；旧 `UI重做方案` / `UI重做分批计划` 保留历史，不把已完成 B 批重新标待做。

每个实施批记录：对应主线批次、改变的入口、实际修改文件、自动回归、人工截图/操作结果、仍未验项、Git提交或备份回滚点。只迁移布局和展示的批次应保持存档契约；涉及正式状态字段时另列迁移方案，不能混在样式调整中提交。

本计划最终交付要求：玩家能够清楚知道“轮到谁、现在做什么、哪些对象能选、为何被拒、这一步是否已落账”，并通过真实正式界面完成对应主线。完整主线、全规则覆盖和人工签收仍按重构计划分别验收。
