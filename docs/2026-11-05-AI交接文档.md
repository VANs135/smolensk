## 4. 当前计划与优先级

执行顺序为A0盘点 → S1初设/抽取 → S2增援及专规日程 → A1阶段 → A2地面移动/ZOC → A3补给 → A4战斗/轰炸 → A5其它非空运行动 → A6交叉验收。共用阻断可以插入当前批次，最近A3修复即属此类，不能据此把S1/S2永久推后。

| 层级 | 退出条件                                                       |
| ---- | -------------------------------------------------------------- |
| R0   | 各可选剧本从新建到合法开局，增援与专规日程核对通过             |
| R1   | 双方完整A–H有真实常规行动并连续结算                            |
| R2   | 全部非空运适用行动、专规和日期分支覆盖，合法结算点存读档可继续 |
| R3   | 补齐空运/空投等低频项，再验完整回合                            |

完整Game Turn包括准备、先手方A–H、后手方A–H和回合收束。E反应阶段通常由对手操作，先手也不能写死为轴方。不能以空过所有阶段、预制盘面或演练编辑工具代替真实流程。互斥模式和结果分支通过多个合法场景覆盖，不要求一个单位一回合做完互斥动作。

## 6. 接手后优先做什么

### 先关闭当前补给链的验收缺口

最近刚改D段恢复→供养→实际断补→损耗。建议先用真实工作台付款/拖取网络验证，而不只依赖替身端口：

- 多单位共用或部分重叠补给源、完全不同补给源时，恢复优先和供养额度的来源是否一致，是否有跨来源借用已付费额度的问题。这里是待核查风险，尚不能称全部已复现或已修复。
- 供养后进入实际损耗名单；掷骰后等待玩家分摊时，合法保存策略明确；如果允许该状态保存，冷读档后骰面、分摊、义务和付款账本必须保留，不重掷、不重复付款、不丢待办。
- 不用修改库存数字代替运输/装卸/付款，验证资源来源和去向能对账。

随后回到S1/S2的P0主线：逐剧本正式开局及资源总账、逐回合到达/移除/转换/补给/补员/慢动员日程。苏军慢动员的锁定对象、按军/师释放及玩家选择、所属部件完整释放仍是待核查重点；不要把计数递增或已有测试通过当作专规正确的证据。之前上下文提示当前实现可能依赖编号前缀与全局数量，需重新定位核实后再裁定和修改。

### 仍然不能宣布完成的事项

- S1/R0完整初设和资源总账、真实界面验收。
- S2所有适用日期和剧本的日程覆盖、苏德专规完整验收。
- 地面来源的整体分配、SP运输/装卸/防接力与付款联验。
- ZOC在移动、补给、战斗、撤退和推进中的独立政策及正式承诺账本。
- 地面战斗/轰炸从宣布、补给、骰序到损失、选项、撤退、推进、进击的全链，以及已付款/掷骰后不能通过取消逃避结算。
- 双方完整回合及各单位行动清单的自动与人工证据。

上述是后续任务，不代表每一项都有已定位代码缺陷。接手者应记录具体复现、规则依据、预期、实际与测试，再修复。

## 7. 代码入口与解耦边界

- `src/stores/workbench.ts`：仍较大的集成层，构建事实、连接地图和跨域提交。不要继续向其堆规则计算，也不要为了拆文件而改行为。
- `src/stores/setup.ts`与`src/engine/rules/setup*.ts`：初设来源、必做项、抽取进度；`src/engine/setup-draw-snapshot.ts`保存抽取历史。
- `src/stores/phase-coordinator.ts`：阶段协调；`snapshot-registry.ts`、`game-snapshot.ts`及`src/engine/board-snapshot.ts`负责保存恢复链。
- `src/stores/supply-phase.ts`：D段独立域，显式端口处理付款、标记、淘汰、骰源和日志。
- `src/engine/rules/supply-phase.ts`：恢复、供养计划、损耗规则；`supply-phase-progress.ts`提供待办推进；`trace-supply.ts`提供补给事实和可达性。
- `src/engine/rules/normalize-supply-dumps.ts`：归并与别名；`panzer-groups.ts`：装甲集群供给限制。

D段重要账本为`supplyRecoverySettled`、`supplyFeedingSettled`、`supplyPhasePlan`、`attritionInputs`、`attritionResults`和`attritionAppliedHexes`。供养结算后不应重算/清计划绕过损耗；新阶段才重置。实际供养费通过纯函数`supplyPhaseFeedingCostT`计算，只累计付款成功者的RE。当前不新增存档字段。

规则计算放`engine`，纯TS、无Vue/Pinia/DOM/网络/Math.random；store负责显式事实与提交，组件负责交互和展示。随机走种子RNG，数值读数据/规则常量，TypeScript严格模式禁用any。改变状态所有权时一起核对保存恢复和生命周期。
