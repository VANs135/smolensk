## 1. 术语定义

### 1.1 具象补给（有 SP 实物）

> 用户口径：战斗补给付费、图上 SP、HQ 按「投递距离 + 类型」发放 SP、单位自带（卡车/内部储备）。

规则落点（原文）：

- **12.3a**（txt 1395–1402）：「要拖取补给时，单位必须在一个补给站的 **5MP** 内，或单位在补给站的相邻格内(12.3c)。……在计算单位到补给站的距离时，**始终要使用轮式 MP**。(例外：对于投递距离为步行或履带的指挥部，则使用对应的移动类型)。」
- **12.3b**（txt 1408–1420）：「能够从补给站拖取SP的指挥部(根据 12.3a)，可以将其他单位所需补给传递至更远处，**距离以它印刷的投递距离为准**。指挥部的投递距离会显示在算子上，单位是 MP。**数字的颜色用来表示该投递距离的移动类型**(3.1a)。……或者也可投递到与指挥部相邻(12.3c)的单位处。」
- **12.4**（txt 1403–1420）：「直接拖取(12.3a)和指挥部投递(12.3b)都可用于接收及分配战斗补给(9.5)。……攻击者的消耗为每个攻击的军力各消耗 1T……防御者每次战斗的消耗合计为 2T……」。
- **12.10a**（txt 1615–1622）：「只有在单位无法从图上补给获得所需SP时(通过直接拖取或从指挥部投递)，才能使用部队储备。」

### 1.2 抽象补给（追溯补给线，不消耗 SP）

> 用户口径：单位 trace 到补给源（铁路网/城市/地图源），不消耗 SP，只判「在补给/脱补给」。

规则落点（原文）：

- **12.6 开头**（txt 1458–1462）：「战斗单位需要在自己的补给阶段中，检查是否存在追溯补给。如果无法获得追溯补给，且无法”吃图上补给”(12.6c)，则该战斗单位会被标记为断补……」
- **12.6a**（txt 1466–1475）：「补给源分为三种：1) 允许增援入场的地图边缘铁路格，加上游戏专属规则中提到的其他补给源，或 2) 火车卸货格(见13.3c)，或 3) 包含一个延补队(12.7)的格，且该延补队可与一个火车卸货格相连，或直接与一个补给源相连。」
- **12.6b**（txt 1477–1481）：「在上述类型的补给源格内如果有一个敌军 ZOC，则会阻止玩家从该补给源获得追溯补给，但这些敌方 ZOC 可以根据 4.5b 的说明被抵消。」
- **12.6c**（txt 1484–1495）：「无法向补给源”追溯补给线”的战斗单位，可以通过”吃”SP，来获得追溯补给。每消耗 1T，就可以为最多 2RE 的战斗单位提供追溯补给(前提是单位在补给站的**拖取或投递距离内**)。所有小数向上取整……**只有在没有追溯补给的情况下，单位才能”吃图上补给”**。」
- **12.6d**（txt 1498–1499）：「战斗单位如果不能”追溯补给线”，也不能”吃图上补给”，则会被标记为断补，并进行损耗掷骰(见 12.8)。」

### 1.3 三条边界（用户口径，规则支持）

| 边界句 | 规则支持 | 代码落点 |
|--------|----------|----------|
| 「能 trace 到源」≠「手上有 SP 可付」 | 12.6 判「有没有追溯补给」；12.4 判「付几 T」；两条判据各自独立 | `hasTraceSupply()`（`trace-supply.ts:1253`）vs `deliverableDumpsFor()`（`workbench.ts:9998`）/`combatSupplyDumps` |
| 「HQ 投递距离内」≠「trace 成立」 | 12.3b 只判「HQ 能不能把 SP 投到单位」；trace 走 12.6a 的三类源 | `hqDeliveryDumpKeys()`（`workbench.ts:9963`）vs `hasTraceSupply()` |
| 「脱补给」≠「不能领 SP」 | 12.6c 正文明写**无法 trace 者**才可以吃 SP；12.6d 是「两样都没有」才断补 | `assessUnitSupply()`（`trace-supply.ts:1489–1508`） |

### 1.4 规则自带的一座桥（不是串味）

**12.6**（txt 1463–1464）：「直接拖取(12.3a)和指挥部投递(12.3b)均可用于**追溯补给的接收与分配**。」

⇒ 具象的「拖取/投递」本身也是抽象「追溯补给」的一种**取得方式**。因此：

- 「`hasTraceSupply` 在拖取成功后置真」**不是串味**，是 12.6 明文规定（代码在 `markTraceSupply()`，`workbench.ts:10827`，注释 10824 明写这条对接）。
- 但字段名 `hasTraceSupply` 同时承载「trace 成立 / 拖取成功 / 空投豁免 / 特殊续命」多种来源 ⇒ 属**命名/展示问题**（§4-(b)(d)）。

## 3. 命名混淆源：`trace-supply.ts`

用户的直觉是对的，但需要精确：

| 名字 | 实际服务 | 说明 |
|------|----------|------|
| `drawableDumpsFor` | **具象**（12.3a/c 直接拖取） | 位置合理（在 `trace-supply.ts` 因为 12.3d 与 12.6 共用计费原语），但文件名「trace」误导 |
| `hqDeliveryDumpKeys` | **具象**（12.3b HQ 投递） | **不在 `trace-supply.ts`**，在 `workbench.ts:9963`（store 层） |
| `countSupplyDistanceToAny` | **两侧共用**（12.3d 的「假想非战斗单位」计费） | 12.3a/b 拖取投递与 12.6c 吃图上 SP 都用它 |
| `nearestTarget` | **已删除** | 并入 `nearestInBudget`（`trace-supply.ts:832`），注释 824–831 声明与旧实现逐字等价 |

**为什么文件名是 `trace`**：该模块以 12.6 追溯为主入口，但 12.3 的拖取/投递与 12.6c 的「在拖取/投递距离内」**必须共用同一个 12.3d 计费原语**；把具象原语放回 `supply.ts` 会与抽象侧形成两套距离实现（历史上正是漂移源）。⇒ 现状是「**文件按主入口命名**，内含两套」，不是「把抽象当具象」。

## 4. 串味清单 (a)–(d)

### (a) 具象判据里用了抽象的距离/路径

- **现象**：`canEatOffTheMap`（抽象兜底）→ `canDrawFromDump`（具象）；`combatSupplyDumps` 链只走 `deliverableDumpsFor` 的**纯距离**。
- **判定**：**规则一致**。12.3d（txt 1441–1447）明文三种路径共用计量；12.6c（txt 1487–1489）明文「前提是单位在补给站的拖取或投递距离内」。
- **是否有反例**（具象判据读 trace 状态）：`combatSupplyDumps` / `confirmCombatSupply` 均**不读** `hasTraceSupply`（本轮 grep 复核：`attackerAvailableT` 无该字段读取）。**结论：无串味**。

### (b) 抽象判据里用了具象的 SP 存在性

- **现象 1**：`assessUnitSupply` 先判 trace，成功则**禁止**吃图上 SP（`reason: 'alreadyTraced'`，`trace-supply.ts:1493–1495`）。
- **判定**：**规则一致**，12.6c 末句「只有在没有追溯补给的情况下，单位才能吃图上补给」。这是**规则要求的单向耦合**，不是「有 SP ⇒ trace 成立」。
- **现象 2**：`refreshTraceSupply` 把 `sustainedThisTurn`（12.6c 吃图上 / 12.10e 储备 / 21.10 缓存）算进 `inSupply` ⇒ `hasTraceSupply = true`（`workbench.ts:11096–11102`）。
- **判定**：12.6c 原文确实说吃 SP 是「获得追溯补给」⇒ **原文有支撑**；但 12.8e 括注（txt 1630–1637）把「吃图上补给」与追溯补给**分开列举** ⇒ 产生歧义 **Q1** 与内部不一致 **E2**（§6、§7）。
- **是否存在「trace 失败 ⇒ 不能领 SP」**：否。`canEatOffTheMap`（`trace-supply.ts:1292`）**完全不读** `hasTraceSupply`；trace 失败恰恰是吃 SP 的入口。**结论：无该串味**。

### (c) 同一张缓存表（2b 的 `WeakMap<facts, tables>`）被两套共用

- **确认共用**：`distanceTables`（`trace-supply.ts:507`）被 12.3a/b 拖取投递、12.6c 可达性、12.7g 延补队回连（间接）共用。
- **判定**：**非正确性问题**。key 是 `side|mobility|maxMp|fromKey`（纯距离语义），value 是 `{best, prev}`，按 `facts` 身份失效；注释 620–624 已声明「只用于源→单位方向，A→B 可达不代表 B→A 可达」。
- **风险**：若未来有人把该表反向复用，会引入**方向性错误**（12.3d 阻断取决于目标格）。⇒ 建议仅文档注明（§10）。

### (d) 同一个 UI 提示把两者混成一个「补给状态」

- **确认**：`SupplyPanel.vue:1074–1080` 只给一个状态 tag（`有追溯补给（12.6a）` / `断补（12.6d）`），「吃图上补给需 X T（12.6c）」是**旁挂**信息，不改变 tag；来源清单（1095–1101）把「基础源（抽象）」与「吃图上补给」「拖取/投递（具象）」放在**同一个选来源列表**。
- **判定**：**展示问题**，非规则错误。`hasTraceSupply` 语义混装（trace / 拖取成功 / 空投豁免 / 特殊续命），标签无法区分「凭什么有补给」。
- **规则一致性**：12.6 明文允许拖取/投递用于追溯补给的接收 ⇒ 「有补给」的结论正确，只是**来源不可见**。

## 5. 四条基线核对

### 5.1 脱补给仍可吃图上 SP 维持状态 —— **一致**

| 检查点 | 代码事实 | 结论 |
|--------|----------|------|
| trace 失败的单位能否进「吃图上 SP」判定 | `assessUnitSupply`：`trace.ok ? eat=alreadyTraced : canEatOffTheMap(...)`（`trace-supply.ts:1489–1502`） | 能；trace 失败**正是**吃 SP 的入口 |
| 是否有「脱补给 ⇒ 不能领 SP」 | 无。`canEatOffTheMap` 不读 `hasTraceSupply`（`trace-supply.ts:1292–1325`） | 无该耦合 |
| 是否有「有 SP ⇒ trace 成立」 | 无。`eat` 的结论不回写 `trace`；`status` 由 `trace.ok` 优先决定（1504–1508） | 无该耦合 |
| 12.6c 的「前提在拖取/投递距离内」 | `canEatOffTheMap`：先 `canDrawFromDump`，再逐 HQ（`selfAndNeighbors` + `countSupplyDistanceToAny`） | 一致 |
| 12.6e 战略模式禁吃 | `unitMode==='strat'` 直接拒（1304–1305） | 一致 |
| 12.6c「永不强迫」 | `planOutOfSupply` 只有玩家勾选（`eatOffTheMap?.()`）才摘标（1556） | 一致 |

**残留问题（E2）**：喂食后「已带断补标」与「未带标」的单位落盘结果不同（详见 §6-E2）。这是**内部不一致**，不是本条基线被违反。

### 5.2 HQ 投递 10/8 MP（按方常数） —— **与用户口径不一致；与原文一致**

**原文**（12.3b，txt 1408–1417）：「距离以它印刷的投递距离为准。指挥部的投递距离会显示在算子上，单位是 MP。数字的颜色用来表示该投递距离的移动类型(3.1a)。」

- 原文**没有**「德军 10 / 苏军 8」的按方常数；只有「按算子印值 + 颜色表移动类型」。

### 5.3 道路 0.5 MP/格 ⇒ 10 MP = 20 格、8 MP = 16 格 —— **一致（纯道路）**

| 检查点 | 事实 | 结论 |
|--------|------|------|
| 道路格代价 = 0.5 | `charts-tec.json:271–300`：`Secondary Road`（hexside），`track/truck/leg` 均 `fixed 0.5`；`note`:「沿路移动时按本行取成本（6.2a road override），无视格内地形」 | 一致 |

| 实算（用实际函数，非手算） | 合成纯道路地图（`road:'secondary'` 边、`terrainsPresent: []`），`createTraceSupplyFacts` + `countSupplyDistanceToAny`：**maxMp=10 → 可达 20 格，逐格 1:0.5 … 20:10.0；maxMp=8 → 16 格（16:8.0）** | 一致 |

### 5.4 12.3c「相邻即可」专项 —— 直接拖取**一致**；HQ 投递**缺失**

**原文全文**（12.3c，txt 1436–1439）：

> 「12.3c 相邻即可。补给路径的”相邻即可”规则非常重要：无论地形如何(即使是禁入地形)，只要补给能到达单位的相邻格，那么单位就可以获得补给。这适用于所有使用直接拖取或指挥部投递的补给机制。」

（12.3a 同义句，txt 1395–1397：「单位必须在一个补给站的 5MP 内，或单位在补给站的相邻格内(12.3c)」；12.3b 同义句，txt 1418：「或者也可投递到与指挥部相邻(12.3c)的单位处」。）

**逐情形分开写**（不同对象的口径不同，不能合并）：

| 机制 | 原文口径 | 实现 | 结论 |
|------|----------|------|------|
| 直接拖取（12.3a/c） | 5 MP **或** 相邻（不论地形） | `drawableDumpsFor`：`targets = selfAndNeighbors(hex)` + `adjacent = areAdjacent(dump, hex) || sameHex(...)`，`canDirectDraw` 邻接短路（`trace-supply.ts:772–782`、`717–735`） | **一致**（判据含邻接；邻接判定本身是 O(1)：`areAdjacent`，`hex-geometry.ts:210`） |
| HQ 投递（12.3b + 12.3c） | 投递距离 MP **或** 相邻（12.3c 明写适用于投递） | `hqDeliveryDumpKeys`（`workbench.ts:9963–9996`）**只用** `countSupplyDistanceViaTable(from: hq.hex, to: unit.hex)`（`trace-supply.ts:626`），**无邻接分支**；其自身注释 9958 却写「印刷投递距离，或 12.3c 的相邻」 | **不一致 ⇒ E1 疑似规则错误** |
| 12.6c 吃图上 SP（HQ 支） | 前提「在投递距离内」+ 12.3c | `canEatOffTheMap` 用 `selfAndNeighbors(unit.hex)` + `countSupplyDistanceToAny`（`trace-supply.ts:1309–1322`） | **一致** |
| 追溯补给线（12.6/12.6a） | **连通到源**（铁路格/城市/延补队链），**不看格数/MP** | `floodFrom` / `hasTraceSupply`（`trace-supply.ts:1253`） | **一致**（与 12.3c 无关，不能被「相邻」替代） |
| 12.3d 的计量 | 三种路径共用假想非战斗单位 | `supplyStepCost` 共用 | **一致** |

**调用链（HQ 投递）**：

`deliverableDumpsFor`（`workbench.ts:9998`）→ `hqDeliveryDumpKeys`（9963）→ `countSupplyDistanceViaTable`（`trace-supply.ts:626`）→ `runDijkstra`（551）→ `cachedSearch`（521）→ `distanceTables`（2b 缓存）。

- **是否只判邻接（O(1)）**：**不是**。该支只判「精确格可达」，完全**没有邻接判定**。
- **是否走了距离/MP/Dijkstra**：**是**（HQ→单位的一次有向最短路，按投递距离预算）。
- **性质**：不是「用错工具」（HQ 投递本来就按 MP），而是**漏了原文给的邻接捷径**。⇒ 规则缺陷，且**只在「单位所在格不可达/被阻断、但其相邻格可达」时暴露**（例如单位站在禁入地形，或唯一通路只能到相邻格）。

**与 2b/P1a 的关系**：

- `hqDeliveryDumpKeys` 已经是**读表**（每 HQ 一次 Dijkstra，之后 O(1)），因此它**不是**「每单位 × 每 dump 一次查询」那 11.5× 的主体。
- 若按原文补邻接，只需把 1 次表查询扩成 `selfAndNeighbors(unit.hex)` 的 7 次表查询（`countSupplyDistanceViaTable` 对已建表是 O(1)），**不新增 Dijkstra** ⇒ **规则错误与性能无关**。
- 11.5× 的主体是 `deliverableDumpsFor` 对**每个受益单位**各跑一次 `drawableDumpsFor`（轴心 turn 1：287 次查询 / 25 次唯一 / 11.5×，见 `docs/2026-11-05-补给追溯性能方案.md` §1 表）。`drawableDumpsFor` **已含邻接判据**，但**先跑 5 MP Dijkstra、后判邻接**（`trace-supply.ts:776–782`）：邻接本可在 O(1) 时短路，省掉该 dump 的搜索。
  - 该短路**属于**那 287 次的一部分，但**不是 11.5× 的来源**（11.5× 来自「同一距离被逐单位重算」，已由 2b 缓存吸收为 O(1)）。
  - 量化：每单位 5 个 dump 中通常 0–1 个相邻 ⇒ 最多省 ~20% 的拖取搜索；相对 2b 后的「查表 O(1)」收益**边际**。⇒ 若做，属性能微优化，**不在本轮范围**。

## 6. 疑似规则错误清单（**待用户裁定**，未改）

### E1（规则错误）12.3b 的 HQ 投递漏掉 12.3c 邻接

- **条款/原文**：12.3c（txt 1436–1439）「只要补给能到达单位的相邻格……这适用于所有使用直接拖取或**指挥部投递**的补给机制」；12.3b（txt 1418）「或者也可投递到与指挥部相邻(12.3c)的单位处」。
- **代码**：`workbench.ts:9963–9996`（`hqDeliveryDumpKeys`）→ `countSupplyDistanceViaTable(to: unit.hex)`（`trace-supply.ts:626`）。
- **偏差表现**：受益单位所在格不可达（禁入地形/被阻断），但其相邻格在投递距离内时，代码判「投不到」；同模块的 `canEatOffTheMap` 对同一情形判「投得到」⇒ **同一规则两处结论不一致**。
- **影响面**：`hqDeliveryDumpKeys` → `deliverableDumpsFor` → 战斗补给（12.4 / 10.1b-A）可用来源集合；会让本可经 HQ 付款的用例被禁。**不改** trace 状态（12.6 侧由 `canEatOffTheMap` 兜住）。
- **性质**：规则错误（判据缺失），修法成本低（表查询 1→7 次，无新搜索）。
- **状态**：**待裁定**（原文可确证，但本轮只读；且修法需先在 Q2 明确「相邻」方向）。

### E2（内部不一致）喂食后 `hasTraceSupply` 的落盘取决于「有无断补标」

- **条款/原文**：12.6c（txt 1484–1495）「可以通过吃 SP 来获得追溯补给」；12.6d（txt 1498–1499）「两样都没有 ⇒ 断补」；12.8e 括注（txt 1630–1637）把「吃图上补给之后」单列。
- **代码**：
  - `supply-phase.ts:344–350`：`plan.outOfSupply.clear` ⇒ `markTraceSupply(id, true)`；只对**已带断补标**者执行。被喂但**未带标**者不进 `clear`。

- **性质**：内部不一致（规则语义取决于 Q1 的读法）。**待裁定**。

### E3（数据缺口，无法判定）投递距离的「颜色 = 移动类型」无数据

- **原文**：12.3b（txt 1413–1416）「数字的颜色用来表示该投递距离的移动类型(3.1a)」；12.3a 例外（txt 1402–1404）「对于投递距离为步行或履带的指挥部，则使用对应的移动类型」。

## 7. 歧义项清单（**只列歧义与两种读法的结果，不给推荐**）

### Q1「吃图上 SP」是否等于「有追溯补给」

- **原文 A（12.6c）**：「无法向补给源追溯补给线的战斗单位，可以通过吃 SP，**来获得追溯补给**。」
- **原文 B（12.8e 括注）**：「在一个单位发现自己没有追溯补给的第一个回合(**不是在“吃图上补给”之后**，也不是在使用补给储备或树皮汤等特殊的追溯补给方式之后)，上述条件将被免除……」
- **读法 R1**（吃 = 获得追溯补给，12.6c 字面）：本回合被喂饱者 `hasTraceSupply=true` ⇒ **不进入 12.8e 突围候选**；12.6d 断补标记也摘除。
- **读法 R2**（吃 ≠ 追溯补给，12.8e 括注为前提）：被喂饱者仍属「当前没有追溯补给」⇒ **进入突围候选**，但**不享受首回合豁免/+1**（因为括注排除了「吃图上补给之后」）。
- **代码当前行为**：两条路径都有（E2）⇒ **R1 与 R2 同时存在于不同单位**。
- **结果差异**：同回合同一局，被喂单位「能否突围」取决于它此前有没有断补标。

### Q2 12.3c 的「相邻」是相对谁

- **原文 A（12.3c）**：「只要补给能到达**单位的相邻格**。」（相邻格以**单位**为参照）
- **原文 B（12.3b）**：「或者也可投递到**与指挥部相邻**(12.3c)的单位处。」（相邻以**指挥部**为参照）
- **读法 R-A（广义）**：投递路径终点可为「单位的任一相邻格」⇒ `selfAndNeighbors(unit.hex)`。
- **读法 R-B（窄义）**：只对「与 HQ 相邻的单位」成立（HQ 格本身即单位的相邻格）⇒ 只需 `areAdjacent(hq, unit)`。
- **结果差异**：R-A 覆盖「路径能到单位旁边但进不了单位格」的远距离情形；R-B 只覆盖 HQ 贴身情形。**两种读法下当前实现（精确格）都漏判**，E1 成立；但**修法范围不同**。
- 说明：12.3c 末句「适用于所有……机制」更支持 R-A；本轮**不替用户裁定**。

### Q3「第一个回合」的起点

- **原文**（12.8e）：「在一个单位发现自己没有追溯补给的第一个回合……」。
- **代码**：`cutSinceTurn`（`workbench.ts:11108–11109`）只在「由有到无」时落值；`isFirstTurnOfBeingCut` 要求 `cutSinceTurn === turn`。
- **两种读法**：① 连续断补的**起点回合**（代码）；② 每个「本回合首次发现断补」都算（含反复断补/恢复的回合）。
- **结果差异**：反复断补的单位能否反复拿 +1 豁免。本条**未在规则书中找到进一步限定句**，代码取①。
