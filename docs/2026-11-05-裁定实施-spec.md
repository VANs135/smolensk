## 5. ⑦ 3.3c 撤离 + 通用选择机制（已实施）

### 5.1 规则依据与口径

- 专规 3.3c：「On 19 August, start rolling during every Axis Reinforcement Phase until a division,
  either SS Reich or 14th Motorized, is Removed (using the 1.6a procedure). See Axis Arrival Card.」
  表值：`1 → remove SS Reich (all)`、`6 → remove 14 Mtr (all)`、`2-5 → roll again next turn`。
- 1.6a：「When a unit is called on to be "Removed" by the arrival charts **it, or else a unit with
  identical factors**, is immediately removed from play, regardless of its current situation
  (even if in the dead pile or surrounded).」
- 用户裁定（2026-11-05）：撤离结果出现时**直接移除**该编队；若该编队已无算子在场，**由玩家从符合条件者中选择**。
  通用交互要求：高亮有可选单位的格子、玩家点选；堆叠中只列可选单位。

★ 口径（**实现依据：1.6a 原文**；2026-11-05 用户裁定"按原文来"，无需另裁）：

1. 「已被消灭」＝**盘面与死亡堆都找不到该编队算子**。依据：1.6a 原句
   「…is immediately removed from play, **regardless of its current situation (even if in the dead pile
   or surrounded)**」⇒ 死亡堆内的目标仍**直接**移除、不触发选择。
2. 「符合条件」依据 1.6a 原句「**it, or else a unit with identical factors**」：本实现取**战斗面印值
   `attack`/`ar`/`ma` 三元组**相等（不含移动力 / 炮击值 / 军力）。替补只在**盘面**算子中挑选
   （死亡堆无格可点，不列入——界面要求"高亮格＋点选"）。
3. 表值的 `(all)` ⇒ 一次移除该编队**全部**算子（盘面地面 + 死亡堆地面）。
   空军单位**没有 `formation` 字段**，无法按编队匹配；且 SS Reich / 14 Mtr 均无飞机 ⇒ 行为上等价（不虚构匹配）。

回滚点（技术留痕，不挂审批）：`workbench.ts` 的 `resolveVariableExitNow` / `variableExitSelectionSet`，
以及 `tests/engine/unit-selection.test.ts`、`tests/stores/variable-exit-flow.test.ts` 里
"同印值替补 / 死亡堆直接移除"两组断言。

### 5.2 引擎：可复用「可选单位清单」（新文件 `src/engine/rules/unit-selection.ts`）

纯函数、零规则判断（只做集合运算），供任何"规则要求玩家选单位"的情形复用：

```ts
export interface UnitSelectionCandidate {
  id: string
  col: number
  row: number
  /** 是否可选 */
  eligible: boolean
  /** 不可选原因（eligible=true 时忽略；本机制只列可选者，故一般不用） */
  reason?: string | null
}

export interface UnitSelectionHex {
  col: number
  row: number
  /** 该格**可选**子集（不含不可选者） */
  ids: readonly string[]
}

export interface UnitSelectionSet {
  /** 全部可选 id（按输入顺序、去重） */
  eligibleIds: readonly string[]
  /** 有可选单位的格（只含有可选子集的格；本机制不给"整格都不可选"的格高亮） */
  hexes: readonly { col: number; row: number }[]
  /** 每格可选子集 */
  byHex: readonly UnitSelectionHex[]
}

export function buildUnitSelectionSet(
  candidates: readonly UnitSelectionCandidate[],
): UnitSelectionSet
```

- 排序：`byHex` 与 `hexes` 按 `row` 升序、同 `row` 按 `col` 升序，保证界面与测试稳定。
- 只把 `eligible === true` 的候选放进 `eligibleIds` / `byHex` / `hexes`。
- 单测：空输入；全部不可选；同格混选（只列子集）；跨格混选；重复 id 去重；排序。

## 5.10 修 `engineerCapable` 缺模式判据（2026-11-05，已实施）

- **原文**：5.5b「Units must be in Combat Mode to convert railroad gauge (13.3f) and perform
  Engineering functions (13.8a)」；13.8a「…an HQ or Engineer must be in Combat Mode, **or else be in
  DG Mode and oriented toward Combat Mode** (per 5.10e)」。
- **例外分辨（不做一刀切）**：5.5b 对**全部**工程职能（架桥 13.8b、建造/机场、修铁端等）一律要求战斗模式，
  **没有**按动作分档的例外；唯一的例外来自 13.8a 自身——**DG 但朝向战斗面**。该例外已由 `modes.ts`
  的 `canEngineer`（`MODE_MARKER_EFFECTS.dg.engineering = 'combatOrientedOnly'`）唯一实现，
  ⇒ 不再另写判据，直接复用。
- **缺口**：`workbench-model.ts` 建卡时 `engineerCapable` 只按 `specialized` 含 `'hq'` 判，不看模式
  ⇒ 移动模式 HQ 会被当成工程单位（`construction.ts:178` 与 `air-mission.ts:453` 都吃这个值）；
  且 15.4 基地缩减的 `operatingUnits` 映射**根本没传**该字段 ⇒ 工程能力一侧恒缺席。
- **实现（最小改动）**：
  1. `workbench-model.ts` 新增导出 `engineerCapableNow(unit) = engineerCapable === true && canEngineer(mode)`。
  2. `workbench.ts`：`canEngineerInPhase` 首行改用它；`engineerExecutorFor` 与 `constructionGateNow`
     的 `engineerCapable` 改用它；**15.4 `reduceBaseNow` 的 `operatingUnits` 补 `engineerCapable`**。
  3. `rail-supply.ts` 的 `engineerCapableHqAt` 由 `mode === 'combat'` 改为 `canEngineer(mode)`，
     `EngineerHqFacts.mode` 收窄类型为 `ModeState`（与 13.8a 的 DG 例外保持一致）。
- **既有测试期望变更**：**0 处**。全量 `tests/engine + tests/stores` 258 文件 / 3483 通过 / 3 skip，
  无任何既有用例因本修正而改变期望或删除断言（15.4 的既有用例只覆盖 RE≥1 路径，工程豁免路径此前无断言）。
