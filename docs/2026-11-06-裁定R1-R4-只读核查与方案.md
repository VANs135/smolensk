## 2. R2：12.3c 读法 A（终点可为单位的任一相邻格）

### 2.1 原文

12.3c（txt 1436–1439）：「无论地形如何(即使是禁入地形)，只要补给能到达**单位的相邻格**，那么单位就可以获得补给。这适用于所有使用直接拖取或**指挥部投递**的补给机制。」

### 2.2 当前实现

- 直接拖取：`drawableDumpsFor`（`trace-supply.ts:767`）`targets = selfAndNeighbors(input.hex)`，**已一致**。
- HQ 投递：`hqDeliveryDumpKeys`（`workbench.ts:9963`）只用
  `countSupplyDistanceViaTable(from: hq.hex, to: unit.hex)`（`trace-supply.ts:626`），**无邻接分支** ⇒ 偏差（E1）。
- 12.6c 的 HQ 支（`canEatOffTheMap`，`trace-supply.ts:1309`）已用 `selfAndNeighbors` ⇒ 两处答案会不一致。

### 2.3 实施方案（**不做「范围整体扩一格」**）

新增引擎函数（`trace-supply.ts`）：

```ts
// 读表版「到任一目标」：不传 stopAt ⇒ 走 cachedSearch / distanceTables（每源一次 Dijkstra）
countSupplyDistanceToAnyViaTable(facts, { from, targets, side, mobility, maxMp }) → SupplyDistanceResult
```

- 语义与 `countSupplyDistanceToAny` 相同（min over targets），但**不早停**、**复用缓存**；
- `targets = selfAndNeighbors(unit.hex)`（含自身与六邻；越界格自动跳过）。

再新增 HQ 投递判定（集中 12.3b + 12.3c）：

```ts
hqDeliveryVerdict(facts, { hq, unitHex }) → SupplyVerdict
// targets = selfAndNeighbors(unitHex)
// reach = countSupplyDistanceToAnyViaTable(... hq.throwRangeMp)
// return canThrowViaHQ({ hqMode, distanceMp: reach.mp, throwRangeMp, receivedByThrow })
```

`hqDeliveryDumpKeys` 改为对该 HQ 的每个受益单位调用上述判定（保留「HQ 自身须能拖取该 dump」的既有条件）。

### 2.4 验收夹具（`tests/engine/hq-delivery-adjacency.test.ts`，合成地图）

合成一条 20+ 格直线道路（0.5 MP/格），HQ 10 MP 摩托化投递：

| # | 单位位置 | 期望 |
|---|----------|------|
| 1 | 第 20 格（消耗恰 10.0） | 可获得 |
| 2 | 第 21 格（自身在外，邻格=第 20 格） | **可获得** |
| 3 | 第 22 格（邻格为第 21 格，仍在外） | 不可获得 |
| 4 | 单位格不可进入（`stepCost` 返回 null），邻格在范围内 | 可获得（与 12.6c 口径一致） |
| 5 | 非道路（每格 1 MP、10 MP ⇒ 第 10 格；第 11 格经邻格可得） | 成立 |
| 6 | 既有 `drawable-dumps-equivalence.test.ts` | 全绿、逐字符不变 |

## 3. R3：补给阶段顺序与 12.8e 首回合豁免

### 3.1 当前实现顺序（只读产出）

| 步 | 动作 | 条款 | 代码位置 |
|----|------|------|----------|
| 0 | 进入补给阶段即重判 trace，写 `hasTraceSupply` / `cutSinceTurn` | 12.6 | `workbench.ts:5440` → `refreshTraceSupply`（11076） |
| 1 | 制定阶段计划：① 部队储备恢复（先占 T） | 12.10e-A | `supply-phase.ts(engine):588` |
| 2 | ② 逐单位 `assessUnitSupply`（**追溯**） | 12.6/12.6a-b | 同文件 602 |
| 3 | ③ 玩家勾选的**吃图上 SP**，按来源组扣 T | 12.6c | 同文件 618–668 |
| 4 | ④ 断补置标/摘标（只有真正喂饱者摘标） | 12.6d | 同文件 670–675 `planOutOfSupply` |
| 5 | ⑤ 本阶段损耗义务（按格汇总） | 12.8a/b | 同文件 677+ |
| 6 | 结算恢复 → 结算供养（`markTraceSupply(true)` 摘标） | 12.10e / 12.6c | `store/supply-phase.ts:520–524`、`workbench.ts:11312` |
| 7 | 玩家逐格分摊损耗，**本回合落盘** | 12.8b | `store/supply-phase.ts:460–492` |
| 8 | 移动阶段突围：候选=`!hasTraceSupply`；豁免=`cutSinceTurn===turn && sustained!==turn`，+1 | 12.8e | `workbench.ts:7436`、`7392` |

**与用户口径比对**

| 问题 | 答案 |
|------|------|
| 先追溯、后图上 SP？ | **是**（步 2 在步 3 前）；部队储备恢复更先（12.10e-A 明文优先） |
| 「不吃就马上断补判损耗」本回合还是下回合？ | **本回合**（步 4/5/7 同一补给阶段）；符合 |
| 首回合豁免/有利修正落在突围阶段？ | **是**；补给阶段在移动阶段之前 ⇒ 被切断当回合的突围就享豁免/+1 |
| 第二回合起取消豁免？ | **有**（`cutSinceTurn` 非当前回合 ⇒ 无豁免）；但见下方偏差 |

### 3.2 已确认的偏差（E2，必须修）

- 喂食后：`applySupplyPhaseFeedingNow` 对 `plan.outOfSupply.clear` 统一 `markTraceSupply(id,true)`
  ⇒ **已带断补标**的被喂单位 `hasTraceSupply=true`、`cutSinceTurn=null`；
  **未带标**的被喂单位保持 `hasTraceSupply=false`。同一规则两种落盘。
- 后果：被喂单位（已带标）① 被 `12.8e-A` 当作「有追溯补给的友军」；② 不进突围候选；
  ③ `cutSinceTurn` 被清空 ⇒ 下一次断补又算「首回合」，**可能反复拿豁免**。
- 用户裁定：吃图上 SP 属「其它手段」，**吃了不算断补，但也不等于有追溯补给**。

### 3.3 实施方案

1. **`hasTraceSupply` 只表示追溯类**（trace / 空投豁免 / 不需补给单位），**喂食不再写 true**。
2. 新增纯函数（引擎）：`isOutOfSupplyNow(unit, turn) = !hasTraceSupply && sustainedBySpecialSupplyTurn !== turn`
   （喂食/储备/21.10 续命均算「不吃也不算断补」）。
3. 所有把 `!hasTraceSupply` 当「断补」用的位置改走该函数：
   - `store/supply-phase.ts:152`（计划输入 `outOfSupply`）、`workbench-model.ts:1127`、
     `hotseat.ts:156`、`map-view.ts:225`、损耗义务输入（`supply-phase.ts:363` 附近）。
   - **不改**：12.8e 的候选/友军判定仍读 `hasTraceSupply`（原文是「有追溯补给」）。
4. `applySupplyPhaseFeedingNow`：喂食者只 `markSustainedBySpecialSupply(turn)`；`clear` 中
   **仅** `inSupply` 者走 `markTraceSupply(true)`（喂食者不清 `cutSinceTurn`）。
5. `refreshTraceSupply`：`inSupply` 去掉 `sustainedThisTurn`；断补计数同样用 `isOutOfSupplyNow`。
6. 验收夹具（引擎级即可）：三回合时序
   - 回合 1 断补且不吃 ⇒ `outOfSupply=true`，`cutSinceTurn=T`，本回合突围豁免 `isFirstTurnOfBeingCut=true`；
   - 回合 2 仍断补 ⇒ `isFirstTurnOfBeingCut=false`（按条件）；
   - 回合 2 吃图上 ⇒ `outOfSupply=false`、`hasTraceSupply=false`、`cutSinceTurn` 不变（不重置）。
   （若 `isFirstTurnOfBeingCut` 仅存在于 store，则把判据抽成引擎纯函数并保留 store 调用。）

### 3.4 需注意的规则冲突（先记录，不自行取舍）

用户「下个回合就有突围有利修正」与引擎「补给阶段→移动阶段同回合」的**回合编号口径**可能差一；
规则 12.8e 原文是「第一个回合……上述条件将被免除」，未规定「回合」从补给阶段还是移动阶段起算。
本轮按引擎既有口径（同回合）实现，并在交付摘要中写明，不擅自改阶段结构。

## 4. R4：投递移动类型通用化

### 4.1 原文

- 12.3a（txt 1402–1404）：「在计算单位到补给站的距离时，**始终要使用轮式 MP**。(例外：对于投递距离为**步行或履带**的指挥部，则使用对应的移动类型)。」
- 12.3b（txt 1413–1416）：「数字的**颜色**用来表示该投递距离的移动类型(3.1a)。」

⇒ 原文已允许「步行/履带投递距离的 HQ」，只是本作数据未给颜色。R4 是把该例外通用化。

### 4.2 现状

- `SupplyMobility = MobilityType`（`src/data`），已含 `leg` / `track` / `truck`；
  `supplyStepCost` 直接复用 `selectMovementTerrain`（同一套 TEC/道路/河侧代价）⇒ **无需另写代价表**。
- `toThrowHqView` 缺省 `throwMobility:'truck'`（`workbench-model.ts:1866`），数据无字段。

### 4.3 Schema 方案（**不动生产数据**）

```jsonc
// units-*.json（可选字段，缺省=不写）
"throwMobility": { "combatFace": "truck", "moveFace": "truck" }
```

- 类型：`Partial<Record<'combatFace'|'moveFace', MobilityType>>`；
- 缺省：未提供 ⇒ 两面都 `'truck'` ⇒ **行为与现状逐字节一致**（同一取值、同一函数）；
- 迁移：**无**（可选字段；老存档/老数据不需改）；
- 读取：`throwMobilityOf(unit) = raw.throwMobility?.[orientation] ?? 'truck'`；
- 兼容性验证：全量测试 + `drawable-dumps-equivalence.test.ts` 逐字符不变；
  另加 1 组夹具：同一合成 HQ 分别 `truck` / `leg`，在「林地 2/1 MP」地形上投递距离不同。

### 4.4 待裁定 / 留白

- 本作**是否有**非轮式投递 HQ：数据无颜色字段 ⇒ **无法判定**（不推断、不填值）。
- 其它作品是否允许徒步 HQ：属作品数据，**不在本作代码判定范围**（留白 L-R4）。
