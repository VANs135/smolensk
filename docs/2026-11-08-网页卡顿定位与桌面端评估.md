# 网页卡顿定位与桌面端评估（2026-11-08）

> 口径：本报告只做定位，**未改任何 `src/` 代码**（`src/engine`、`src/data` diff 为 0）。
> 临时探针脚本放在 `node_modules/.tmp/`（不入库），全部数据来自真实浏览器实机输入。

## 0. 结论摘要

1. **首屏「卡」主要来自开发模式**：dev 首屏要拉 250 个模块、21.9 MB 脚本（FCP 696–984 ms）；生产包 1 个 bundle、0.55 MB（FCP 160–256 ms）。日常若用 `npm run dev` 体验，必然被放大 4 倍。
2. **交互卡顿是应用层真问题，与渲染内核无关**：生产包同样存在 **1327 ms 的「打开移动会话」** 与 **734 ms 的「进入突围环节」** 长任务。
3. **平移/拖拽、点格展开堆叠、点算子并不卡**：平移 3 次实测帧间隔均值/最大均为 17 ms，零掉帧；点格 39–67 ms、点算子 64 ms。
4. **桌面壳不会变快**：Tauri/Electron 共用同一渲染内核，实测成本在 JS 主线程（引擎全量重算 + 响应式代理读取），打包不改变这条路径。桌面端的收益只在分发、离线、文件系统与窗口管理。
5. 本机 **WebView2 157.0.4341.42 已装**，**Rust 工具链未装**（`rustc` / `cargo` 均不存在）；Node 22.12 / npm 10.9 可用。

## 1. 测量方法（可复现）

- 浏览器：无头 Edge（`--headless=new`，1600×1000，DPR 1），CDP 驱动真实鼠标事件（`mouseMoved/Pressed/Released`），非 `element.click()` 合成事件。
- 两套构建各测一遍：`npx vite --port 5199`（dev）与 `npx vite preview --port 4199`（当前 `dist/` 生产包）。
- 采集：
  - 首屏：Navigation/Paint/LCP + `longtask` + 资源传输量（清缓存后各 3 次）。
  - 交互：`Event Timing`（真实输入→下一帧的 `duration`）+ `mark → 双 rAF + 宏任务` 结算耗时 + 期间 `longtask`。
  - 热点归属：CDP `Profiler` 采样，按**自身耗时**聚合到函数。生产包函数名被压缩，故热点函数名取自 dev 采样（两套构建交互耗时基本一致，见 §2）。
- 场景：剧本 1 → 进入对局台 → 初设（用既有 store 动作 `presetSelfSetupNow` + `startGameNow` 收束，不改代码）→ 推进到「模式与移动」→ 点堆叠格 → 点其中一枚 → 点「开始移动（6.1）」。
- 局限：headless 无垂直同步抖动、无 GPU 合成差异；数值用于横向比较，绝对值可能比可见窗口低 5–10%。

## 3. Top 3 热点与证据

### 热点 A：打开移动会话 1.27–1.41 s（最严重）

CPU 自身耗时（dev 采样，总 1460 ms）：

- `neighbor`（[hex-geometry.ts](file:///D:/OCS/smolensk/src/engine/hex-geometry.ts#L160-L165)） **442 ms**
- Vue 响应式 `get`（proxy trap） **362 ms**
- `sameHex` **191 ms**
- 其余为 BFS 队列/对象分配与 `path` 数组拷贝

机制：`reachableForMove` 对堆叠内**每个单位**各跑一次 `computeReachableHexes`（[move.ts](file:///D:/OCS/smolensk/src/engine/rules/move.ts#L545-L612)，本堆叠 7 枚 → 7 次全图 BFS）。BFS 内每格 6 向调用 `evaluateStepFrom`，而 `context`/`unit.hex` 来自 Pinia 响应式对象，每次 `.col/.row` 读取都过 proxy；`neighbor` 每次新建 `{col,row}`；`best` 节点还保存整条 `path` 并逐步 `[...current.path, step]` 复制。

可优化（按收益排序，均不动规则判据）：

1. 会话开启时把 `MoveContext` 需要的单位/地图事实做成**一次性 plain 快照**（`toRaw` + 只读拷贝），BFS 内零 proxy 读 → 直接消掉 362 ms。
2. 六邻表预生成（每格一次）或就地 `col/row` 计算并复用对象；`sameHex` 改成 `col/row` 直接比较 → 吃 191 ms，并压掉 `neighbor` 的大部分。
3. `path` 改父指针回溯，去掉逐节点数组拷贝。
4. `reachableForMove` 结果按 `(unitId, mpSpent, 环节)` 记忆化；先出会话框、高亮计算推迟到下一帧（`requestIdleCallback`），避免点击线程被 1.2 s 阻塞。

### 热点 B：进入「突围」环节 0.60–0.70 s

同一模式：`neighbor` 124 ms、响应式 `get` 106 ms、`terrainsAt` 53 ms、`searchFrom`（补给追踪 38 ms）、`inEnemyZoc` 24 ms、`stepCost` 18 ms。

机制：切段时对所有相关单位预计算突围资格与补给可达；`terrainsAt` 按格扫图层，`trace-supply` 从每个候选格重复展开。

可优化：

1. 只算「玩家点到的堆叠/单位」，其余按需惰性计算（与 UI 新交互规格一致：点开才出会话）。
2. 补给追踪缓存键已含动态事实（[trace-supply.ts](file:///D:/OCS/smolensk/src/engine/rules/trace-supply.ts#L204-L211)），但调用端按格重复触发；把「每阶段一次」的结果上提为共享。
3. `terrainsAt` 建一次「格键 → 图层地形」索引，避免逐次扫描。

### 热点 C：进入对局台/地图首绘 0.37–0.46 s

`getBoundingClientRect` **94–111 ms**（同步布局抖动：挂载期反复读容器尺寸），`(program)` 175–235 ms（Vue 挂载），`terrainsAt` 54 ms，`findUnitRecord` 23 ms。

可优化：挂载期批量读一次 rect（或 `ResizeObserver` 首帧回调）再写 transform；对局台首绘只用已应用的初设数据，避免重复投影；地形索引同上。

## 4. 桌面端评估（基于实测）

前提：Electron 与 Tauri 在 Windows 上都是 Chromium 系内核（Electron 自带、Tauri 走 WebView2）。**打包不改善渲染性能**——本报告的热点全部是应用层 JS 主线程成本，换壳后同一段代码仍要跑 1.3 s。

| 维度               | Web（现状）  | Tauri（WebView2）                                                       | Electron                                   |
| ------------------ | ------------ | ----------------------------------------------------------------------- | ------------------------------------------ |
| 本机前置条件       | 无           | **Rust 未装**（需一次性安装 rustup + CLI）；WebView2 157.0.4341.42 已装 | Node 22.12 / npm 10.9 已有，无需额外工具链 |
| 安装包体积         | —            | 约 3–10 MB                                                              | 约 80–150 MB                               |
| 冷启动             | 浏览器标签页 | 快（复用系统 WebView2）                                                 | 较慢（自带 Chromium）                      |
| 离线/文件系统/窗口 | 受限         | 原生                                                                    | 原生                                       |
| 性能收益           | —            | **无**（同一内核、同一 JS）                                             | **无**                                     |

**推荐**：先按 §3 修热点（这是唯一能真正变快的事）；若确有分发/离线/窗口需求，选 **Tauri**——本机只缺 Rust 工具链（已具备 WebView2），体积与启动都优于 Electron。不建议为「变快」上 Electron。

**打包后必须复测同组指标**（复用 `node_modules/.tmp/perf-probe.mjs`，把 URL 换成 `tauri://localhost` 或壳内地址）：首屏 FCP/LCP、进入对局台、平移帧间隔、开始移动会话。验收线：不劣于修复后的 Web 生产包基线。

### C 进入对局台：**未达成**，已撤回改动（留证据）

生产包同一探针（`click:进入游戏`）实测：**352ms → 264 / 280ms**（B 批次的地形索引附带收益），
仍未到 ≤250ms。为定位，做了未压缩包 + CPU 采样（含调用栈聚合），结论如下。

`进入游戏` 那一次的耗时构成（未压缩包，单次采样）：

| 归属                                    | 自耗时     | 说明                                                        |
| --------------------------------------- | ---------- | ----------------------------------------------------------- |
| `syncSize` 内的 `getBoundingClientRect` | **106 ms** | 挂载期 DOM 刚建好尚未布局，这一次读矩形**强制同步布局整页** |
| `drawMap → drawHexside`                 | **147 ms** | 首屏把两万多条格边逐条 `stroke()`                           |
| 其余（组件挂载、computed、候选渲染）    | ~70 ms     |                                                             |

试过并**已全部撤回**的三条路子（都在等价前提下实测更慢或无差异）：

1. `ResizeObserver` 的 `contentRect` 替掉 `getBoundingClientRect`（并去掉挂载期同步调用）：
   进入游戏 391–613ms，**更慢**——首帧拿不到尺寸，地图先以空视口画一遍再重画。
2. 网格/格边按线型**批量描边**（两万多次 `stroke()` → 3 次）：
   进入游戏 395–462ms、突围段 281–320ms，**更慢**（Skia 对超长子路径反而更贵），已撤回。
3. `syncSize` 尺寸未变时跳过重排/重画：与基线 377/427ms 相比 397/447ms，**在噪声内无差异**。

结论：C 的 ≤250ms 目标**不在"挂载期批量读尺寸 / 去交错布局"这条范围内**——真正的两块是
「首屏整页首次布局」与「首屏两万条格边绘制」，要动就得改渲染策略（分块/降采样/首帧粗画），
或减少对局台 DOM 规模（属 U1 布局范围）。**按约定停下等口径**，未为凑数字改渲染。
