### 1.2 判定

| 块   | 判定                                                                                  |
| ---- | ------------------------------------------------------------------------------------- |
| 1–5  | **本环节必须**（13.9 整编）——只在 `reinforce:consolidation` 这一步出现                |
| 6–10 | **应是另一个独立窗**（2.3c，且**仅苏方 B 段**）；在轴方窗出现属跨阵营泄漏（差异表 ②） |
| 5    | 属于当前步的推进按钮，不单独拆窗                                                      |
| 11   | 「不该在此刻出现」，由 `sessionStep === null` 的兜底全量渲染带出（差异表 ②/③）        |

### 1.3 一句话结论

**这个窗实际承担了 3 件事**：13.9 整编、苏方 2.3c 方面军预备队、环节推进；**应拆成 2 个业务窗**（13.9 整编窗、2.3c 方面军预备队窗），推进按钮各留各窗。另有一个独立缺陷：`sessionStep === null` 时不应全量渲染，窗应显示「本环节已完成」或直接收起。

## 5. 根因与改法（本轮已实施）

1. `SESSION_STEP_GATE` 增加配套的 `SESSION_STEP_HOSTED`：`MapDock` provide `true`；`SessionStep` 用纯函数 `sessionStepVisible(hosted, exposedId, itemId)` 判定。
   - 无宿主：全量渲染（验证页 / 右栏照旧）；
   - 有宿主且无待决：**一节都不渲染**；
   - 有宿主：只认当前暴露项。
2. `ReinforcementPanel` 的 2.3c 块加 `workbench.activeSide === 'soviet'`，与 `frontalReservesPending` 同源双保险。
3. `MapDock` 在无待决时显示「本环节已完成。」，不再留空窗。
4. 窗标题仍取 `segmentStep.label`（SOP 的权威位置）；增援段窗口次序与标题对齐留待批三（增援段专审）。

## 6. 未发现/暂不改

- 战斗、轰炸、空军、移动、补给、专规各窗均按 `SessionStep` 一次只暴露一件，未发现并列多件。
- 事务性动作（A 整备、D 恢复储备、基地修建/缩减/夺取）留在侧栏，不弹会话框，符合「除增援外，点操作才出会话」。
- `reinforce` 段会话的项目次序 vs SOP 环节次序仍可能错位（`reinforceItems` 不按 `stepId` 过滤），归批三统一核。
