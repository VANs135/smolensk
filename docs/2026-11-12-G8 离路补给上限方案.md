# G8 离路补给上限方案

日期：2026-11-12
状态：**方案（本批不改代码）**
缺口编号：G8（见 `docs/2026-11-12-具象补给支付台账.md` §1.4 / §4）

> 结论先行：现有实现里，12.6 的追溯补给是**无界洪泛**（`trace-supply.ts` 的 `baseSourcesFor` /
> `reachableFrom` / `floodFrom` / `floodIncoming` 都不设距离上限）——沿路与离路都不限。
> 本方案把「沿路不限、离路 5 点轮式 MP」落成一个**预算原语**，只作用于 12.6 的追溯链；
> 12.3a 直接拖取、12.3b HQ 投递、12.7b 延补队回连的既有距离口径**一律不动**。

## 1. 原文核对：哪些是原文，哪些是实现口径

### 1.1 逐条原句

**12.3a 直接拖取**

> "要拖取补给时，单位必须在一个补给站的 **5MP** 内，或单位在补给站的相邻格内 (12.3c)。
> 在需要补给时，可从该距离内的一个或多个补给站拖取所需补给。
> 在计算单位到补给站的距离时，**始终要使用轮式 MP**。(例外：对于投递距离为步行或履带的指挥部，
> 则使用对应的移动类型)。计算距离时，就像移动一个单位那样计算 MP (见 12.3d)。"

**12.3b 指挥部投递**

> "能够从补给站拖取 SP 的指挥部 (根据 12.3a)，可以将其他单位所需补给传递至更远处，
> **距离以它印刷的投递距离为准**。指挥部的投递距离会显示在算子上，单位是 MP。
> 数字的颜色用来表示该投递距离的移动类型 (3.1a)。……就像移动一个单位那样计算 MP (见 12.3d)。"

**12.3c 相邻即可**

> "无论地形如何 (即使是禁入地形)，只要补给能到达单位的相邻格，那么单位就可以获得补给。
> 这适用于所有使用直接拖取或指挥部投递的补给机制。"

**12.3d 沿补给路径的移动**

> "任何一种补给路径 (拖取补给、投递补给或追溯补给) 都会视为一个**假象的非战斗单位**沿着一条
> 补给路径逐格移动，以此来计算距离。追溯这种补给路径时，可以穿越敌方非战斗单位、舰船和飞机，
> 但**绝不能穿越包含敌方战斗单位的格**。在计算补给路径时，**6.1 节中包含的所有移动限制都适用**。
> 在使用卡车 MP 计算补给路径时，一个**未被抵消的敌方 ZOC 格，会阻挡进入该格或离开该格的补给路径**。
> 请注意，一些指挥部和延补队使用的是步行 MP 或履带 MP，因此它们的补给路径不受 ZOC 影响。
> 计算补给路径时，**始终按'正常'地形的 MP 消耗计算**(以夏季/晴朗条件为准)，忽略所有临时的
> '恶劣'地面条件，如泥泞和积雪，以及通过运输破坏区域产生的额外 MP 消耗。"

**6.2 / 6.2a 道路**

> "在以下所有情况中，'道路'一词涵盖所有类似道路的地形 (**小径、铁路和各种质量的道路**)。"
> "如果移动中的单位沿着一条连续的道路移动，则该单位便可以使用道路。该单位可**消耗道路移动费用**，
> 并**无视它穿越的格或格边中的地形**。……即使在地图上没有用道路绘图实际显示，
> 请将同格内所有道路和铁路视为相连。"

**12.6 追溯补给**

> "战斗单位需要在**自己的补给阶段**中，检查是否存在追溯补给。如果无法获得追溯补给，
> 且无法'吃图上补给'(12.6c)，则该战斗单位会被标记为断补，且必须检查损耗。……
> **直接拖取 (12.3a) 和指挥部投递 (12.3b) 均可用于追溯补给的接收与分配。**"

**12.6a 补给源（三种）**

> "1) 允许增援入场的地图边缘铁路格，加上游戏专属规则中提到的其他补给源，或 2) 火车卸货格 (见 13.3c)，或 3) 包含一个延补队 (12.7) 的格，且该延补队可与一个火车卸货格相连，或直接与一个补给源相连。"

**12.6b 源格 ZOC**

> "在上述类型的补给源格内如果有一个敌军 ZOC，则会阻止玩家从该补给源获得追溯补给，
> 但这些敌方 ZOC 可以根据 4.5b 的说明被抵消。"

**12.6c 吃图上补给**

> "无法向补给源'追溯补给线'的战斗单位，可以通过'吃'SP，来获得追溯补给。每消耗 1T，
> 就可以为最多 2RE 的战斗单位提供追溯补给 (**前提是单位在补给站的拖取或投递距离内**)。"

**12.6e 战略模式**

> "战略模式的单位不允许'吃图上补给'，且必须此时有追溯补给的格内结束移动。"

**12.7 / 12.7a / 12.7b 延补队**

> "延补队用于帮助连接追溯补给中补给线的断点。"
> "**延补队的唯一作用是创造一个新的位置，以便从该位置上延续追溯补给。**
> (延补队永远不能移动 SP，不能帮助移动铁路货物，也**不能增加投递或抽取的距离**。)"
> "延补队都拥有一个距离 (以 MP 为单位)，这是延补队距离后方被连接格的最远距离。"

**4.5b ZOC 抵消**

> "在执行上述行动的时候，如果某一格内包含友方战斗单位，则该格内的敌方 ZOC 会被抵消。
> 但用于抵消 ZOC 的单位在之后时间里不能消耗 MP 直到当前阶段结束。"

**13.3c 火车卸货格（源②）**

> "符合以下所有要求的铁路格，为铁路卸货格：
> • 该格有村庄、城市 (任意规模)、港口或有工程能力的指挥部 (13.8a)。
> • 该格已被控制 (13.3h)。
> • 该格有一条由铁路构成的路径，该路径可延申至一个补给源，且该路径上没有敌方 ZOC。
> 判断追溯补给时，延补队的连接可以作为该路径的一部分，但延补队不能用于移动货物。
> 注意运输货物时，EZOC 不可以被抵消，但判断与补给源是否连接时，EZOC 可以被抵消。"

**专规 2.1 / 3.1（Smolensk Living Rules v1.1，原文同句）**

> "Pax, Eq, special repls, and breakout returns arrive at any HQs able to get
> trace supply (OCS 12.6a) by **direct draw**, or else in any map-edge supply source hexes."

## 2. 判据设计

### 2.1 三种预算（统一抽象 `SupplyBudget`）

```ts
type SupplyBudget =
  | { kind: 'fixed'; maxMp: number } // 12.3a/12.3b/12.7b：总 MP 上限（现状）
  | { kind: 'offRoad'; maxMp: number } // 12.6 项目口径：道路步 0 计费，离路累计 ≤ maxMp
  | { kind: 'unlimited' } // 仅诊断/旧用例逃生口，不得进产品路径
```

- **固定总量**（现状）：`cost = 该步 MP`，累计 ≤ maxMp。直接拖取、HQ 投递、延补队回连继续用它。
- **离路预算**（新增）：`cost = 该步是否沿 6.2a 道路 ? 0 : 该步轮式 MP`，累计 ≤ 5。
  - 道路步 0 计费 ⇒ 沿连通路网走多远都不消耗预算（"沿路不限"）。
  - 离路步按轮式正常地形成本累计（2/3/4 MP、格边 +N 都算，12.3d）。
  - 判定"是否沿路"沿用现有唯一实现：`crossing.routes` 非空且 `selectMovementTerrain` 给出
    `roadOverride`（`ROAD_FEATURES = ['Secondary Road', 'Track', 'Railroad']`，即 6.2 的"道路"）。

### 2.2 核心公式

```text
edge(from → to) 的可走性 = stepMp(...)（12.3d：图内、不穿敌方战斗单位、卡车时 EZOC 阻挡进出）
edge 的追溯预算成本 =
    budget.kind === 'offRoad'
      ? (isRoadEdge(from, to, mobility) ? 0 : edgeMp)
      : edgeMp
路径合法 ⇔ 累计预算成本 ≤ budget.maxMp
```

- **累计口径**：是"整条路径上所有离路步之和 ≤ 5"，**不是**"每一段离路各自 ≤ 5"。
  因此"离路 3 → 上路 30 格 → 再离路 3"合计 6，判**断**（见用例 U5）。
- **方向性**：与现状一致，`supplyStepCost` 的取费取决于**被进入格**，故覆盖集必须用反向边洪泛
  （`floodIncoming`）；预算也要在反向边上按同一条公式累计，不能复用正向结果。

### 2.3 与 12.3a / 12.3b / 12.7b 的边界

| 机制                         | 预算类型            | 是否本次改动 |
| ---------------------------- | ------------------- | ------------ |
| 12.3a 直接拖取               | `fixed(5)`          | 否           |
| 12.3b HQ 投递 / 12.5e 覆盖   | `fixed(印值)`       | 否           |
| 12.7b 延补队回连             | `fixed(印值)`       | 否           |
| 12.6 追溯（基础源 + 延补队） | `offRoad(5)`        | **是**       |
| 12.6c 吃图上补给的前置       | 复用 12.3a/b 的判定 | 否           |

> 关键：**不要**把 `DIRECT_DRAW_RANGE_MP` 直接拿来当追溯预算。两者数值同为 5，但语义不同：
> 直接拖取的 5 是"总 MP、道路照常计费"，追溯的 5 是"仅离路累计、道路免费"。
> 建议新增独立常量 `traceOffRoadBudgetMp: 5`，避免未来调参互相污染。

### 2.4 与 12.3c「相邻即可」的关系

12.3c 只适用于**直接拖取与 HQ 投递**（原文"这适用于所有使用直接拖取或指挥部投递的补给机制"），
**不适用于 12.6 追溯**。因此：

- 追溯判定仍以"单位格本身能否连到源"为准，不做"相邻格即可"的一格膨胀；
- `traceCoverageHexes` 的 HQ 投递支仍按 12.3b + 12.3c 膨胀一格（该支不经过离路预算）。

### 2.5 延补队

- 延补队回连后方格：`fixed(印值 MP)`，不改（12.7b）。
- 延补队一旦可用，就成为 12.6a③ 的**新源点**；单位到该源点仍按 `offRoad(5)` 判。
- 12.7a 明文"不能增加投递或抽取的距离"⇒ 不允许把延补队的印值加到单位预算上（不是 5+印值）。

### 2.6 需要写进实现注释的三个未决点

- **D1（预算机动类型）**：追溯预算按**轮式**地形成本计（12.3a"始终使用轮式 MP"），
  但路径可走性仍按调用方传入的 `mobility`（12.3d 的 HQ/延补队例外）。二者分开传参。
- **D2（道路判定）**：沿用 `crossing.routes` + `roadOverride`，不新造地形判据；"同格道路视为相连"已由
  逐边道路实现覆盖（6.2a 末句）。
- **D3（专规 direct draw 歧义）**：G7 未裁定前，`hasDirectDrawTraceSupply` 跟随 12.6 收紧；
  若后续裁定"专规 direct draw = 12.3a 的 5MP"，再把增援落点切到 `fixed(5)`。

## 3. 改法：函数签名与数据结构

### 3.1 新常量

- `src/data/rules-constants.json` 的 `supply` 下新增 `"traceOffRoadBudgetMp": 5`；
- `src/data/schema/rules-constants.schema.ts` 同步加 `z.number().int().positive()`；
- `trace-supply.ts` 导出 `TRACE_OFF_ROAD_BUDGET_MP`（不要复用 `DIRECT_DRAW_RANGE_MP`）。

### 3.2 `TraceSupplyFacts` 只做**增量**

```ts
export interface TraceSupplyFacts {
  // …既有字段保持不变…
  /** 12.3d：正常地形成本下的一步 MP（含 6.2a 道路优先）；不可通行 → null */
  stepCost(from: HexRef, to: HexRef, mobility: SupplyMobility): number | null
  /**
   * 新增（可选）：该步是否按 6.2a 走在道路上（道路步在追溯预算里计 0）
   * 缺省不提供 ⇒ 一律按离路计（旧的手写 facts 不必改签名也能编译）
   */
  isRoadStep?(from: HexRef, to: HexRef, mobility: SupplyMobility): boolean
}
```

`createTraceSupplyFacts` 内新增实现，并给 `supplyStepCost` 增加返回 `roadOverride`
（`selectMovementTerrain` 已经给出该布尔值，不新增地形判断）：

```ts
function supplyStepCost(...): { mp: number; road: boolean } | null
```

### 3.3 搜索原语

```ts
interface SearchInput {
  from: HexRef
  side: Side
  mobility: SupplyMobility
  budget: SupplyBudget // 替换现在的 maxMp: number
  stopAt?: ReadonlySet<string>
}
```

- `stepMp` 改为返回 `{ ok, mp, budgetCost }`；`budgetCost` 按 §2.2 计算。
- `searchFrom` / `runDijkstra` / `cachedSearch` / `distanceTableKey`：
  - 累计与截断用 `budgetCost`；
  - 缓存键加入 `budget.kind|maxMp`（同一 `facts` 下 fixed(5) 与 offRoad(5) 必须分开）；
  - `unlimited` 不进入 `cachedSearch` 的有限表（或单列键）。
- `reachableFrom` / `floodFrom` / `floodIncoming`：同样按 `budgetCost` 洪泛；
  `floodIncoming` 仍判 `next → current`。

### 3.5 向后兼容

- **返回结构不变**：`hasTraceSupply` 仍返回 `TraceVerdict`；`traceCoverageHexes` 仍返回 `Set<string>`；

  直接拖取/投递入口默认 `fixed(既有常量)`（行为不变）。
- **手写 facts 兼容**：`isRoadStep` 可选；缺省按"全是离路"计，编译不受影响。
- **逃生口**：`{ kind: 'unlimited' }` 仅供"只测连通性"的旧用例与诊断面板显式使用，产品路径不得传入。
- **常量隔离**：不改 `DIRECT_DRAW_RANGE_MP`，避免把 12.3a 的 5 改成"道路免费"。

### 3.6 是否需要统一的 `tracePathBudget` 抽象？

**需要，且只放在 `trace-supply.ts` 一处。** 理由：

- 现在"距离怎么累计"已经分散在 `searchFrom`、`floodFrom`、`floodIncoming`、`nearestInBudget`
  与 `countSupplyDistance*` 五套代码里；再按入口各写一遍"道路 0 计费"，必然漂移。
- 统一后，`drawableDumpsFor`（fixed）与 `hasTraceSupply`（offRoad）只是**同一原语的两个预算值**，
  测试可以逐格对照"固定 5 与离路 5 的差异"，这本身就是防漂移闸门。
- store 只传 `TraceBudget`，不得自己判"道路/离路"（与现有"判据只在引擎"的架构一致）。

## 6. 落点建议

### 6.1 顺序

```text
① 铁路链路收尾（rail-supply / railhead / 13.3e）      ← 已提交 c69df55 / bfe9828，等其不再改
② 战斗链路收尾（combat-interaction / CombatPanel / workbench 战斗 hunk）
③ 补给消耗段 20 个红用例转绿（attrition / feeding / plan / reach-payment…）
④ G8：trace-supply 预算原语 + 新用例（本方案）
⑤ 只在这之后：把 supply 面板文案、G7 的增援落点裁定接上
```

理由：`trace-supply.ts` 是补给核心的**唯一搜索原语**，它一动，铁路的延补队回连、战斗的断补减半、
补给阶段的喂食与损耗、AI 对打全部同时变；必须在一个"其他线都已绿"的基线上做，红了才能一眼归因。

### 6.2 分批（每批单独提交、跑六门槛）

1. **批 1（纯引擎 + 单测）**：常量 + `SupplyBudget` + `trace-supply.ts` 改造 + 新增 9 条用例；
   此时 store 不显式传参也能工作（追溯入口默认 `offRoad(5)`）。
2. **批 2（接线显式化）**：`workbench.ts` 的两个构造点显式传 `TRACE_BUDGET`；补一条 store 级流程用例
   （断补单位在补给阶段的标记与损耗义务）。
3. **批 3（文案 + 回归）**：`SupplyPanel` 提示；跑全量并在 `docs/` 记录 AI 对打是否出现 stall。

### 6.3 风险与回滚

- **最大风险不是判错，而是判严后 AI 对打 stall**：`tests/flows/ai-selfplay.test.ts` 的 `stalls` 必须仍为 0；
  若出现 stall，优先检查"沿路步是否被误计费"（U1/U4 就是为此设的）。
- **性能**：预算不增加搜索规模（仍是最短路），但缓存键多一维；确认 `traceCoverageHexes` 的
  "按方一次"缓存未被破坏（9.14d 曾因逐格洪泛到 5 秒级）。
- **回滚**：整个 G8 只依赖一个默认参数；若线上异常，可把追溯入口默认改回 `unlimited` 并保留新用例
  （用例显式传预算），无需回滚 store。
