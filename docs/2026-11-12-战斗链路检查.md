## 0. 结论摘要

1. **主链完整**：9.2 十步（`composition → combatSupply → declareAr → declareTerrain → surprise → battleDice → losses → options → retreat → advance`）在引擎状态机（`src/engine/rules/combat-interaction.ts`）与界面（`src/components/combat/CombatPanel.vue`）两侧都有对应步骤、按钮与落盘动作；常规战斗可以走到 `finished === true` 并清理。
2. **历史上「没有可点项」的三处死路已经修掉**：攻方全灭跳过攻方选项页（`optionsSkipped`）、无推进候选时自动收束（`workbench.ts:11194`）、突袭强制推进（9.12g-D）。证据见 `docs/specs/2026-11-10-战斗终局组合收束/spec.md` 与 `tests/stores/combat-terminal-states.test.ts`。
3. **仍然存在 1 个可复现的硬卡死结构点**：撤退落点为空（见 §3 的 C1）。此时「确认撤退」永久灰显，而补给已付 ⇒ **放弃本场战斗与存档同时被拒**，只能重启程序。
4. **1 处规则权利在界面上不可达**：9.10c 守方「忽略选项」勾选框的显示条件依赖上一次提交才写入的字段（见 C2）。
5. **中断不可继续**：战斗中 `settlementBlockedReason()` 拒绝存档，存档文件也不含战斗态 ⇒ 「结算到一半退出」无法恢复（见 C8）。
6. **范围口径**：用户提到的「10.1b 的进攻补给」在本仓库中是**火炮轰炸**补给（`BarragePanel.vue:389-436`、`engagement-inputs.ts:80-86`），不是战斗补给。战斗侧的进攻补给实际走 **9.5 / 12.4**（`battle.ts:252`、`supply.ts#computeCombatSupplyCost`）。本文按 9.5/12.4 核对；10.1b（轰炸）不在本链路范围。

## 3. 卡点与死路清单

> 严重度口径：**卡死**＝没有合法可点项、且无法放弃/存档；**需绕路**＝有出口但不在提示的位置，或被迫多操作；**只是提示不清**＝能走通但玩家会误解。

### C1【卡死】撤退落点为空 ⇒ 确认撤退永久灰显，且不能放弃、不能存档

- **现象**：进入「第 9 步 撤退」后，某单位「候选 0 格」，该行永远 `未选`；`确认撤退` 因 `retreatPlan.complete === false` 永久禁用。此时补给已付，`放弃本场战斗` 被 `combatCancelBlocker` 拒绝，保存也被 `settlementBlockedReason` 拒绝 ⇒ **唯一出路是重启程序**。
- **代码位置**：
  - 落点计算 `src/engine/rules/battle.ts:1123` `planRetreatDestinations`、`:1085` `retreatPathTo`（排除「路径穿越战斗开始时含敌方战斗单位的格」）
  - 只做**几何**可行性检查 `src/engine/rules/combat-interaction.ts:269` `hasHexAtExactDistance`（被 `planOptions` 在 `:779` 调用）——只验证「精确距离的格存在」，不验证「存在合法路径」
  - 确认按钮 `src/components/combat/CombatPanel.vue:713-721`
  - 放弃拦截 `src/stores/workbench.ts:9687` `combatCancelBlocker`；存档拦截 `src/stores/workbench.ts:24611` `settlementBlockedReason`
- **触发条件**：某次撤退（攻方或守方）格数 ≥1，且**所有**精确距离落点的**所有**单调路径都必须穿过「战斗开始时含敌方战斗单位」的格。最直观的例子：撤退单位六个邻格在战斗开始时都有敌方战斗单位（被合围），或撤退 2 格时包围圈把第 1 环全封死。
- **补充**：`planRetreatDestinations` 本身**支持**「必被消灭」的落点（面板图例「暗红＝必被消灭」即来自它），所以这不是引擎能力缺失；缺的是「9.12f 绝对禁穿」与「9.12 必须穿越即消灭」之间没有兜底出口。按 9.12 原文，这种情况本可给一个「必死落点」让单位被消灭后继续。
- **严重度**：**卡死**。

### C2【需绕路 / 规则偏差】9.10c「守方忽略选项」勾选框不可达

- **现象**：守方选项页看不到「行使 9.10c：忽略守方自己的选项」勾选框；玩家只能把选项点数全部吃成损失/撤退。攻方在选项中撤退（9.10c 的主要适用场景）时尤其明显。
- **代码位置**：
  - 显示条件 `src/components/combat/CombatPanel.vue:527-536`：`state.resolution.defender.optionIgnorable === true`
  - 该字段只在 `planOptions` **成功提交后**写入：`src/engine/rules/combat-interaction.ts:910-911`（正常提交分支）与 `:834`（忽略分支自身）
  - 进入守方选项页的路径（`planLosses` → `step: 'options'`, `stage: 'defenderOptions'`）**不写**该字段（`combat-interaction.ts:686-778` 内无赋值）
- **触发条件**：守方选项点数 > 0，且攻方在选项中撤退（或攻方已无法承受其选项）——正是 9.10c 应当可用的两种情形；攻方全灭时另有一键按钮兜底。
- **结果**：唯一能用到 9.10c 的是「攻方全灭 ⇒ 结束战斗」按钮（`CombatPanel.vue:603-614` → `workbench.ts:11022`），其余情形该权利不可行使。
- **严重度**：**需绕路**（被迫承受本可忽略的选项，属规则偏差）。

### C3【已闭合 · `7672eba`】推进步的确认入口已收回战斗面板

- **原现象**：第 10 步面板写着「勾选与确认请点地图上高亮的推进格（就近小窗）」，但防御格**未空**时 `combatAdvanceHex === null`，地图上没有高亮格，玩家以为卡死；唯一出口是点防御格本身弹出小窗。
- **现状（2026-11-12 复检）**：
  - 唯一主按钮在面板 `src/components/combat/CombatPanel.vue:791-795` → `workbench.confirmCombatAdvance()`；
  - 防御格未空时按钮文案就是「结束战斗（不推进）」（`CombatPanel.vue:109-113`），面板同屏写「防御格 未空；本场不推进」（`:764-768`），原提示语已不存在；
  - 地图小窗整段推进已删（`src/components/game/MapActionPopover.vue:359` 只留一句注释），`map-view` 也不再为战斗会话开辅助小窗。
- **验收**：`tests/stores/combat-panel-picker-flow.test.ts` 的「推进勾选与确认的唯一入口在战斗面板」契约（16/16 通过）。
- **严重度**：已解决。

### C4【已闭合 · `7f34a01`】战斗补给已允许逐单位多站取源

- **原现象**：所需 T 大于单站持有量时无法开战，即使附近多站合计足够。
- **现状（2026-11-12 复检）**：
  - `src/stores/workbench.ts:3054` `combatSupplyDumpPicks` 每方记多座已选来源；`combatSupplyDumpIds`（`:3043`）只记首座，保留给旧单源界面/测试；
  - `confirmCombatSupply` 的 `allocateUnit`（`:10601`）按单位逐个分配到该单位 12.3a/12.3b 真正拖得到、且余额足够的已选站；`allocateLump`（`:10624`）承接守方整场 2T 等不可拆需求；先全部校验再一次性落盘，不足整笔拒绝；
  - 测试 `tests/stores/combat-supply-multi-source.test.ts`：两单位两站分别扣款、总额守恒；仅一源不足时整笔拒绝且不动账本。
- **口径**：9.5/12.4 原文未写「必须同源」（10.1b-A 的同源只约束炮击），现按「原文未禁止即允许多站」实现，不再需要原文裁定。
- **严重度**：已解决。

### C5【需绕路 / 提示不清】自动选取攻方会带上战略模式 / 未释放预备单位，开战才被 9.1e 拒绝

- **现象**：点敌方格时，`attackersForHex` 把相邻的**所有** `isCombat && attackCapable` 单位都选进攻方，包括战略模式与未释放预备模式单位；点「开始战斗」后被 `9.1e` 拒绝，面板显示引擎原因码（如 `stratCannotAttack:<id>`），玩家必须逐个点掉才能继续。
- **代码位置**：
  - 自动选取 `src/stores/workbench-model.ts:1420` `attackersForHex`（无模式过滤）；调用点 `src/stores/workbench.ts:10061`
  - 手动加入 `src/stores/workbench.ts:9931` `toggleCombatAttacker`（只拦 `isCombat` / `attackCapable` / 进击阶段，不拦战略与未释放预备）
  - 引擎拒绝 `src/engine/rules/battle.ts:211-213`
- **触发条件**：攻击格内有战略模式或未释放预备模式的战斗单位。
- **严重度**：**需绕路**（理解成本高；原因码直接暴露内部字符串）。

### C6【隐患 / 只是提示不清】9.12d 跟随限制在引擎侧恒通过

- **现象**：`toBattleUnitView` 不输出 `isCombat` / `noncombatKind`，而 `canJoinRetreat` 对缺失字段按「可跟随」处理 ⇒ 引擎的 9.12d 校验对任何跟随者都放行。界面路径由 `combatTagalongCandidates` 正确过滤，所以正常操作不会出错。
- **代码位置**：`src/stores/workbench-model.ts:1234` `toBattleUnitView`（无 `isCombat` / `noncombatKind`）；`src/engine/rules/battle.ts:133` `canJoinRetreat`；调用点 `src/stores/workbench.ts:11084`
- **触发条件**：非界面调用方（AI/测试/未来脚本）直接传非战斗单位参与撤退。
- **严重度**：**只是提示不清**（当前 UI 路径正确，属健壮性缺口）。

### C7【规则偏差】9.12e 额外损失的承受者没有选择入口

- **现象**：撤退堆叠进敌 ZOC 且原已 DG 时，额外 1 点损失由代码取 `eligibleUnitIds[0]` 承受，玩家无法选择。
- **代码位置**：`src/stores/workbench.ts:11127-11142`（`combatInputs.extraLossTakerId` 只被读取，全仓库无写入点）；`src/stores/engagement-inputs.ts:44, 68`
- **触发条件**：9.12e 触发时该堆叠有 ≥2 个 DG 候选。
- **严重度**：**只是提示不清**（不阻断流程，但与 9.12e「由拥有者选择」不符）。

### C8【需绕路】战斗中不能存档，也不能「读档续战」

- **现象**：补给一旦确认（`combatIsCommitted`），`settlementBlockedReason()` 返回「请先完成当前战斗、移动、付款或其他结算，再保存或读取对局」；`src/engine/save-file.ts` 也不含任何 combat 字段 ⇒ 结算到一半退出＝该场战斗无法恢复（只能靠日志复盘）。
- **代码位置**：`src/stores/workbench.ts:24611`；`src/engine/rules/engagement-progress.ts` `combatIsCommitted`；`src/engine/save-file.ts`（无 combat 序列化）
- **触发条件**：任何战斗非 `finished` 状态。
- **严重度**：**需绕路**（设计取舍；与 `docs/archive/2026-11-01-战斗与轰炸流程重构.md:61` 的既定口径一致）。

### C9【只是提示不清】战斗结束后状态不自动清除，会话步回落到「发起战斗」

- **现象**：`finished === true` 后 `combatState` 仍非空；面板只显示「战斗结束」+ 按钮，但会话步投影已回到 `combat:declare`（`combatLiveStep` 为 null）。若不点「清理并关闭」，下一场战斗要靠「开始战斗 / 清除选择」重新覆盖状态。
- **代码位置**：`src/stores/map-view.ts:2622-2722`（`sessionFacts` → `planSessionSteps` → `sessionStep`）；`src/components/combat/CombatPanel.vue:762-765, 836-843`
- **严重度**：**只是提示不清**（有出口，不会卡死）。
