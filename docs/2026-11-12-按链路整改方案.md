### 2.3 数据或原文缺口

- **2-②【原文】**：战机扫荡（14.6）是否还有独立结算。当前只做「格内有敌机则空战，否则写 `missionNote`」，`assignAirMission` 允许该类型但没有额外判据。验证方式：查 14.6 全文。

- **2-④**：空运投送到己方部队格是否另有未接线的入口（工具条 / 小窗）。验证方式：上机逐一点击已知按钮。

### 2.4 独立提交的边界

- 第 1 批：**2-4**（静默错目标）。影响结算落点，必须最先单独提交并回归；否则后续所有验收的盘面都不可信。
- 第 2 批：**2-1 + 2-2**（入口判据与基地入口）。都在 `map-view.ts` 的入口层，可一条。
- 第 3 批：**2-6 + 2-8 + 2-9**（自动连跑中断后的出口）。同一模式：中断后必须停在带「重试 / 继续 / 落点」的步上。其中 2-9 依赖 1-1，必须与炮击第 1 批同批或紧随其后。
- 第 4 批：**2-3 + 2-7**（流程语义：改类型不再自动跑、拦截可达）。会改变操作顺序与自动连跑行为，单独提交并跑既有空军用例。
- 第 5 批：**2-5 + 2-10 + 2-11 + 2-12 + 2-13**（提示与按钮语义）。纯界面，可合一条。
- 断点：`done` 之后（2-10）与取消语义（2-11）最好同批，否则「完成后残留 + 取消名不副实」会互相放大误解。

## 6. 附：跨链路共性机制（不在各章重复，统一在此定口径）

各章只写了本链路的表现；下面六条是同一根因在多条链路重复出现，应一次性定机制、再分链路验收。

### A1. `ops` 外壳不得替代会话 facts（炮击 1-1 / 空军 2-9）

「右键目标 → 选单位 → 结算」的炮击与空军轰炸/扫射两条链路共用 `OpsFlowPanel` 外壳，但会话投影只认 `kind === 'barrage' / 'air'`，`ops` 落进 `default` 空表 ⇒ 宿主把所有 `SessionStep` 隐掉。**机制**：会话外壳只能决定标题与取消语义，当前待决项必须由被包裹的引擎状态（`barrageState.step` / `airState.step`）投影。**落点**：`map-view.ts#sessionFacts` 或 `session-steps.ts#planSessionSteps` 增一条转发，不新增状态源。

### A2. 候选必须与落点算法同源（炮击 1-2 / 1-3、空军 2-2、突袭 3-2、战斗 4-1）

四条链路都出现过「界面能选 / 引擎必拒」或「界面看不见 / 名单里还在」。**机制**：每条链路只保留一个候选函数（`barrageCandidatesAt` / `bombingCandidatesAt` / `overrunTargets` / `attackersForHex`），入口、面板、宣布前校验三处都调它；任何「额外过滤」只能加在候选函数内部。**判据**：同一格 / 同一单位在候选与引擎校验里的结论必须一致，否则视为缺陷。

### A3. 引擎 `reason` 不得直出到界面（炮击 1-7 / 空军 2-12 / 战斗 4-1 的原因码）

现在三处都把 `barrageSupplyNeedsADump`、`unitAlreadyBarraged`、`stratCannotAttack:<id>` 原样显示。**机制**：建一张 `reason → 中文句（含规则条号）` 的映射表，store 产出 `{ rule, code, message }`，UI 只显示 `message`；日志保留 `code` 供复现。映射表放在 store 层而不是组件层，三条链路共用。

### A4. 「取消」按钮名必须等于实际动作（炮击付款后 / 空军 2-10 / 2-11 / 突袭 3-5 / 战斗 4-9）

同类问题反复出现：付款后不可取消却仍给一个会静默失败的按钮；ops 的「取消本次」其实只关面板；战斗中的 `×` 置灰而面板底部的「放弃」仍可点（只写日志）。**机制**：每个会话只暴露一个 `closePolicy`（`close` / `refused` / `collapse`），按钮文案与 `closePolicy` 一一对应；`refused` 时必须显示原因；不允许「看似可点、点了只写日志」的按钮。

### A5. 自动连跑中断后必须停在一个带出口的步（空军 2-6 / 2-8）

`autoResolveAirMissionNow` 「逢 false 即停」，但停下后正式界面没有重试入口，只能刷新或取消。**机制**：自动连跑只负责「无需玩家表态的连续结算」；一旦需要输入或失败，必须把控制权交回一个渲染中的 `SessionStep`，该步至少有一个「重试 / 继续 / 完成分配」按钮。空军 ② 空战与 ⑤ 货物结算都按这条补。

### A6. 交互进行态与存档闸门（战斗 4-9 / 突袭 3-8）

`settlementBlockedReason` 已覆盖 `combatState` / `barrageState` / `airState` / `moveInteraction` 未完成的情况，因此「补给已扣、状态不在档里」的窗口应被闸门挡住。**机制**：任何新增的「已提交但未收束」状态都必须同时进 `settlementBlockedReason`；不能只靠「快照字段不收集交互态」来保证一致性。3-8 先核对是否已覆盖，再决定是否补拦截。

### 跨批次的先后约束（三句）

1. **炮击 1-1 / 空军 2-9 必须先于** 炮击 1-3、1-4 与空军 2-8、2-10 的验收——后者只有能走到第 2 步才可复现。
2. **空军 2-4 必须先于** 空军其余条目的上机验收——它会静默改变结算落点，污染盘面。
3. **战斗 4-4 必须先于** 战斗其余条目——它是唯一硬卡死，会掩盖后续步骤的可达性。
