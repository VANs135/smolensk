## 0. 结论摘要

### A. 1.6b 随机增援的铁路运输

1. 引擎层**已经具备**「入场格登车」的能力：`validateRailMovement` 在 `facts.isEntryHex(from, side)` 为真时按 13.6b 的「地图外登车」跳过 13.3e-1 的登车格检查（`src/engine/rules/rail.ts:337`），上一批 `ee2addf` 已接线。
2. **缺的是入口与流程**：增援投放只有「点单位 → 引擎给卡面候选格 → 点格直接落地」这一条路（`beginArrivalPlacePickNow` → `placeArrivalNow`），没有任何「铁路运输」分支；1.6c 特殊补员返场、2.3c 编制转化新单位也同样没有。引擎能力没有被消费。
3. **运力侧已完整**：`railCapSpentThisTurn` / `railCapUsedBy` / `spendRailCapacity` / `railCapRemaining` 都在 `workbench.ts`，成本公式 `railCapacityCost` 在 `rail.ts`；目前只有两个消费者——移动阶段铁路运货（`railMoveNow`）与 1.4b 边缘盒进出（`containers.ts#moveEdgeBox`）。
4. **落点合法性**按 13.3c + 13.3e-2 + 13.3e-3 + 13.3f：终点必须是**可火车卸货格**、不在敌方 ZOC、沿本方轨距的连通铁路、沿途无敌方单位/ZOC；入场格本身只是「含铁路」即可（13.6b），不受 13.3c 与 EZOC 限制。
5. **按钮形态可行**：现有 `beginHexPick` 机制就是「高亮候选 → 点格生效」，3.6 补给列车落 SP 就是同型先例（`beginSupplyTrainHexPickNow` / `placeSupplyTrainSpNow`）。按「不可用项不出现」，按钮只在该条目的**解算入场格含铁路**时显示。
6. **冲突已由裁定 1 收口**：既有数据里 `K=1.26`、`I=1.12` 不是铁路格，13.6b 的条件是「arrival hex contains a railroad」；上一轮 5-D3 按字母放开的做法**收窄**为「是入场格且该格含铁路」。轴方实际只有 J/H/F/G 四处合格。见 §A.3、§A.8。

### B. 1.6b 的补给只能空运

1. 原文依据充分：1.6b Notes 明写「'Extra' SP cannot be shipped onto the map with Rail Cap, but can be brought in with Air Transport」；1.4a 明写图外空军盒「there is 'extra' SP available that can be flown onto the map via Air Transport missions」。
2. **空运侧已经能带 SP**：14.9c 允许 SP 空运；代码 `planAirSupplyLoad` 已支持「图外空军盒库存」作为装货来源（`workbench.ts:16894`），并在宣布任务时扣账（`:16959`）、任务取消/退运时回盒（`:2049`）。
3. **图外空军盒的数据结构**：`airBoxMembers` 只存**飞机实例 id**（`workbench.ts:1560`），`airBoxView().holdings` 也只投影飞机（`src/engine/rules/containers.ts:1501`），`markers.json → containers.airBoxes` 只有盒元数据。**但**另有一本独立的 `offMapSupplyStocks: Record<string, SpHoldings>`（`workbench.ts:1930`，已入存档 v6）就是盒内 SP 库存——即「标记/库存」在账本层已存在，只是没有视图、没有入库入口、没有初设数据。
4. **裁定 2**：不需要「新建一套空运机制」。空运任务带 SP 的链路是通的；按路线 1 复用 `offMapSupplyStocks`，只补**入库入口、提示、显示与初设**，不新造第二套账。见 §B.4、§B.5。

1.6b 补员表本身给的是 **Repls（Pax/Eq）**（`src/engine/rules/variable-repl.ts`），不是算子；能「入场」的是 1.6c 的返场单位与 2.3c 的新单位，其落点是 2.1 的「能直接拖取的 HQ，否则图边补给源格」。这些 HQ/源格中**很多就是铁路格**（例如 `43.01`、`1.26` 等），所以用户描述的「从有铁路的格子入场」在这个投放面同样成立。

### 缺口（与 A.3 同源，另加两条）

1. 两个投放面都没有「铁路运输」动作。
2. 候选是 `hqOrEdgeSource` 的**落点**，不是「从该落点再铁运出去的终点集」；需要新增一层候选投影。
3. 运力已用/剩余在增援阶段是可读的（`railCapRemaining`），但没有任何 UI 显示「本笔铁运会花几点」。
4. `withdrawArrivalNow`（`:22774`）能撤回已投放条目；若铁路运输已扣运力，撤回必须**退回运力**，否则同一回合额度被永久吃掉【口径/实现细节】。

## A.5 落点合法性：火车运输的可放置格与「入场格」的关系

### A.5.1 可放置格（13.3c / 13.3e / 13.3f）

一个格能作为**卸货终点**，必须同时满足：

1. **是铁路格**（13.3e-3 首句「可火车卸货的铁路格」；`RailFacts.hasRail(to)`）。
2. **是 13.3c 可火车卸货格**：村庄/城市（任意规模）/港口/有工程能力的指挥部；该格已被控制；该格有铁路路径可延伸至补给源且路径无敌方 ZOC。
3. **不在敌方 ZOC**（13.3e-3）。
4. **无敌方战斗单位、无敌方单位占据**（13.3e-3 + 13.3e-2 的「未控制」口径）。
5. **轨距为本方可用**（13.3f）。
6. 路径满足 13.3e-2：逐格以铁路相接、全程本方轨距、沿途无敌方单位/ZOC。

代码落点：`validateRailMovement` 的 ④ 段（`rail.ts:386-396`）逐条判；`isDetrainable` 由 `railMoveFacts`（`workbench.ts:4056`）注入，结论唯一来自 `railSupply`。

### A.5.2 与「入场格」的关系

| 角色           | 判据                                                                                                            | 依据                |
| -------------- | --------------------------------------------------------------------------------------------------------------- | ------------------- |
| 入场格（起点） | 只需**含铁路**；不受 13.3c 的「可卸货」限制，也不判入场格的 EZOC（13.6b 明确「忽略 13.3e 中通常要求的'登车'」） | 13.6b；13.3e-1 末句 |
| 终点（卸货格） | 必须满足 A.5.1 全部六条                                                                                         | 13.3c / 13.3e-3     |
| 两者之间       | 13.3e-2 的路径条件                                                                                              | 13.3e-2             |

**表达方式建议**：不要把「入场格」塞进 `isDetrainable`；保持两个独立判据：

- `entryHasRail(hex)`：`map-layers` 静态铁路图（或运行期 `hasRail`）；
- `isDetrainable(hex, side)`：13.3c 结论（已有）。

候选集＝「满足 A.5.1 的格 ∩ 从入场格沿铁路可达（13.3e-2）∩ 成本 ≤ 剩余运力（13.3b）」。

**边界情况**：若入场格本身也是可卸货格，「铁路运输到原地」是无意义动作。建议**把入场格从候选集中排除**，玩家若要原地落子就走普通投放路径【口径】。

### A.5.3 成本与额度

- 成本按 `railCapacityCost`（13.3a）：单位当量（RE，短腿减半）× 破坏区/多轨修正。
- 额度按 `railCapRemaining`（13.3b），不足即拒，且**不得部分扣点**（对齐 `railMoveNow` 的「超额度不改动任何货物」，`:4538-4550`）。

## A.6 按钮形态可行性

### 现有流程（可套用）

```
点手牌单位（pickArrival）
  → store.beginArrivalPlacePickNow(index)
    → arrivalCandidates[index]（引擎按卡面口径）
    → beginHexPick({ label, rule, candidates, apply })
      → 地图高亮候选
        → 点格 → apply(hex) → placeArrivalNow(index, recordId, hex)
          → 校验（敌占 / 候选范围）→ 建算子 → markArrivalPlaced
```

同型先例：3.6 补给列车 `beginSupplyTrainHexPickNow`（`workbench.ts:19850`）→ `beginHexPick`（候选＝`supplyTrainPlacementHexes`）→ 点格 `placeSupplyTrainSpNow`（`:19798`）。用户说的「和补给列车事件时放 SP 差不多」在代码层面就是这一条链。

### 裁定 3：铁路运输的通用流程（增援按钮复用它）

裁定 3 把流程钉成五步，增援放置不得另写一套：

```
① 合法位置点「铁路运输」
   （位置合法＝该条目解算入场格含铁路；无合法入场格时按钮不出现）
② 有运力 → 高亮可达目的地
   （候选＝13.3c 可卸货格 ∩ 13.3e-2 可达 ∩ 成本 ≤ 剩余运力；无运力则不高亮并报「运力不足」）
③ 点目的地 → 到达（先在界面上"待确认"，不立即扣点）
④ 弹「确认／撤回」小窗
   · 确认：validateRailMovement → 扣运力 → 落子 → 记账
   · 撤回：清掉待确认落点，运力不变
⑤ 落子后仍可从手牌撤回（withdrawArrivalNow），撤回时退回该笔运力
```

与 3.6 的唯一差别：3.6 落的是 2 SP 且**不扣运力**；本流程落的是一枚算子且**扣运力**，所以第 ④ 步的确认窗必须显示「本次耗 X 点、本回合余 Y 点」。这是裁定 3 对既有 `beginHexPick`（点格即生效）的唯一扩展点：需要一个「待确认」中间态。

### 套入方式

1. 在`ArrivalHandCard`（`ReinforcementPanel.vue:219`）增加一个**并列按钮**「铁路运输」，与「放置」互斥进入两种选格态。
2. 按钮**显示条件**：该条目的解算入场格 `hex` 非空且 `isRailHexAt(hex)`（13.6b）。`noCandidates` 时本来就没有入场格，按钮不显示。满足「不可用项不出现」。
3. 点击后进入第二种选格态：
   - `label: '增援铁路运输落点'`，`rule: '13.6b / 13.3e'`；
   - `candidates`＝A.5.1 的终点集；
   - `apply(hex)` 走新的 `placeArrivalByRailNow(index, hex)`（建议名），而不是 `placeArrivalNow`。
4. 非铁路入场（`K=1.26`、`I=1.12`、`C=62.12` 等）时按钮**不渲染**，不显示灰项。

### 可行性结论

**可行**，且不需要改 `beginHexPick`。真正要新写的是三样：

- 一个「入场格是否含铁路」的投影；
- 一个「从入场格出发的铁路终点候选」投影；
- 一个「校验 → 扣运力 → 在终点建算子 → 记账」的动作。

### A.7.2 关键实现难点（必须在动手前定）

1. **`railPathBetween` 的入场格放行会污染候选集**
   现有 `railPathBetween`（`workbench.ts:4095`）在起点是入场格时**刻意不按轨距/敌情滤格**（`:4104 entryStart`），目的是让引擎给真实拒绝原因。若直接拿它生成「高亮候选」，会把走不通的格也点亮。
   ⇒ 需要一条**过滤版**搜索（或参数 `filterFromEntry = true`）专供候选投影；真正的裁定仍交 `validateRailMovement`。这是本功能最容易踩的坑。

2. **阶段闸门**
   `validateRailMovement` 第一句拒非 `movement`（`rail.ts:327`）。建议加显式入参（如 `arrivalRail: true`）放行，并在注释里引 13.6b + 13.3e-1 末句；**不要**在调用点伪造 `phase: 'movement'`，否则反应/进击阶段的误用无法区分。需用户确认这是 13.6b 对 13.3b 的例外【口径】。

3. **单位模式**
   13.3e-1/5.6a 要求移动模式，13.6b 允许任意主动模式入场。建议：铁运落地时把新算子置为**移动模式**（铁路运输的语义），这不改变「入场模式自由」——玩家仍可选择普通投放保留任意模式。需确认【口径】。

4. **没有实例 id 时的 cargo**
   `validateRailMovement` 的 `cargo.id` 只用于 `isRailRepairUnit` 与日志。到达条目此时尚未建算子，建议用到达记录/需求组装 `re`、`mobility`、`moveMa`、`currentMa`、`preLoadMp=0`，并传一个稳定的合成 id（如 `arr:<index>`）；若该型是铁路修理单位，按真实规则仍需识别——【口径】。

5. **编成条目**
   一条到达卡可能是「多枚算子共同到场」（`formationComponents`）。铁运按钮对整条编成是「整条一起运」还是「逐枚运」原文未写【口径】。建议第一版只对**单算子条目**显示按钮，编成条目沿用普通投放，避免一次性多枚共用一个当量。

6. **撤回退点**
   `withdrawArrivalNow` 必须把该笔 `spendRailCapacity` 退回；否则撤回后本回合额度永久减少。建议在到达账本里记 `{index → railCost}`，撤回时扣回。

7. **1.6b 的 SP 不走这条按钮**
   1.6b Notes 明写额外 SP 不能上铁路；本按钮只对**单位条目**显示。SP 条目（`demand.kind === 'sp'`）本来就不在手牌（`ReinforcementPanel` 过滤掉），无需额外处理。

| `AirBoxSchema`                       | `src/data/schema/markers.schema.ts`       | 盒元数据                                          | 否                 |
| `offMapSupplyStocks`                 | `workbench.ts:1930`                       | `Record<string, SpHoldings>`，键 `${side}:${box}` | **是（独立账本）** |
| 存档                                 | `workbench.ts:26145`、`:26326`（v6 字段） | 已持久化                                          | 是                 |

**结论**：盒的**视图/成员表**只认飞机；但盒的 **SP 库存**已经有一本独立账本 `offMapSupplyStocks`，且已被空运装载与退运使用。也就是说，「图外空军盒放 SP」在数据层不是从零开始，缺的只是：

1. **入库入口**：除了「任务退运」以外，没有任何代码写入这本账本；
2. **显示**：`airBoxView` 的 `holdings` 不投影 SP，面板看不到盒里有多少 SP；
3. **初设/事件数据**：`offMapSupplyStocks` 初值为 `{}`，没有剧本初设，也没有 1.6b 掷骰后的入库动作；
4. **命名不一致（小坑）**：账本键的 `box` 实际写的是 `axis`/`soviet`（`workbench.ts:16881`），不是 `axis-air-box`/`soviet-air-box`（`airBoxView` 的 `id`）。日后加面板/迁移存档要留意。

## B.5 裁定与理由

**裁定 2 采用路线 1。** 理由：

1. **运输侧已经完成**：`offMapSources`（`workbench.ts:16894`）→ `planAirSupplyLoad`（`air-supply.ts:53`）→ 扣账（`:16959`）→ 退运回盒（`:2049`）是闭环；缺的只是「SP 怎么进盒」。
2. **1.4a 的语义是库存**，不是无限修饰符；`offMapSupplyStocks` 正是库存账本，复用它不需要解释原文。
3. **1.6b 明令禁止铁运**，所以本功能与 A 章的运力完全解耦，不会互相污染。
4. **改动面最小**：一个入库动作 + 一个入口 + 一个显示；不碰 `validateRailMovement`、不碰 `planAirSupplyLoad`。
5. **可回滚/可审计**：入库、装载、退运各有 settlement 记录，符合本仓既有记账习惯。
