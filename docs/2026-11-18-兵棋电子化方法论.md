# 兵棋电子化方法论：从原始素材到可玩成品

> 来源：2026-11-18 由 OCS《斯摩棱斯克》电子化项目（`D:\OCS\smolensk`）全流程蒸馏。
> 同内容技能：`wargame-electronization`（安装于 `c:\Users\KD\.trae-cn\skills\wargame-electronization`）。
> 读法：第 1–13 节是方法本体，逐阶段给输入、产出、判据、坑与验收；附录 A 是文件级落点，附录 B 是案例与踩坑，附录 C 是单批交付清单。
> 与既有兵棋技能的分工见 §10——本文件不重写专项细节，只定全链顺序、阶段交接物与验收判据。

一句话总纲：**把规则书拆成三样可执行的东西——静态数据、时序状态机、玩家可见的投影；其余一切（留痕、闸门、批次、打包）都是保证这三样不漂的手段。**

全链八阶段，顺序不可跳：

```
1 原始素材 → 2 数据库分层 → 3 规则库与引擎常量 → 4 阶段/环节与窗口
→ 5 store 编排与撤销记账 → 6 界面交互与信息呈现 → 7 AI 覆盖与自对弈 → 8 六门槛与打包
```

**一次只推进一个阶段。** 每阶段有明确的输入、产出、判断依据与验收方式；没通过本节末尾的交接门，不进下一阶段。跳阶段的代价不是返工一次，而是后面所有阶段的结论都建立在错误前提上（最典型：网格标定错 → 数据"看起来有噪声" → 逐格修改 → 全错）。

## 0 三条总线

整条链上所有具体判断，都归到这三条：

| 总线          | 内容                                                               | 违反的后果                                 |
| ------------- | ------------------------------------------------------------------ | ------------------------------------------ |
| 原文 > 一切   | 规则书条款 > 专规/剧本 > 卡面图表 > 现有实现 > 口述记忆            | 用实现去"补圆"原文，规则错得自洽且查不出来 |
| 原件 > 转录物 | 算子图/地图扫描 > 表 > 剧本文字 > 工具输出                         | OCR 的错读被当成设计，成片数据错           |
| 静态 ≠ 运行期 | 库只放"这东西是什么"；位置、堆叠、损失、模式、剩余补给一律在运行态 | 存档、回放、撤销全部失准                   |

判定冲突时按上表自上而下取第一个能判的；判不了的写进待裁定，**不要用低优先级去圆高优先级**。

## 1 原始素材：把"看得见读不出"变成"机器能读、人能复核"

| 项           | 内容                                                                                                                                                                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **输入**     | 扫描地图（可能多幅拼接）、算子图/算子表、规则书 PDF、剧本页、勘误、辅助卡与图表页                                                                                                                                                                                     |
| **产出**     | 素材清单（原件/派生件/正反不成对/缺页）；标定后的网格配置；切好的算子图档；规则全文（带页/行号）；图表 JSON；每类素材的同步脚本与目检图                                                                                                                               |
| **判断依据** | 三类素材三套管线：**可直接读**（规则、剧本）→ 提取+通读+结构化；**需识别**（算子印值）→ 分阵营/批次管线+群体一致性；**需标定**（地图）→ 几何先行+接缝校验+逐格逐边                                                                                                    |
| **落地锚点** | `public/map/`、`public/counters/{axis,soviet,markers}/`、`src/data/map-config.json`、`src/data/map-layers.json`、`scripts/sync-map-layers.mjs`、`scripts/sync-counters.mjs`、`scripts/sync-charts.mjs`、`scripts/sync-aux-cards.mjs`、`tests/data/*-verbatim.test.ts` |
| **验收**     | ① 叠加图目检无系统性偏移（完整格中位 ≤0.5px，P95 <1px）；② 浏览器实测绘制的网格与 Python 叠加图一致；③ 每张图表都有逐字用例；④ 图档数 = 库内引用数，无孤儿、无缺图；⑤ 同步脚本可重跑且幂等                                                                            |

关键判据：

1. **网格几何先定死再判读。** 平顶/尖顶、奇偶列错位方向、每格像素尺寸、每幅独立 `dx`、印刷行号与程序行号的 `rowDecode` 换算。标定错的表现是"数据有噪声"，不是"标定错"，极难返工。
2. **一图只检查一类要素。** 地形、河流、道路、铁路各自出图；图例放图外，别盖住待检查的格。
3. **边缘终止不是断头。** 通到图边的线要素本质是"自图外进入"，在库里简化为"源"，判据写进方案。
4. **正反不成对的图档不自动建实体**，逐项裁定为弃用/备用面/轮换面并登记。
5. **目录类条目从目录取，不做识别。**
6. **每类素材配一个同步脚本 + 一个契约用例。** 素材更新只跑脚本，不手改派生件；脚本本身要有用例（改前快照能否报错）。

**常见坑**：把全局平均用于逐格地形（一格多地形被抹平）；面板白线当对齐目标；只画 `col/row ≥ 0` 导致上半区缺格；叠加图脚本手抄参数与浏览器不同步；印刷行号直接当引擎行号用（编号镜像）。

> 工具级细节见 `wargame-processor`、`hexgrid-calib`、`map-terrain-identify`、各 counter 识别技能。本阶段只要求：**素材清单、同步脚本、逐字用例、目检回路四件齐备**。

## 2 数据库分层与留痕回滚

| 项           | 内容                                                                                                                                                                                                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **输入**     | 阶段 1 的识别结果、图表 JSON、规则文本、剧本页                                                                                                                                                                                         |
| **产出**     | `src/data/*.json` + `*.schema.ts`（Zod）+ 唯一加载入口 + `DATA_VERSION`；数据字典；留痕字段与留底目录                                                                                                                                  |
| **判断依据** | 三层模型（实体 → 面 → 印值）；分层声明谁权威谁派生；字段名以实施为准；计数三方一致；双向核对；蕴含关系断言                                                                                                                             |
| **落地锚点** | `src/data/index.ts`（校验→冻结→版本号）、`src/data/version.ts`、`tests/data/schema-strict.test.ts`、`tests/data/units.test.ts`、`tests/data/map-hexes-contract.test.ts`、`tests/data/map-edges-contract.test.ts`、`scripts/sync-*.mjs` |
| **验收**     | ① 全库 schema 严格校验通过（多余字段即报）；② 计数三方一致且由工具重算；③ 契约用例覆盖取值域与蕴含关系；④ 任一记录能从值反查到依据（条款号/图档/批次）；⑤ 用改前快照跑一遍闸门，确认它真能报错                                         |

关键判据：

1. **面语义按类别确认，不假定"双面 = 两个数值"。** 战斗单位正/反可能是战斗模式面/移动模式面；炮兵两面都印轰炸值与射程；补员可能只有移动面。
2. **静态库不含运行期状态。** 把禁止字段列成清单，逐条断言 0 命中，不靠人工记忆。
3. **"设计上不填" ≠ "尚未填"。** 前者显式标不适用 + 依据，不算缺口；后者进开放项。混淆会造出成片假缺口或漏数据。
4. **留痕写在记录内、留底是整文件复制、回滚靠覆盖**，不写反向脚本。批量替换必须跳过留痕字段。
5. **权威源唯一。** 同一事实只允许一个 JSON 是权威（如 `map-layers.json`），图档与前端产物都是派生件；派生件不手改。
6. **改结构必须先改声明再搬数据最后重算计数**（一批一层，批内验收）。

**常见坑**：手写计数；三个登记位只写两个；只做单向字段核对；把描述式文本当正则；不同类别条目混比；剧本值覆盖印值；改名不传播到引用。

> 建库与符合性核对细节见 `wargame-db-pipeline`、`ocs-db-build`；扩剧本/扩单位见 `wargame-db`。本阶段只要求：**schema + 版本号 + 两道闸门 + 计数工具**这套骨架先立起来。

## 3 规则库与引擎常量：让每条结算都说得出依据

| 项           | 内容                                                                                                                                                                                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **输入**     | 规则全文（带页/行号）、专规、图表、阶段 2 的数据字典                                                                                                                                                                                                                                           |
| **产出**     | `src/data/rules-constants.json`、`charts-*.json`、`src/engine/tables/*.ts`、`src/engine/rules/*.ts`、统一结果契约、术语对照表                                                                                                                                                                  |
| **判断依据** | 剧本 > 专属 > 通用（覆盖式增量，不混写）；数值只有一个来源；规则编号落字符串；能一次结清的与留待后续的分开表达                                                                                                                                                                                 |
| **落地锚点** | `src/engine/result-types.ts`（`RuleOutcome`：`{ok, rule, data, pending}` / `{ok:false, rule, reason}`）、`src/engine/derivation.ts`（复核链）、`src/engine/tables/`、`src/engine/rules/`、`tests/data/rules-constants.test.ts`、`tests/engine/rules-per-clause.test.ts`、`CODE_SPEC.md` 术语表 |
| **验收**     | ① 任一结算返回都带条款号；② 测试名含条款号，可反查规则书；③ 组件里搜不到规则数字字面量（架构扫描会抓）；④ 查表数值有逐字用例；⑤ `pending` 覆盖所有"结算完还没完"的情况                                                                                                                         |

关键判据：

1. **统一结果形状是引擎的地基。** 所有规则函数共用同一把尺子：成功了带 `data` + `pending`，失败了带机器可读 `reason`。调用方不需要猜"还有哪些事没做"——`pending` 就是答案。
2. **`pending` 只放规则上不能一次结清的东西**：需要玩家二选一（撤退/损失）、留待后续阶段施加的标记（DG、进击）、战后推进。不要把强制后果塞进 `pending`（那会变成玩家可以忽略的选项）。
3. **复核链（derivation）与结论同源。** 掷骰、修正项及来源、合计、查表、结果，按同一条链生成，界面只渲染不重算。日志面板能展开的"为什么"和引擎算的是同一份数据。
4. **术语一张表定死，代码标识符照表。** 中文规则书说法与图表页不一致时以正文为准，图表说法登记别名。禁止同义造词（典型：把 Hip Shoot 另造一个 `strafing`）。
5. **规则性空白当 N/A 处理**（如铁路炮兵无 MA、运输单位无 A/AR），写进"不适用清单"，不补值。
6. **专属规则做覆盖块，镜像被覆盖路径**，便于"同路径覆盖"合并与溯源；禁止把专属值混进通用段。

**常见坑**：规则书 OCR 直接照抄；专属/通用不分；把"数据里有字段"当"规则要求"；界面与引擎各算一遍判据；改了主字段忘派生字段。

> 规则提取与常量提炼细节见 `ocs-rules-db`。本阶段的交付线是**契约**：结果形状、条款号、复核链、术语表。

## 4 阶段 / 环节与操作窗口：先把"什么时候能做什么"钉死

| 项           | 内容                                                                                                                                                                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **输入**     | SOP/流程表（如 OCS 2.2）、专规、卡面、阶段 3 的动作清单                                                                                                                                                                                                               |
| **产出**     | 阶段-环节-操作矩阵（人读）+ 环节链定义（机读）+ 动作族闸门表 + 窗口设计文档                                                                                                                                                                                           |
| **判断依据** | 段/节/环/块四层粒度；每个环节必须标渲染宿主；自动步三归宿；一窗一事；落点类型（地图格/图外盒）                                                                                                                                                                        |
| **落地锚点** | `src/engine/rules/sop-segments.ts`（环节链与 `driver`/`actions`）、`src/stores/workbench-model.ts#ACTION_GATES`（动作族 → 阶段/环节/条款）、`actionKeysOfSegment()`（唯一派生源）、`src/stores/action-families.ts`（动作族 × 入口盘点）、`docs/阶段-环节-操作矩阵.md` |
| **验收**     | ① 每个环节在代码里有 id、在文档里有同名行、在界面上有渲染宿主；② 自动步不占环位；③ 每个动作族只有一处闸门定义；④ 组件不自拼阶段名；⑤ 走一遍"初设→回合末"不需要点空转按钮                                                                                              |

关键判据：

1. **按玩家停留建环，不按数据结构建节。** 判据只有一句：玩家在这里有没有决定，或必须看见并确认的结果。都没有 → 自动步。
2. **标不出渲染宿主的节就是空壳。** 先标宿主再写节；空壳的修法是降为自动步或并入相邻环，不是补一个"下一步"按钮。
3. **计数先定口径再报数。** 段/节/环/块同词多义是经典翻车点（一方说 8、一方说 7、玩家看到 5）。文档开头先给口径表，且所有数字由代码枚举生成，不手写。
4. **环节 id 是设计与代码之间的唯一合同。** 设计文档写 `movement.modeAndMovement`，代码里就必须是同一个字符串；改一侧必须同步另一侧。
5. **闸门（`ACTION_GATES`）是"能不能做"的唯一来源**，菜单、面板、会话窗、AI 全从它取值；删入口前先查"该能力是否只剩这一个入口"。
6. **落点类型是必填字段。** 地图格走"引擎算候选 → 高亮 → 点格即落"；图外盒走"点条目即移入"，**盒不是格，不做候选集、不高亮**。

**常见坑**：一屏铺 8 件待办；前一步完成自动关窗吞掉后续块；轴方窗里冒出苏方专规；同一动作两个菜单名；把卡面数据缺失当可实现。

> 窗口与环节设计方法见 `wargame-phase-window-design`；算子身上的入口分工见 `wargame-counter-interaction`。本阶段新增的只有一条：**设计文档的环节 id 必须与 `sop-segments.ts` 同字符串，闸门只允许一处**。

## 5 store 编排与撤销记账

这是既有技能覆盖最薄、也最容易做错的一段。**规则算对 ≠ 流程走对**：错都错在"谁拥有状态、一步改了哪些账、什么时候不能再撤"。

### 5.1 状态所有权

| 层                    | 拥有                                            | 不得                                     |
| --------------------- | ----------------------------------------------- | ---------------------------------------- |
| `engine/`             | 纯判定 + 交互状态机（`rules/*-interaction.ts`） | 引 Vue/Pinia/DOM、读时钟、碰存储、持盘面 |
| `data/`               | 静态事实 + schema + 版本号                      | 业务逻辑、格式化                         |
| `stores/session`      | 流程：段/回合/待答/终止                         | 承载算子动作                             |
| `stores/setup`        | 初设：落位栈、抽取、强制效果                    | 管回合内移动                             |
| `stores/workbench`    | 盘面：单位、补给站、标记、各类账本、当前交互态  | 自己实现规则判据                         |
| `stores/containers`   | 运输容器与装卸账                                | 管别的事                                 |
| `stores/ui` / `theme` | 界面状态、主题                                  | 参与规则                                 |
| `render/`             | Canvas 绘制、坐标换算、命中检测                 | 写状态、判规则                           |
| `components/`         | 只读投影 + 调提交入口                           | 自算合法性、自拼规则号                   |

一句话：**引擎不持盘面，store 不判规则，组件不算合法性，render 不写状态。**

### 5.2 一次动作的五拍

```
候选（投影）→ 开始（建交互态）→ 逐步提交（每步记 before/patches/费用/条款）
→ 结束（提交并封存）→ 回执（日志 + 结算记录）
```

| 拍   | 要求                                                                                             | 反例                                       |
| ---- | ------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| 候选 | 只来自 `ACTION_GATES` 与既有候选投影；没有候选投影的动作族如实标 `unsupported`，**不临时造候选** | 组件里 `if (phase === 'C')` 拼一份可做列表 |
| 开始 | 交互态是显式对象（移动、战斗、炮击、补给各一个状态机），不是散落的 ref                           | 用 6 个布尔量表示"正在移动"                |
| 逐步 | 每步带**改前快照 + 变更 + 费用 + 条款号**；失败即整笔拒绝，不做半截                              | 先扣 MP 再判目标格合法                     |
| 结束 | 结束 = 提交 = 封存；之后不再有任何撤销                                                           | 关窗后还能"撤销一步"回到盘中               |
| 回执 | `appendLog` 写会话日志 + `recordSettlement` 写日志手册；两者同源                                 | 界面弹一句、日志里没有                     |

### 5.3 撤销与记账三条线

| 线       | 范围           | 机制                                                                 | 边界                                       |
| -------- | -------------- | -------------------------------------------------------------------- | ------------------------------------------ |
| 步级撤销 | 本次交互内一步 | 用该步 `before` 快照还原，**并同步对销派生账**（ZOC 停车、MP、点数） | 遇到不可逆步即止                           |
| 整次放弃 | 本次交互全部   | 回到交互开始前                                                       | 同上；"无步可锚"的不可逆步（如入盒）同样挡 |
| 段间     | 已结束的交互   | 不可撤；换段/换方/换回合即封存                                       | 没有全局撤销栈                             |

**不可逆边界（硬判据）**：一步可撤销 ⇔ 它只改动了 `before` 快照能还原的运行态。一旦该步**落盘了快照之外的事实**——掷骰结算、突袭战斗、特战、入盒、生成新单位——就把边界推到该步之后，撤销入口**不再出现**（不是置灰）。

实现上把边界做成一个数（`rollbackFloor`）+ 一个原因串，按钮态与拒绝文案**读同一个判据**，避免"按钮亮着但一点就被拒"。

### 5.4 守卫与视角

- 每个提交入口第一行判 `mayMutate()`：非行动方、观察方、AI 非控制方一律只读。
- 视角方默认 = 玩家选择的阵营；切阵营自动更新，无需重开窗口。
- 投影里**不得携带对方内部字段**；发现协议层泄漏就登记上报，不在 UI 层"顺手遮一下"。
- 热坐换手、PVE 交棒都是**显式的段边界**，不要用"当前选中单位属于谁"隐式推。

### 5.5 确定性与存档

| 要求       | 做法                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| 掷骰可重放 | 禁 `Math.random`；随机只走 `engine/rng.ts`（纯函数：状态进、新状态 + 值出）；`seed + drawCount` 入档     |
| 版本分层   | 存档外壳版本 / 会话容器版本 / 会话数据模型版本 / 数据契约版本，四者独立、逐层校验                        |
| 盘面随档   | 引擎只认识会话（记录、日志、种子）；盘面快照由 store 序列化后作为不透明字段透传，引擎不解释内容          |
| 读档纪律   | 缺字段、版本不符、剧本对不上 ⇒ 报错并指出字段路径；**不静默迁移**，唯一例外写成显式迁移函数              |
| 日志可复算 | 固定种子重放日志里的每次掷骰，逐条比对骰面；分歧时报"第几条、什么动作、依据哪条、游标、日志值 vs 重放值" |

### 5.6 常见坑

| 坑               | 表现                           | 正解                                       |
| ---------------- | ------------------------------ | ------------------------------------------ |
| 撤销只还原主状态 | 单位回去了，ZOC 停车账/MP 没回 | 每步都记派生账，撤销一并对销               |
| 撤到上一环节     | 上一段的落位被撤回             | 撤销只登记本交互；结束即封存               |
| 点了没反应       | 入口可见但入口内判据拒绝       | 入口与拒绝共用同一判据，不可用就不生成入口 |
| 两处各算一遍     | 菜单说能做、会话说不能         | 闸门唯一来源，会话内只判"能不能落账"       |
| 半截提交         | 扣了费用但落位失败             | 先全量校验再整笔提交，失败不落任何账       |
| 结束仍可撤       | 关窗后状态漂移                 | `finished` 是硬闸；"结束=提交"写进测试名   |
| 存档只存会话     | 读档后记录轨与盘面矛盾         | 盘面快照随档，四层版本逐层校验             |
| 换手未封存       | 后手能撤前手                   | 换方/换段/换回合都是显式封存点             |

**验收**：① 每个交互状态机有单测（含边界：不可逆步、整次放弃、结束后再撤必须被拒）；② 固定种子整局回放一致；③ 存档往返（存→读→继续）状态一致；④ 每一拍都能在日志里找到对应记录。

## 6 界面交互与信息呈现

| 项           | 内容                                                                                                                                                                                                                                                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **输入**     | 阶段 4 的窗口设计、阶段 5 的投影                                                                                                                                                                                                                                                       |
| **产出**     | 组件、设计令牌、地图渲染与命中检测、操作反馈                                                                                                                                                                                                                                           |
| **判断依据** | 极简；窗内不放描述；条款进 `?`；不可用不出现；单入口；能点图不手输；状态用角标；观察方只读                                                                                                                                                                                             |
| **落地锚点** | `src/styles/tokens.css`（唯一色/尺度来源）、`src/styles/base.css`、`src/stores/theme.ts`、`components/base/{RuleTip,RuleNote,BaseDialog,BasePanel}.vue`、`components/map/MapCanvas.vue`、`components/game/{MapActionPopover,DecisionQueue,OverstackPanel}.vue`、`docs/数值修改指南.md` |
| **验收**     | ① 每个格画了什么、点空白做什么，有一张现状对照表；② 实点走查覆盖拖拽/悬停/双击/键盘；③ 观察方截图里没有任何可执行项；④ 触摸端长按/捏合/命中区与鼠标端行为一致                                                                                                                          |

关键判据：

1. **信息分四级，不越级**：格内（算子图 + 角标）→ 弹层（右键/堆叠窗，只放可执行项）→ 面板（会话，一窗一事）→ 侧栏（事务性动作，如整备、恢复储备、基地修建，不弹会话）。
2. **有算子图的地方不重复印名称与数值。** 全量信息进悬停，状态用角标/描边/贴图，不平铺成文字行。
3. **条款号只出现在 `?` 与悬停里**；主标签是动词（炮击、加油、重建），不是条款号或长句。
4. **不可用 = 不生成**，不是置灰。三种"不出现"要分清：整项不生成（条件不成立）、生成但空态一行原因（这一组本该有）、置灰（不应使用）。
5. **同一能力只留一个入口。** 自查方法：按执行函数反查调用点；同一函数出现在两个 UI 入口且各自算条件 → 必须合并。
6. **主题只换外壳，不换地图。** 默认浅色（暖纸底、墨色文字、压低纯黑纯白对比），深色保留为可切换并记住选择；令牌唯一来源，组件禁写十六进制；地图本身的地形/铁路/算子底色/高亮不随主题变。
7. **鼠标与触摸同一套代码、按 `pointer` 分派**：右键 ↔ 长按 500ms；滚轮 ↔ 双指捏合；命中区在 `pointer: coarse` 下放大。
8. **拒绝要可读**：一句话说清缺什么（缺 1 SP / 本阶段已动过），不铺规则解释；点了毫无反应一律算缺陷。

**常见坑**：堆叠窗里塞说明文字；图外盒被当格高亮；一排灰项；同一功能两个入口；菜单项随可用状态跳位；文字行代替角标；主题令牌混入地图配色。

> 左键/右键分工、菜单生成算法、十条硬规则见 `wargame-counter-interaction`。本阶段只补"呈现口径"与"实点验收"。

## 7 AI 覆盖与自对弈：用 AI 找 bug，不用 AI 刷分

| 项           | 内容                                                                                                                                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **输入**     | 动作族表、各动作族的提交入口、既有只读投影                                                                                                                                                                                                                   |
| **产出**     | 覆盖盘点表（动作族 × 提交入口 × AI 是否调用）；策略层（纯决策）；驱动层（快照 + 提交）；PVE 循环；对局日志与状态转储                                                                                                                                         |
| **判断依据** | 先盘点再补缺口；AI 只调公开提交入口；失败就换候选不预判；卡住/报错/状态不一致都算缺陷                                                                                                                                                                        |
| **落地锚点** | `src/ai/policy.ts`（纯决策，不掷骰）、`src/ai/driver.ts`（快照 `snapshotOf` + 执行 `execute` + 循环 `runAiSelfPlay`）、`stores/legal-actions.ts`（`available/blocked/unsupported` 三态）、`stores/recorder.ts`（JSONL 事实日志）、`tests/flows/ai-*.test.ts` |
| **验收**     | ① 覆盖表逐项闭合或有明确"不做"理由；② 教学剧本单回合能从初设跑到终局不卡；③ 剧本 1 多回合覆盖增援落位、可变补员、跨回合补给与整编；④ 每次跑都留下"跑到哪、卡在哪、为什么"的记录；⑤ 天气允许时走完整空军链，受限时不飞                                        |

关键判据：

1. **先做覆盖盘点，再写策略。** 三列对照（动作族 / 提交入口 / AI 是否调用），标 ✅ 直接调用、△ 间接或兜底、❌ 从未调用。缺口不是"AI 笨"，先归因到三类：
   - **快照没带候选** → 补投影，不补策略；
   - **入口是多段式点图**（需要先选格再选单位再结算）→ 驱动层要走地图分派，不能直接调底层提交；
   - **策略没写这条链** → 才写策略。
2. **驱动层只调已公开的提交入口**，不直接改 `units`/`spDumps`/会话内部；只按既有 UI 语义给输入对象赋值。这条保证"AI 走的路 = 玩家走的路"，AI 卡住就是玩家也会卡住。
3. **不用 `Math.random`、不额外消费骰流**：同种子 + 同盘面 ⇒ 同决策。AI 的可重放性和玩家一致。
4. **提交失败就记录并换候选**（按条款号分组统计），不做"我认为合法"的预判——预判会和闸门分叉。
5. **卡死判据显式化**：循环上限 + 连续拒绝计数 + 每步记忆（已移动单位、已试目标、已整备基地、已出动飞机…）。记忆的作用是"同一个候选不反复试"，不是"跳过困难"。
6. **必须由玩家决定的地方给默认值**（领军取 AR 最大、地形取对守方最有利、撤退取损失最小），让 AI 不卡死；**但不得放宽判据、不得删断言换绿**。
7. **自对弈是回归探针，不是行为证明。** 它能证明"不卡死、不崩、状态自洽"，不能证明"规则实现正确"；后者靠条款级单测与逐字用例。真实对局验收由人完成。

**验证阶梯**：教学剧本（单回合、小盘面、限格）跑通 → 剧本 1（多回合、增援、跨回合补给）→ 天气受限分支 → 空军完整链。每一级都要有日志与状态转储，否则"跑通了"不可复核。

**常见坑**：拿 AI 胜率当质量指标；用自对打代替条款单测；AI 绕过地图层导致多段式动作永远不可达；拒绝时不记录，只看到"停在原地"；为了跑通把闸门放宽。

## 8 六门槛与打包交付

### 8.1 六门槛

| #   | 门槛     | 命令                   | 报告什么                                                 |
| --- | -------- | ---------------------- | -------------------------------------------------------- |
| 1   | 静态检查 | `npm run lint`         | 错/警告数（0 错）                                        |
| 2   | 格式     | `npm run format:check` | 通过/失败文件清单                                        |
| 3   | 类型     | `npm run typecheck`    | 错误数（0）                                              |
| 4   | 用例     | `npm run test`         | 文件数 / 通过数 / 跳过数 / 失败清单                      |
| 5   | 架构     | `npm run arch`         | 组件数 / 样式数 / 源码数 / CSS 变量数 / 零调用白名单条数 |
| 6   | 构建     | `npm run build`        | 耗时、产物体积、gzip 体积                                |

**纪律：报实数，不写"已通过"。** 数字要能对上本次提交；跳过项要写清跳过原因（如"不跑内置人机对打，不作为行为证明"）。`npm run check` 是前五关的合并命令，但交付报告仍要逐关列数。

### 8.2 架构闸门查什么

| 项             | 判据                                                               |
| -------------- | ------------------------------------------------------------------ |
| 组件规则字面量 | `components/`、`views/` 里不得出现规则数字与规则号字面量           |
| CSS 变量       | 引用的变量必须在全树有定义（`tokens.css` 或 scoped 样式）          |
| 零调用导出     | 导出未接线必须进白名单；**白名单陈旧项也要报**（接线后该删那一行） |
| 资产           | 库引用的算子图必须在 `public/counters/` 下存在（由数据用例守）     |

架构闸门的价值在"防止第二套判据长出来"：组件里一旦允许写规则数字，引擎的唯一来源就形同虚设。

### 8.3 批次纪律

```
先红后绿 → 单独提交 → 跑六门槛报实数 → 非 force 并入 main → 不打包则明说不打包
```

| 纪律             | 说明                                                                        |
| ---------------- | --------------------------------------------------------------------------- |
| 先红后绿         | 先写会失败的用例，确认它红，再改实现；红不起来说明用例没测到东西            |
| 一批一提交       | 一批只做一件事；提交前 `git status` 确认暂存区只含本批文件，禁 `git add -A` |
| 不 amend、不强推 | 新提交优于改写历史；并 main 只快进                                          |
| 不顺手改         | 其他线正在改的共享文件，只挑自己的 hunk；发现不属于本批的问题先记录         |
| 证据             | 报告里"原文原句 + 结论 + 实际改动"对齐，不只报结果                          |
| 文档同源         | 新增/修改的 `.md` 也要过 `format:check`；只对失败文件 `prettier --write`    |

### 8.4 打包三条产物

| 形态          | 命令                                                           | 产物                                       | 前置                                                               |
| ------------- | -------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------ |
| 网页/双击即开 | `npm run pack` → `scripts/pack-release.mjs` + `serve-dist.mjs` | `release/`（dist + 静态服务器 + 启动脚本） | 工作树干净、HEAD 对应本批                                          |
| 桌面安装包    | `npm run tauri:build`                                          | MSI / NSIS                                 | Windows 构建链                                                     |
| 安卓侧载      | `npm run android:apk`                                          | `release/*-android.apk`                    | JDK 17 + SDK 35 + 签名文件（签名与口令**不入库**，换机要一起带走） |

**打包纪律**：打包前确认工作树干净、提交对应本批；打包过程不改代码；失败如实报失败点，不改判据凑通过。打包后报：产物路径、体积（安装包/主程序）、总耗时；并做一次双击启动冒烟（能进主界面、能新开一局、能读档）。

**常见坑**：打包前顺手改代码；force push；把全量格式红算进本批（只 `--write` 自己改的文件）；跳过自对打却声称"行为已验证"；换机打包签名不一致导致只能卸载重装（连带清掉 WebView 存档）。

## 10 与既有兵棋技能的分工

本技能是**全链索引与交接判据**，不重写任何专项细节。发现某阶段需要工具级做法，转对应技能：

| 既有技能                                                        | 管什么                                                       | 与本技能的边界                                               |
| --------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `wargame-db-pipeline`                                           | 建库通用思路（分层、留痕、闸门）                             | 本技能只规定"何时算建完"与产物落点，不重复建库判据           |
| `ocs-db-build`                                                  | 具体建库与符合性核对                                         | 同上；本技能不列字段级清单                                   |
| `ocs-rules-db`                                                  | 规则提取、规则库、引擎常量                                   | 本技能接它的产出，定义 `RuleOutcome`/条款号/复核链这一层契约 |
| `wargame-phase-window-design`                                   | 阶段/环节/窗口设计文档                                       | 本技能负责"设计 → 代码"的映射验收（id 同名、闸门唯一）       |
| `wargame-counter-interaction`                                   | 左键/右键分工、菜单生成                                      | 本技能只要求"合法性与入口同源"，不重写十条硬规则             |
| `wargame-processor` / `hexgrid-calib`                           | 网格标定、算子识别                                           | 本技能把它们的产出当阶段 1 的交付物验收                      |
| `map-terrain-identify` / `map-terrain-db`                       | 逐格地形判读与地形库                                         | 同上                                                         |
| `axis-counter-db` / `sov-counter-db` / `ocs-smolensk-counter-*` | 具体算子识别建库                                             | 同上                                                         |
| `wargame-db`                                                    | 扩剧本/扩单位的具体操作                                      | 本技能只管"扩完要过哪些门"                                   |
| `ocs-wargame-dev`                                               | 另一套技术栈（原生 ES Module + Python 静态服务器）的引擎接线 | 本技能的分层与交付判据可套用，文件落点不同                   |
| `gazala-wargame-dev`                                            | 单作品的开发规范                                             | 作品级规范优先于本技能；本技能只在它没写到的链路补位         |

判断是否重复：**如果一条做法已经能让另一个作品直接照做（含具体命令/字段），它属于专项技能；如果它回答的是"这个阶段做完了没有、下一步能不能开"，它属于本技能。**

## 12 反模式总表

| 反模式               | 后果                                   | 正解                                 |
| -------------------- | -------------------------------------- | ------------------------------------ |
| 先做界面再定闸门     | 每个面板各算一套合法性，删入口就漏能力 | 先 `ACTION_GATES`，再 UI             |
| 用实现去解释原文     | 规则错得自洽                           | 原文优先；两读法就停下报差异         |
| 标定错就改数据       | 越改越像"数据有噪声"                   | 先验证几何，再判读                   |
| 手写计数             | 与实况差几条且不易发现                 | 工具重算                             |
| 把"不适用"当缺口     | 造出成片假缺口                         | 显式 N/A 清单                        |
| 撤销只还原主状态     | 派生账残留                             | 每步记全量账，对销                   |
| 结束仍可撤           | 状态漂移、可重复获益                   | 结束=提交，硬闸                      |
| 灰项表达不可用       | 玩家反复点、怀疑卡死                   | 不生成                               |
| 两处各算一遍         | 菜单能做、执行被拒                     | 判据唯一来源                         |
| 用 AI 跑通当规则证明 | 规则错也能跑通                         | 条款单测 + 逐字用例；AI 只证明不卡死 |
| 为跑通放宽判据       | 缺陷被"修"成特性                       | 记缺陷，不改判据                     |
| 打包前顺手改代码     | 产物与报告不符                         | 打包只打包                           |
| 报"已通过"不报实数   | 无法复核                               | 逐关列数                             |

代码侧的三个落点：

派生只允许一条链：

```
sop-segments.ts（环节有哪些动作）
  + ACTION_GATES.where（每条动作族在哪些环节放行）
  → actionKeysOfSegment()（此刻该环节可做的动作族）
  → workbench.segmentActionKeys / actionAllowedNow()
  → 菜单 / 面板 / 会话窗
```

组件里**不得**出现 `phase === 'C'` 之类判断；一律问 `actionAllowedNow(key)`。

设计文档 ↔ 代码的合同：

- 文档表格每行一个环节，`环节 id` 列必须与 `sop-segments.ts` 同字符串。
- 每个环节标"驱动"（人工 / 自动 / 待答）与"渲染宿主"；标不出宿主的是空壳。
- 每个动作族在文档里出现一次，归属环节与 `ACTION_GATES.where` 一致。
- 数字（阶段数、环节数、自动环节数、动作族数）由代码枚举生成后写入文档；手写必漂（本作就出现过 30 → 32 的口径差）。

### 一次动作的实现骨架

```
1 候选：legal-actions 给出 { status, candidates, submit }
2 开始：建交互态（MoveInteractionState / CombatInteraction / …），记初始快照
3 逐步：每步 { before, patches, cost, rule }；失败整笔拒绝
4 结束：finished = true（= 提交 = 封存）
5 回执：appendLog + recordSettlement
```

### 撤销实现要点

| 概念       | 实现                                         | 说明                                          |
| ---------- | -------------------------------------------- | --------------------------------------------- |
| 步级撤销   | `undoLastStep()`                             | 用该步 `before` 快照还原 + 对销 ZOC/MP/费用账 |
| 整次放弃   | `cancelWholeMove()`                          | 回到交互开始前                                |
| 不可逆边界 | `rollbackFloor` + `markIrreversible(reason)` | 掷骰结算、突袭、特战、入盒后边界推到该步之后  |
| 撤销可用性 | `undoBlockedReason`（computed）              | 按钮显示与拒绝文案**同一判据**                |
| 结束即提交 | `interaction.finished` 硬闸                  | 结束后撤销/放弃入口都不出现                   |
| 段间       | 换段/换方/换回合封存                         | 无全局撤销栈                                  |

判据写法（避免两处各算）：

```ts
// 一步可撤销 ⇔ 它只改动了 before 快照能还原的运行态
// 快照之外的账一旦落盘（掷骰、特战、入盒），边界即前移
const undoBlockedReason = computed(() => {
  if (!interaction) return null
  if (interaction.finished) return '本次移动已结束：结束即提交，不能再撤销'
  const sealed = ports.undoSealReason()
  if (sealed) return sealed
  if (rollbackFloor.value >= 0) return `移动已触发${rollbackReason}，本段不能再撤销`
  return null
})
```

## 1 规模与形态

| 项       | 事实                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 作品     | OCS #17《Smolensk: Barbarossa Derailed》                                                                     |

## 2 关键裁定（按主题）

| 主题             | 裁定                                                                             | 落地表现                                             |
| ---------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 原文优先         | 规则书能确证的直接实现，不挂审批；原文缺失或自相矛盾才停下                       | `CODE_SPEC.md §0`；两读法写成待裁定，附各自影响      |
| 结束即提交       | 一次移动"结束"后不再有任何撤销                                                   | `interaction.finished` 硬闸；撤销/放弃入口都不出现   |
| 掷骰即封存       | 本段只要经过任何掷骰结算，撤销一步与放弃整次都关闭                               | `undoSealReason()`；破例会让"撤骰后步"变成可重复获益 |
| 撤销只在本段     | 没有全局撤销栈；换段/换方/换回合即封存                                           | 各交互态自己记历史                                   |
| 初设期只选中     | 初设时左键点单位/堆叠不投移动力范围，只做选中与堆叠显示                          | 范围提示只在移动类阶段且单位有可用 MP 时投           |
| 纯机械动作自动化 | 无玩家决策的动作（如轴心抽取编队）改为完成初设时自动执行，撤掉按钮               | 只在落点无法计算时保留待落位入口                     |
| 空军任务单入口   | 左键点六角格内的空军基地图标 → 打开该基地飞机堆叠窗 → 窗内右键某架飞机出任务菜单 | 不走其他触发路径                                     |
| PVE 初设交棒     | 双方各自使用独立的初设窗口，一方完成后再轮到另一方                               | 同一窗口内不混两方布置与按钮                         |
| 视角隔离         | 观察方只读；付款与补给源只能选本方；敌方盒不可见不可交互                         | 投影层若仍带对方内部字段，登记上报，不在 UI 遮       |
| 界面口径         | 极简；窗内不放描述；条款号收进 `?`；不可用不出现；同一功能单入口；一窗一事       | 新增面板一律照此验收                                 |
| 主题             | 默认浅色（暖纸底、压低纯黑纯白对比），深色可切换并记住                           | 只换外壳令牌，地图配色不动                           |
| 自对弈定位       | 用来找"卡死/异常/状态不一致"，不用来刷分，也不当行为证明                         | 全量验证可跳过内置自对打，但不得声称"行为已验证"     |
| 批次纪律         | 先红后绿、单独提交、六门槛报实数、非 force 并入 main、不打包就明说               | 每批报告含实测数字                                   |

## 3 踩过的坑（现象 → 根因 → 判据）

| 现象                                          | 根因                                     | 固化下来的判据                                                   |
| --------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------- |
| 算子移动类型成片错（曾一次误判 14 个装甲 HQ） | 按名称推断颜色，未目检                   | 推断记 `*_by`；低置信度与 unknown 必须目检，目检结论不被程序覆盖 |
| 网格"看起来有噪声"                            | 标定错，不是数据错                       | 先验证几何（完整格中位/P95），再逐格判读                         |
| 界面格号镜像颠倒                              | 把印刷行号当程序行号                     | 锚点实测方向，`印刷行号 = rowDecode − 程序行号`                  |
| 图卡数值与原文不一致                          | 转录时"顺手修正"                         | 逐字用例锁死（`*-verbatim.test.ts`）                             |
| 同一能力菜单能做、执行被拒                    | 菜单与会话各算一套判据                   | 闸门唯一来源；会话内只判"能不能落账"                             |
| 点击命中敌方算子时被射击菜单吞掉              | 右键分派优先级只按"格内有无单位"         | 地图格右键按"格归属 + 当前环节 + 能力作用域"三重判；单入口       |
| 空军轰炸目标选错层级                          | 按单位选目标，原文要求整体目标           | 回到原文（10.0c）改成整体目标；规则判断先于交互方便              |
| 撤销后 MP/停车账残留                          | 撤销只还原主状态                         | 每步记全量账（`before` 快照 + 派生账），撤销一并对销             |
| 关窗后还能撤，状态漂移                        | 没有"结束=提交"的硬闸                    | `finished` 后撤销入口不生成                                      |
| 存档读回后记录轨与盘面矛盾                    | 只存会话，不存盘面                       | `board` 不透明透传；四层版本逐层校验                             |
| AI 永远做不到某些动作                         | 驱动层直接调底层提交，绕过多段式地图分派 | AI 走与玩家相同的公开入口；覆盖表逐项归因                        |
| 计数对不上（30/32、8/7/5）                    | 手写数字、段/节/环/块同词多义            | 计数工具生成；文档开头先定口径表                                 |
| 全量格式红混进本批                            | 顺手 `prettier --write .`                | 只对自己改的文件执行；报告里分开列                               |
| 打包后行为与报告不符                          | 打包前又改了代码                         | 打包只打包；工作树干净 + HEAD 对应本批                           |
