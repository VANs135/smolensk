# OCS 斯摩棱斯克：代码审查与修改方案

审查日期：2026-11-01。目标：掷骰、查表、合法性检查、补给扣除和状态变更由程序结算，玩家只作规则允许的选择。

后续已按用户要求完成从首页、双方初设、A–H 到终局重开及冷读档的主线检查，详见[全流程检查与修复清单](2026-11-01-全流程检查与修复清单.md)。该报告包含七剧本流程轨迹和新复现的初设、交接、战斗、读档与提前决胜问题；下面保留第一轮审查结果。

## 1. 结论

**建议保留现有技术栈、地图标定、素材、单位库和规则函数，先修结算流程、状态持久化和重复结算，再逐步整理架构。没有必要从头重写。**

目前最主要的问题是：规则函数写出来了，但正式游戏流程没有可靠地调用它们；即使调用，状态和账本也可能没有完整提交、保存或恢复。继续只按某个按钮或某条规则零散修补，会反复出现“一个入口修好，另一个入口仍错”的情况。

本次用独立探针复现了 **10 个场景，归并为 8 类实际流程/状态缺陷和 1 类验证缺口**。其中最影响目标的是自动增援没有执行、H 清理没有执行、强制恢复可以跳过、恢复计划重复扣款、读档缺状态。这些应先于界面美化和新功能处理。

### F01：自动环节被过滤掉，却没有执行器接手

证据位置：

- `src/stores/workbench.ts:16275`：`playerSegmentSteps` 过滤全部 `driver === 'automatic'` 的环节。
- `src/stores/workbench.ts:16503`：环节推进只改变玩家环节索引。
- `src/engine/session-flow.ts:464` 附近：玩家阶段推进只更新记录轨、记 `phase` 日志。
- `src/stores/workbench.ts:16777`：真正掷补给表、补员表并写账的 `rollVariableReplNow`。
- `src/components/reinforcement/ReinforcementPanel.vue:515`：这组按钮又要求当前环节是被过滤掉的自动环节。

本次检索到的 `rollVariableReplNow` 产品调用点在该按钮内，正式推进路径没有调用。结果不是“少一个按钮”，而是每回合的可变增援及相关事件结算未发生。

修改：按 SOP 全部节点执行，自动节点执行后再跳到下一个节点；只过滤显示层，不能从实际执行序列删除。每次自动结果按回合、半场、阵营和节点唯一记账，读档和重复点击不能再掷一次。只在需要选择落点、重建对象等事项时等待玩家。

### F02：自动经过 H 段不等于完成清理

证据位置：

- `src/engine/session-flow-steps.ts`：H 段声明为 `automatic`。
- `src/stores/session.ts:663`：连跑自动步骤。
- `src/stores/workbench.ts:18782`：完整盘面清理在 `runCleanUpNow`。
- `src/views/WorkbenchView.vue:436`：该函数由验证页手动按钮调用，正式推进没有调用。

修改：H 段成为必须执行的引擎节点，在切换行动方前，以原行动方为上下文清理盘面和燃料窗口并提交日志。不能在连跑结束、已经切方后才补调清理函数。执行一次后不得因刷新界面或读档再次清理。

### F03、F08：允许某个动作，不代表允许结束环节

证据位置：

- `src/stores/workbench.ts:5287`：`advanceSegmentNow` 主要检查进行中的战斗、轰炸，之后推进。
- `src/stores/workbench.ts:11296`：强制恢复仍要玩家另点一次。
- `src/stores/workbench.ts:6169`：5.7g 校验位于单次 `finishMove`，没有覆盖整环节离开。

修改：增加统一的“本环节能否结束”判定。强制后果能自动执行的就执行；必须由玩家分配的损失、选择的落点等形成待办；未解决时不允许推进。5.7g 必须检查本环节涉及的全部预备单位，即使它们未开启过移动工具也要检查。

此处应区分自愿行动与规则义务：玩家可以放弃一次可选攻击，不能用同一个跳过动作逃掉强制恢复、损耗或已发生战斗的后果。预备单位“可路过工事、环节结束不能留在工事”的现有口径继续保留。

### F04：结算缺少“这笔已经完成”的状态

证据位置：`src/stores/workbench.ts:11296` 的恢复落盘循环读取原计划，没有完成标记或有效性版本检查；`applySupplyPhaseFeedingNow:11527`、损耗落盘等同类路径也应逐一检查，不能直接认定都已安全。

修改：每份计划包含 `planId`、生成时的盘面版本及完成状态；扣款与状态变更作为一笔提交。重复提交同一计划返回已有结果，不再扣费；盘面变化后的旧计划拒绝或重新计算。按钮禁用只是反馈，最终守卫必须在结算入口。每次扣款都能追查来源站、用途、受益单位和剩余量。

### F05：两条换阶段路径各清一部分

证据位置：

- `src/stores/workbench.ts:5327`：`setPhase` 清理 `oosFedReByDump`、`dumpDestructionAttempts`、换轨及铁路账本等。
- `src/stores/workbench.ts:5247`：正式路径的 `resetSegmentTransient` 只覆盖其中一部分。
- `src/stores/workbench.ts:5303`：正式推进之后调用的是后者。

修改：账本按实际有效期分类：一次结算、移动环节、阶段、回合、直到下个友方清理阶段、整局。使用引擎统一生命周期处理；更稳妥的是账本自带适用范围键，旧范围记录自然不再限制新范围，避免靠多处 `=[]` 维持正确性。燃料窗口不能和普通阶段账本一起清空。

### F06、F07：存档不是完整且原子化的对局快照

证据位置：

- `src/stores/workbench.ts:6784`、`:6803`：HQ、编队燃料窗口。
- `src/stores/workbench.ts:16250`：段内环节索引。
- `src/stores/workbench.ts:19586`：快照字段表没有收录以上状态。
- `src/stores/workbench.ts:19752`：按当前 ref 的浅层种类判断快照，数组元素没有完整校验；当前值为 `null` 时还跳过形状约束。
- `src/stores/session.ts:831`：读档先替换会话，再恢复盘面；恢复出错时没有原子回滚。
- `src/stores/workbench.ts:19802`：逐项写入 ref，旧档缺字段时跳过，会把当前局的值留在那里。

修改：建立独立于当前内存值的存档 schema，完整校验单位、坐标、数值、枚数、唯一 ID 和相互引用；所有缺省值来自对应版本的迁移规则，不能取当前局的值。解析、迁移、校验先在临时对象完成，全部成功后一次替换当前对局。失败时当前对局逐字段不变。

快照至少包含：记录轨、段内节点、双方实体、各期限账本、燃料覆盖集及投递基点、到货与待放置结果、一次性自动事件完成状态、随机源、所有会影响后续行动的待决事项。显示选择和悬停位置可以不保存。

第一轮另发现当前快照排除 `combatState`、`barrageState`、`airState` 等交互状态，而 `saveNow` 没有拦截进行中的结算。**后续全流程检查已完整复现战斗中途存读档丢失未分配损失，以及掷骰后取消逃掉战损，见新报告 G12/G13。**炮击、空军的每种中途恢复状态仍需专项验证。短期只允许在完整结算点保存；长期把必要的待决状态一并序列化，实现中途续局。

### F09：骰子重放需要与规则/盘面重放分开定义

证据位置：`src/engine/log-book.ts:361`；其循环核对骰面，`stateMatches` 比较的是 RNG 的 seed、内部状态和 drawCount，没有重算补给、伤亡、位置或控制权。

这项能力本身有价值，问题在于它不足以证明“自动结算正确”。短期把对外说明限定为“骰序列核验”；长期保存玩家命令和必要参数，由初始状态、固定规则/数据版本及种子重新执行，比较每笔状态摘要和最终盘面。不能用日志中已经写下的结论充当重新算出的结论。

## 4. 反复出 bug 的结构性原因

1. **流程与盘面分居两处。** `session.startGame` 的引擎会话创建空 `units/stacks/markers`，实际算子和账本放在 `workbench`。流程以为自己推进了，引擎却没有真实盘面可供清理、检查和保存。
2. **主要状态文件过大。** 本次 `workbench.ts` 为 20641 行，约 926 KB，同时承担流程、移动、战斗、补给、空军、事件、存档和界面选择。一条规则很容易只接上其中一个入口。
3. **显示用的步骤表承担了执行语义。** 过滤自动环节原本是为了减少玩家点击，但执行器没有对应接手。
4. **测试层次有缺口。** 许多用例直接 `setPhase` 或拉起单模块。`tests/regression/regression-harness.ts` 的基线主要运行会话、推进到第 3 回合，没有带完整盘面操作证明整局可信。现有测试不应废弃，但需要补正式入口和状态连续性测试。
5. **当前架构检查不能发现这些断点。** `scripts/arch-scan.mjs` 的零调用检查统计文本出现次数，测试调用、导出或不可达按钮都能增加计数；它不能证明函数在正式游戏中会执行。
6. **工程规范和历史回执存在过时信息。** 它们能解释原意，不能作为当前已修好的证据。本次也发现 `.gitignore` 的 `unit.name).join('、')}` 条目使 `rg` 报 glob 解析错误，应该一并整理。

## 5. 建议采用的改造方向

### 5.1 一份完整对局状态，所有界面读同一份

逐步扩展现有引擎状态，纳入 board、ledger、pending 和段内节点。保留现有规则函数，通过适配器把输入视图和输出补丁接到完整状态；Vue/Pinia 负责展示和派发意图，不负责手工拼接规则后果。

可以按职责新增以下模块，名称可在实施时结合现有目录调整：

| 模块                        | 职责                                             |
| --------------------------- | ------------------------------------------------ |
| `engine/game-state.ts`      | 完整对局状态及状态不变量                         |
| `engine/commands.ts`        | 移动、攻击、补给选择、推进等玩家命令             |
| `engine/resolve-command.ts` | 校验命令，计算并一次提交结果、扣费与日志         |
| `engine/phase-lifecycle.ts` | 环节结束检查、自动节点、到期状态和阶段切换       |
| `engine/persistence/`       | 存档 schema、显式版本迁移和完整快照              |
| `stores/` 下的领域投影      | 面板选择、提示和只读投影；不再持有第二份规则事实 |

避免一次性搬完两万行。先接通统一入口，再按补给、移动、战斗、空军、增援逐域迁出，每域迁移前后用同一场景对照。

### 5.2 统一推进顺序

每次“下一环节”应由一个引擎入口完成：

1. 检查当前结算和玩家必答事项。
2. 计算并执行当前节点的强制后果；需要选择时停下。
3. 检查端点约束和本节点/本阶段的结束义务。
4. 按有效期处理账本和标记，更新流程位置。
5. 按 SOP 顺序执行后续自动节点；每笔保留执行时的阵营和阶段上下文。
6. 到真正需要玩家选择的节点停下，给出清楚的结果与待办。

正式页面、验证页面、读档后的继续执行都调用同一引擎入口。验证页的手动改值另作为可审计的裁判命令，不能维护另一套正常结算规则。

### 5.3 每次结算有身份、有前提、有完整结果

一次结算需同时包含：命令编号、状态版本、规则/数据版本、参与对象、来源、骰点、费用变化、状态变化和待决事项。余额不足或条件不满足时整笔拒绝；重复命令返回已完成回执；旧计划不能直接应用在新盘面上。

规则表和剧本数据保留单一来源。存档增加能识别规则与内容差异的版本信息，不能仅依赖当前统一的 schema 版本证明不同构建一定兼容。
