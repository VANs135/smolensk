# 兵棋 UI 设计规律与战鼓源码分析

日期：2026-11-04。配套：[UI优化计划](2026-11-04-战鼓参考与兵棋UI优化计划.md)。本篇提炼交互原则，不新增代码改造排期，不修改规则或业务代码。

## 1. 分析范围

依据已下载的战鼓《朔风扬旌》公开前端，重点读了 `app.js`、`table-ui.js`、`map-actions.js`、`board-ui.js`、`combat-ui.js`、`movement-feedback.js`、`phase-ui.js`、`phase-focus.js`、`reinforcement-window.js`、`layout-04.js`、`pingjin-ui.js` 和页面样式。

本地源码位于 `D:/OCS/参考网站/zhangu.asia-2026-11-04/www/games/shuofeng-yangjing/play/`。以下将“源码能确认的行为”和“据此提出的设计建议”分开。没有完整浏览器实玩或玩家测试，故“符合习惯”是基于桌面兵棋操作方式提出的设计判断，尚不能称为经过用户实验验证的规律。

## 2. 先修正两处容易误读的地方

**不能只根据 HTML、旧函数或快捷键认定正式能力。** `app.js` 仍有翻面、伤害、移除等旧分支，`layout-04.js` 的 `removedUnitActions` 会移除对应按钮，动作入口也会拦截这些名称；`help-ui.js` 明确说明部队通过初设和正式增援进入。因此，页面残留算子库与改值函数，不等于当前正式玩法允许自由修改盘面。

**它的撤销并非无条件撤销。** `app.js` 的 `act()` 对移动、进驻、撤退步及骰子/掷骰报告变化等提交清空历史；只有未触发这些条件的操作进入撤销历史。因此应借鉴其“决定前可调整，承诺后继续处理后果”的方向；具体哪些行动可撤销，仍须按 OCS 判定，不能复制其条件表达式。

## 3. 可以提炼的十一条设计原则

### 3.1 玩家先认对象，再选择意图

源码：点算子会选中该单位，更新单位区；增援条目有实际算子图片；战斗目标、搭桥边界和待进驻单位直接呈现在地图上。

设计判断：兵棋玩家往往先关心“这叠部队/这个目标”，再决定行动。UI 应以地图对象承载入口，减少先去菜单找领域、再填对象的往返。

OCS 落地：点堆叠→展开实际算子→确认选择范围→显示本环节合法意图。若只有一种意图，可直接进入准备态；存在多种意图时显式选择，不能因相同点击直接付款或开战。正式界面仍不恢复常驻移动/战斗工具栏。

### 3.2 地理决定在地图上做，数量分配在会话里做

源码：搭桥直接点击高亮河流边界；撤退直接点击地图候选格；进驻选择算子后再确认。相关模块通过现有领域命令提交。

设计判断：目的格、路径、格边和空间关系适合直接指出；多单位分配、付款来源比较和损失选择需要列表。应根据决定的内容选择控件，而不是统一塞入坐标表单或统一变成拖拽。

OCS 落地：移动、撤退、推进、增援落点在图上选；补给来源可在图上定位和选择；参战名单、损失承担及多来源费用在唯一会话里核对。不得让玩家手填格号完成正常游戏。

### 3.3 选中了什么，必须在提交前看清

源码：区分整叠与单枚移动，拖动时对携带对象共同更新视觉位置；另有框选联攻与候选反馈。

设计判断：单枚、整叠、编队和跨格参战组是不同范围。玩家应能从轮廓、算子排列、名称和数量同时确认范围，不能只靠一个全局勾选框猜测。

OCS 落地：会话明确“选中3枚/本格共5枚”，地图同步高亮；同格未选单位保持可见但不加入行动。载货、附属标记、编队燃料受益范围分别标注，不将它们自动等同于移动选择。每次开始或提交行动前展示实际名单。

### 3.4 手势应稳定，领域动作可以随阶段变化

源码：`table-ui.js` 区分点击和拖动；鼠标小幅移动不立即触发拖动；空白拖动平移，滚轮围绕指针缩放。触屏对未选算子先选择，避免第一次触碰就拖走；有指针取消和双指缩放处理。

设计判断：阶段可以改变当前允许的行动，但平移、缩放、查看、选择、取消不应突然变义。拖动是快捷方式，不能成为必须掌握的唯一方式。右键也不能藏住唯一主流程。

OCS 落地：沿用现有选枚与点图口径；拖拽若加入，只作为等价快捷入口，不能改变费用或默认选择。点图模式始终显示“正在为谁选什么”；Esc 优先退出最内层未提交选择。阈值按实际设备验证，不直接复制源码的像素数。

### 3.5 让玩家识别合法对象，少依赖记忆和试错

源码：`phase-ui.js` 根据当前环节标记可进攻对象、增援和变化结果；`map-actions.js` 只为实际合法格边生成搭桥交互目标。

设计判断：可选对象在当前任务中可见，比让玩家逐个点击后读错误更省认知负担。但可行动高亮只是提示，不能将未高亮对象一律变得不可查看。

OCS 落地：区分可查看、可选中、可参与当前动作、可作为目标四种能力。己方暂不能行动的单位仍可检查状态，显示“已行动/缺燃料/本环节不适用”等原因；行动候选列表可以只列合格项，并注明过滤数量。禁止通过高亮泄露未知敌军、隐藏枚数或隐蔽ZOC。

### 3.6 每个行动都应有“选择—预览—提交—反馈—继续”的闭环

源码：移动预览显示请求终点、预计停点、路径和逐格费用；提交结果单独记录实际停点、耗点、剩余点数和停止原因。失败也生成结果说明。

设计判断：玩家需要在决定前理解代价，在决定后确认发生了什么。预览和事实必须能被辨认；即时鼠标反馈不能替代落账反馈。

OCS 落地：移动预览不扣 MP、不付燃料、不写ZOC承诺；实际提交后保留“从哪到哪、扣多少、剩多少、为何停止”。付款说明受益者与来源余额，战斗显示已提交的费用与待决后果。自动完成规则计算，但不替玩家选本应自主决定的方案。

### 3.7 每个区域稳定回答一种问题

源码：回合/阶段、地图、单位区、日志/战术抽屉分区；同类记录和工具维持相对稳定的位置。

设计判断：地图回答“在哪里”；流程回答“轮到谁、现在什么环节”；行动会话回答“接下来选什么”；信息栏回答“这个对象和结果如何”；日志回答“刚才发生了什么”。一致的分工比照搬几栏布局更重要。

OCS 落地：维持顶部单行流程条、地图、唯一会话、只读右栏、盒卡/辅助表格托盘。主推进只有一处；侧栏“定位/查看”可以导航，但不直接支付、结算或换段。规则号放在解释层，不把批次编号、内部步骤名当成主文案。

### 3.8 帮助玩家找变化，同时保持其空间记忆

源码：`phase-focus.js` 从真实可见的增援/断补/恢复事件中轮流聚焦，重绘不随意重置遍历次序；`table-ui.js` 调整窗口大小时补偿视口中心；轨道重绘前后保存滚动位置。

设计判断：玩家会记住当前地图范围、目标和清单位置。每次重绘都复位或自动跳图，会迫使玩家重新寻找。反过来，重要变化也不能只留一条格号日志。

OCS 落地：默认保持视角、选中和面板滚动；提供明确“定位待办/查看下一变化”入口；必须选格时只在当前目标不可见时适度平移。换手后按信息权限清理选择，不为维持视觉连续性保留上方秘密信息。面板拖动位置按展示偏好记忆，不写入规则状态。

### 3.9 收起面板与取消行动是两件事

源码：增援浮窗具有独立收起按钮和重开按钮，关闭不清 pendingReinforcements；未完成撤退或进驻时，常规动作被引导回该待决事项；提交后清空撤销历史。

设计判断：玩家可以腾出地图空间，但不能通过关窗口抹去已经发生的后果。反过来，不应因暂时不想看长列表就被迫放弃行动。

OCS 落地：未提交草稿可取消；只读/待办列表可收起且必须有重开入口；已承诺结算须完成，清楚提示当前操作者和剩余义务。强制决策面板不能无提示消失。标题栏按钮按真实能力命名，Esc 与按钮遵循相同规则。

### 3.10 有选择才打断，有结果可回看

源码：战斗在实际存在特殊战术选择时才增加选择对话框；撤退和进驻直接返回地图；战果可回看，并在CRT里标出实际落表位置。

设计判断：提示框适合真正需要回答的问题。纯计算、每次相同的确认和逐条成功弹窗会打断决策节奏；但隐藏关键费用或随机承诺也会让玩家误操作。

OCS 落地：无需选择的查表和清理由引擎完成，结果进入摘要；不可撤销的提交按钮明确写“支付并继续/掷骰结算”等实际后果。只有对象不明、后果重大或规则要求应答时增加确认。玩家决策固定次序按OCS规则，不能复制参考站的自动损失分配。

### 3.11 棋盘语言应可识别，装饰反馈应克制

源码：保留原版算子和记录轨，图上用轮廓、短标签、路线、动画辅助；按钮有按压反馈和可关闭音效，并考虑减少动态效果设置。

设计判断：熟悉的算子图形、军力/模式符号与地图关联帮助玩家迁移纸棋经验。功能状态不能只有颜色，也不能依赖音效或动画结束才能判断。

OCS 落地：保留扫描算子与既有术语；所选、可达、待处理、已完成使用不同轮廓/符号及文字。确认主按钮有清晰按压、处理中、成功/拒绝反馈；动作结果长期可查。大面积发光、频繁闪动和长战斗演出后置，不能遮住格号或拖慢连续行动。

## 4. 映射到我们的五条常见行动链

| 玩家意图          | 界面应该怎样承接                                                      | 常见失败设计                                                   |
| ----------------- | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| 移动这几枚单位    | 点堆叠→确认枚数/资格→必要模式与燃料选择→开始→地图预览/执行→结束与结果 | 只选到顶枚却移动整叠；鼠标轻抖就落账；未说明停步原因           |
| 攻击这个目标      | 点选攻方与目标→会话确认名单/补给/声明→按OCS步骤应答→损失/撤退/推进    | 普通点选即掷骰；自动替玩家分配损失；关闭面板抹掉后果           |
| 给这些单位付燃料  | 选受益者→列真实可用方法与来源→展示覆盖/费用→一次付款→余额和受益状态   | 统一“补给”灯掩盖不同资格；重复点扣两次；没油且入口也被隐藏     |
| 放置这批初设/增援 | 算子条目→合法区域→点落位→剩余数→继续下一项；可放弃项单独处理          | 重绘后选中条目变化；自动取首入口；必做项与可放弃项混成一个列表 |
| 完成这一环节      | 看待办→定位并处理→返回同一推进按钮→自动段运行→停在下一处真实决定      | 每个面板都有下一步；灰按钮无解释；有必须应答却显示“无事可做”   |

这五条链共享交互结构，但不共享规则结算。统一的是选择提示、费用格式、反馈位置和取消语义；合法性、次序、操作者及可撤销性分别由规则域提供。

## 5. 对已有计划的补充和实施顺序

现有 UI1–UI7 排期保持。先用这些原则约束实现：

1. **优先补可理解性**：当前操作者、所选范围、下一步、被拒原因、费用与结果。不等大布局完成。
2. **再统一行为**：点击/拖动/快捷键，取消/收起/承诺，待办与地图定位。相关守卫留在领域提交入口。
3. **随后减打断和找路成本**：只读内容按需展开，保存视角/滚动，简化无选择步骤。
4. **最后调整美术与动效**：字号、层级、间距、图标和适量动画；不以风格统一替代流程可玩。

## 6. 怎样验证是否真的符合玩家习惯

先找有纸棋经验的玩家完成首次操作，记录第一次误点、迟疑位置、求助、意外提交及恢复办法；再让熟悉程序的玩家连续做同类行动，检查是否被多余步骤拖慢。小规模观察用于发现问题，不能直接外推所有玩家。

建议任务：看懂当前操作者；从堆叠中只选部分移动；发现并解决缺燃料；完成一次战斗后撤退；定位待放增援；收起后重新找回待办；合法结算点存档；热坐反应阶段换手。

验收时观察：

- 不打开帮助，是否能说清“我选了谁、下一步做什么、是否已提交”？
- 是否误将查看当行动、单枚当整叠、预计费用当已扣费用？
- 被拒后，是否能从当前提示找到修正入口？
- 打开、关闭面板或调整窗口后，是否仍找得到刚才的对象？
- 纯计算是否自动完成，而需要玩家的决定是否确实停下？
- 连续重复操作时，是否还要反复找入口、看相同长提示或等待装饰动画？

“更少点击”只在不增加误操作、隐藏信息或省略玩家决定的前提下成立。目标是减少寻找和重复确认，让每一步选择及其后果清楚。
