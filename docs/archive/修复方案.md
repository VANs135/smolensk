## B0 门禁加固与数据止损（最先做）

### ① 用具名护栏的写法保护 sync 脚本

**问题**：`sync-scenarios.mjs:77-97` 的 `toScenario` 只产出 9 个 `setup` 键，而 `scenarios.json` 实际有 12 个；多出的 `formationDraw`、`airSetup`、`printedHedgehogOwners` **全是手写且引擎在消费的**（消费点：`rules/containers.ts:890`、`rules/setup.ts:1158`、`stores/workbench.ts:6104`），schema 里是 optional 所以校验不报错。同类：`sync-charts.mjs:82-88` 丢弃 `surprise` / `attrition` 两张表（`tables/lookup.ts:146` 缺表直接抛错）；`sync-map-layers.mjs:175` 把人工排除的 36.18 印刷工事恢复回来。

**改法**：照 `sync-tec.mjs:201-206` 的既有口径，给这三个脚本各加一段"落盘前比对"：

```js
// 与既有产物不一致 ⇒ 拒绝覆盖（本工程无版本控制，手写块无法再生）
const next = JSON.stringify(nextDoc, null, 2)
if (existsSync(outPath)) {
  const prev = readFileSync(outPath, 'utf8')
  if (prev !== next) {
    console.error(`[sync-scenarios] 产物将发生变化，已拒绝写入：${outPath}`)
    console.error('手写块 formationDraw / airSetup / printedHedgehogOwners 无法由脚本再生。')
    console.error('确需覆盖请加 --force，并先手工备份。')
    process.exit(1)
  }
}
writeFileSync(outPath, next)
```

**验收**：`tests/scripts/` 新增 `sync-scenarios.test.ts`（当前缺失），断言"脚本产物 ⊇ 已提交产物的全部键"；`sync-charts.test.ts` 同理断言 6 张表齐全。

### ② ESLint 覆盖构建脚本

## B1 模式折算契约（最高优先，影响全部战斗与轰炸）

### 现状

`battle.ts:403-437` 的 `unitBattleStrength` 只用 `unit.attack`，`battle.ts` 全文对 `dg` **零引用**；`workbench-model.ts:554-575` 传的是印值，而它的注释（`:551-552`）声称"引擎按 5.10b-A 处理减半"——这句话是错的。正确的倍率确实存在，但**只被 `legality.ts:577` 调用且只取 `canAttack` 布尔，数值被丢弃**（`modes.ts:537` 的 `resolveModeStats`）。

**实测后果**：DG 单位印值 A8 → 模式矩阵给 4，战斗路径给 **8**；预备未释放守方（5.7 应 ×½）矩阵给 4、战斗给 8；战略模式守方（5.8 应 0）矩阵给 0、战斗给 **8**。轰炸侧结构性无法表达折算（`BarrageUnitRequest` 无 DG 字段）。这是本次审查影响面最大的缺陷：DG 是本作最常见战果，凡被 DG 的单位攻防都是满值，**系统性约 2 倍战力偏差**。

### 判据

- 5.10b-A：`They halve their combat, barrage, and movement values.`
- 5.7：`Units attacked while in Reserve Mode defend at half Combat Strength.`
- 5.8：战略模式"战斗值与行动值均降为零"。
- 数值唯一来源：`modes.ts:279-367` 的 `BASE_MODE_EFFECT` / `MODE_MARKER_EFFECTS`（`reserve.defenseMult`、`strat.combatMult/defenseMult/barrageMult = 0`、`dg.combatMult/defenseMult/barrageMult = ½`）。
- 9.13b-A：`Attacking units are in DG Mode. (Non-DG attackers in the same combat treat exploit results normally.)`

### ① 让模式矩阵可以脱离完整 `ModeState` 被调用

`battle.ts` 只有 `BattleUnitView`（含 `mode` / `dg` / `releasedFromReserve`），没有 `ModeState` 的 `orientation` / `exploit`，所以现在没法直接调 `modeEffect`。

**改法**（`modes.ts`）：把 `activeMarker`（`:389-406`）与 `modeEffect`（`:376-379`）的入参类型从 `ModeState` 收窄为结构子集：

```ts
/** 模式矩阵只需要这四项；战斗/轰炸路径没有完整 ModeState 也能查表 */
export type ModeEffectInput = Pick<ModeState, 'mode'> &
  Partial<Pick<ModeState, 'dg' | 'exploit' | 'releasedFromReserve' | 'orientation'>>

export function activeMarker(state: ModeEffectInput): ModeMarker | null
export function modeEffect(state: ModeEffectInput): ModeEffect
```

`activeMarker` 的既有优先级（released reserve → base；`dg` → dg；`exploit` → exploit；`reserve` / `strat`）**不动**，只改类型。`resolveModeStats`（`:537`）随之内联复用，行为不变。

**验收**：`tests/engine/modes.test.ts` 增补"用四项子集调用 `modeEffect` 与用完整 `ModeState` 调用结果逐字段相同"（对 reserve/strat/exploit/dg/base 五种各一条）。

### ② 战斗路径施加折算

**改法**（`battle.ts:403-437`）：在读到印值处施加模式倍率。

```ts
const effect = modeEffect({
  mode: unit.mode,
  dg: unit.dg,
  releasedFromReserve: unit.releasedFromReserve,
})
// 5.10b-A / 5.7 / 5.8：攻方用 combatMult、守方用 defenseMult（同一单位两角色倍率不同，
//  预备守方 ×½ 而攻不变，故不能预先折算成一个字段）
const modeMult = role === 'attacker' ? effect.combatMult : effect.defenseMult
let value = unit.attack * modeMult * terrainMultiplier
```

倍率与既有 9.11d 减半、9.5/9.5a 补给减半的相乘顺序无关（全为乘法），放在 `:423` 即可。

同时**删掉两处互相矛盾的注释**：`battle.ts:70`、`workbench-model.ts:552`（后者声称引擎已处理，实际未处理）。

**注意**：攻方侧的 strat / 未释放 reserve 已由 `battle.ts:190-193` 的 9.1e 拦掉，所以本次改动实际生效的是**守方侧**与**双方 DG**——这正是缺陷所在。

**验收**（`tests/engine/battle.test.ts` 按 9.4 分组新增）：

- DG 攻方印值 A8（有战斗补给、Open）→ `strength === 4`，`rule` 含 `5.10b`。
- DG 守方同上 → 4。
- 预备未释放守方 → 4，且攻方不受影响。
- 战略守方 → 0。
- 已释放预备（5.7b）守方 → 8（回到印值，证明 `releasedFromReserve` 分支正确）。
- 9.13b-A：DG 与同伴混编，同伴进击照常（见 B6①）。

### ③ 轰炸路径施加折算

**改法**：

1. `barrage-interaction.ts:95` 的 `BarrageUnitRequest` 增加 `dg?: boolean`、`mode?: UnitMode`、`releasedFromReserve?: boolean`。
2. `beginBarrage`（`barrage-interaction.ts:284-296`）在折算 `assignedValue` 的那一处施加倍率：

```ts
const units = input.units.map((unit) => {
  const mult =
    unit.dg === true || unit.mode !== undefined
      ? modeEffect({
          mode: unit.mode ?? 'combat',
          dg: unit.dg,
          releasedFromReserve: unit.releasedFromReserve,
        }).barrageMult
      : 1
  return { ...unit, assignedValue: (unit.assignedValue ?? unit.printedValue) * mult }
})
```

3. **连带必须改的一处**：10.0e-B 的 `belowPrintedValue` 判定（`barrage.ts:704-706`）比的是"分配值 vs 印值"。DG 生效后**有效印值**是折半的，调用方（`workbench-model.ts:806-814`）必须改比 `beginBarrage` 返回的 `units[].assignedValue`，否则 DG 炮兵的合法轰炸会被判违规。这一条是本次改动的隐含依赖，务必一起改。
4. `workbench-model.ts:806-814` 的 `toBarrageUnitRequest` 传 `dg: unit.mode.dg`、`mode: unit.mode.mode`、`releasedFromReserve`。

**验收**：`tests/engine/barrage-interaction.test.ts` 新增——DG 炮兵印值 4 → `totalValue === 2`（并因此落在不同列位）；DG 与非 DG 混编求和正确；战略模式炮兵 `totalValue === 0`。

**回归风险**：`tests/regression/replay-baseline.test.ts` 与 `crt-golden.test.ts` 的期望值会变（因为战力口径变了）。**这是预期内的**，但必须逐条人工确认新期望值符合规则，不得整批 `-u` 刷新——否则等于把缺陷固化成基线。

## B2 6.1d 互逆性（单位卡死）

### 现状

`move.ts:292-306` 的 `violatesReciprocity` 反向判定**写死 `followingRoad: false`**，而正向计费（`move.ts:260`）用 `(crossing?.routes ?? []).length > 0`。结果"沿路进得去、沿同一条路出不来"——恰恰是 6.1d 要禁止的不对称，而且**单位永久卡死**（可达格 BFS 同判据，高亮集为空）。

**实测**：全图轮式 **152 组单向步**、履带 152 组、徒步 0 组（对照组，证明成因是禁入地形判据）。最小反例 `2.3(Swamp) ⇄ 2.2 Bobruysk`（格边为二级道路）：`2.2→2.3 = ok`，`2.3→2.2 = reciprocity/6.1d`。

### 改法

`move.ts:298-305`，反向判定与正向同口径：

```ts
const backCrossing = context.map.crossingBetween(to, from)
const viaRoute = (backCrossing?.routes ?? []).length > 0
const back = selectMovementTerrain({
  terrainsPresent: context.map.terrainsAt(from),
  mobility: unit.mobility,
  crossing: backCrossing,
  followingRoad: viaRoute, // 6.2a：沿路离开禁入地形格与沿路进入同权
  forOverrun: false,
})
```

`crossingBetween(a, b)` 经 `hexsideOf` 取键（`map-facts.ts:84-88`），已确认对参数顺序不敏感，故 `(to, from)` 与正向 `(from, to)` 取到同一条格边。

**连带**：`tests/engine/move.test.ts:195-204` 把现状（互逆被拒）写成了预期，必须改为"沿路离开合法"，并在测试名里标明 6.1d。

**验收**：

- `2.3 ⇄ 2.2` 双向均 `ok`。
- 全图扫描：轮式/履带单向步数 **= 0**（把 `_tmp_review/move-verify2.test.ts` 的扫描逻辑正式收进 `tests/engine/move.test.ts`，作为 6.1d 的整体不变量）。
- 反例仍被拒：两条格边都不承载道路时，禁入地形格的进出仍双向拒绝（防止把互逆性改成"永不拒绝"）。

## B3 专规 2.1a 补给源关闭（五个源永不关闭）

### 现状

`exclusive-timing.ts:169-173` 用 `hex.col < minCol`，把 **Entry E 本体**（42.00 / 43.01 / 44.00）排除在外；`:152` 的契约注释声明"南缘＝行号 0 一线"，但**奇数列没有第 0 行**（最小行是 1，已用 `map-layers.json` 核实），于是 13.01 / 29.01 也漏掉。`stores/workbench.ts:8102` 的实现就是 `hex.row === 0`。

**实测**：引擎在 1941-08-19 只关闭 `14.0, 20.0, 20.35`；而 `scenarios.json` 的 `sovietLive` 里 `13.01 / 29.01 / 42.00 / 43.01 / 44.00` 这 5 个源该关没关（`rules-constants.json` 的 `smolensk.supplyShutdown.southSources = 1941-08-19`）。

### ① 关闭判据

`exclusive-timing.ts:169-173`：

```ts
export function isWestOfEntryE(hex, facts) {
  if (facts.entryEHexes.length === 0) return false
  const maxCol = Math.max(...facts.entryEHexes.map((i) => i.col))
  // 2.1a：「Entry E 及以西」含 Entry E 本体
  return facts.isSouthEdge(hex) && hex.col <= maxCol
}
```

（`maxCol` 取 44；`sovietLive` 中西缘源 `51.01`、`56.00`、`58.00` 的列均 > 44，不受影响，与源库逐格 `shutdown` 期望集合完全一致。）

### ② 南缘判据

奇数列没有第 0 行，故"南缘"＝**该格没有图内南邻**。

**改法**：在 `hex-geometry.ts` 增加一个可复用的判据（`isOnMap` 已是该文件的现成导出 `:124`，无需外部注入）：

```ts
/**
 * 南缘：该格没有**图内南邻**
 *
 * ★ 不能写成 `row === bounds.rowStart`：奇数列没有第 0 行（最小行为 1），
 *   故 13.01 / 29.01 这类南缘源会被漏掉（已用 map-layers.hexes 核实）。
 */
export function isSouthEdge(hex: HexRef): boolean {
  return !isOnMap({ col: hex.col, row: hex.row - 1 })
}
```

`SupplyShutdownFacts.isSouthEdge` 的**契约注释同步改掉**（现在的"南缘＝行号 0 一线"是错的），`stores/workbench.ts:8102` 的注入改为 `isSouthEdge: (hex) => isSouthEdge(hex)`（引擎侧唯一实现）。

### ③ 连带：安全边不应再保护已关闭的源

`stores/workbench.ts:7137-7147` 的 `safeEdgeHexesBySide` 直接取剧本原始清单，**未按日期剔除已关闭源**。于是 Entry L（19 Jul 起）与上述南缘源（19 Aug 起）关闭后仍继续享受专规 1.1b"敌方地面单位不得进入"的保护（这是**过度限制**，轴军进不去本应可进的格）。改为按 `supplySourceStatuses` 过滤 `open === true` 的源。

同时复核 `isNorthEdge`（`workbench.ts:7088`、`:7207`）取 `rowEnd - 1 = 34` 的"容许 1 格缓冲"是否成立（真正的北缘是 row 35）。

**验收**（`tests/engine/exclusive-timing.test.ts`）：

- 逐格断言 1941-08-19 的关闭集合 === `[13.01, 14.00, 20.00, 29.01, 42.00, 43.01, 44.00]`（把 `_tmp_review/move-verify2.test.ts` 那条断言正式收编）。
- 1941-08-18 该集合为空。
- `51.01 / 56.00 / 58.00` 始终开放。
- 奇数列第 1 行判为南缘、偶数列第 1 行不判为南缘。

## B5 补给与铁路

建议拆成 5 个子批，逐批过门禁。

### 5① 12.6c 吃图上补给的批量费率

`rules/trace-supply.ts:1116` 逐单位给 `eatingCostT`，`supply-phase.ts:534-544` 逐个扣 `remainingT`，`supply-interaction.ts:552-565` 同样逐个扣。条文 12.6c：`For every 1T spent, up to 2 RE ... can be fed. Round all fractions up; for example, 6 1/2 RE would cost 4T.`——例中的 6.5 RE 只能是**一批单位合计**，取整作用在批次总量上。

**实测**：两个 1RE 单位同格收 2T（应为 `ceil(2/2)=1T`）；四个 0.5RE 营收 4T（应为 1T，**4 倍**）。

**改法**：`trace-supply.ts:878-881` 的 `eatingOffTheMapCostT` 已经是批量口径，改为由 `planSupplyPhase` / `planOosResolution` 按"同格/同批 RE 合计"调用它；`assessUnitSupply` 保留逐单位判**是否可喂**，但不再逐单位计价。

### 5② 13.3f 轨距约束接进铁路补给线

`rules/rail-supply.ts:38-68` 的 `RailSupplyFacts` 没有任何 gauge 谓词，BFS（`:99-149`）只看 control/EZOC；而铁路运输侧有（`rail.ts:190,330,344,356` 的 `railGaugeUsable`）。13.3f：`a side can only use its rail capacity or supply line trace along rail lines of a particular gauge`。Smolensk 的轴方**正是靠轨距转换才有补给线**，缺这条等于把本作核心机制绕过。

**实测**：同一场景下 `validateRailMovement` 正确报 `13.3f / pathHexWrongGauge:36.1`，而 `railSupplyPath` 照样把该格算可达并判为火车卸货格。

**改法**：`RailSupplyFacts` 增 `railGaugeUsable(hex, side)`，BFS 进入与 `detrainableHexes` 过滤都加此条；`stores/workbench.ts:1877-1895` 侧补轨距账本（轨距转换进度），与 `rail.ts` 同源。

### 5③ 13.3c 火车卸货格必须先是铁路格

`rail-supply.ts:151-157` 的 `detrainableHexes` 缺 `isRailHex` 过滤。13.3c：`A railroad hex is detrainable if it meets all of these requirements`。**实测**：延补队停在无铁路的村庄格（12.7a-B/C 的典型布置，延补队格本身常不在铁路上）也被判为卸货格。加过滤即可。

### 5④ 12.4 战斗补给账本不守恒（可免费攻击）

- `stores/workbench.ts:4046-4047` 与 `:2576-2577`：攻守双方的 `availableT` **都取自同一个 `fuelPool`**。
- `:4094-4102`：扣款从 `fuelPool` 扣且 `Math.max(0, …)` 夹住，而玩家**声明的补给来源站**（`pickCombatSupplyDump`，`:1658-1669`）分文未动。
- `availableT = fuelPool.t` 丢掉整 SP：12.1a 的 1 SP = 4 T，引擎自己的 `planSpPayment`（`supply-interaction.ts:157-179`）就有拆分整 SP 找零逻辑，store 却忽略。

**实测**：燃料池 2 SP + 0 T（实有 8T）→ `attackerAvailableT = 0` → `confirmCombatSupply()` 被 12.4 拒绝；声明一个 4 SP + 0 T 的补给站为来源 → 同样 `availableT = 0`；声明 1SP+1T 的站为来源 → 战斗通过后该站分文未动、扣款落在燃料池（5→3）；池为 0 时 → **攻击通过且两处都没扣款（免费攻击）**。

**改法**：`availableT = sp * SP_TO_T + t`（引用常量，禁字面量 4）；扣款落在被点选的 dump 上、按 `planSpPayment` 走；攻守各自付款；删除 `fuelPool` 这条与"声明来源"并行的第二账本，或明确它就是唯一的池并删掉声明入口。

### 5⑤ 12.7b 同一条规则两套实现

`rail-supply.ts:131` 用 `hexDistance(hex, extender.hex) > rangeMp`（格数），而 `trace-supply.ts:711-760` 用 `countSupplyDistanceToAny`（按 MP 与地形成本）。12.7b：`Extenders have a range that is the maximum distance (in MP) back to the connected hex`。**实测**：地形成本 5MP/格 × 6 格时，`traceSourcesFor` 判回连失败，而 `railSupplyPath` 判已接续——两者不可能都对。统一到 `trace-supply` 的距离函数（或把"回连距离"作为事实由调用方注入）。

**验收**：`tests/engine/trace-supply.test.ts`、`supply-phase.test.ts`、`rail.test.ts` 按上述各条新增；`tests/flows/40-phase-d-supply.test.ts` 补"多单位同格同批收费"与"战斗补给从声明 dump 扣款、攻守各自付款"两条端到端。

## B8 Zod schema 收窄

`charts.schema.ts:23` 的 `grid: z.array(z.array(z.string()))` 注释写着"行数 × 列数 = rows.length × columns.length"，但从不校验。实测以下**全部通过校验**：删掉某行末格（ragged）、删掉一整行、多插一行、列宽与 `columns` 不符、整个 grid 行序颠倒（引擎按行列下标取格，错位即静默取错数值）。同类：`units.schema.ts:18-25` 的数值域（实测 `ar = 99`、`ma = 1e9`、`barrage = 1.7` 均放行，而 counter-fields 文档写明 AR 印值 0–5）、`:152` 的 `reSize`（文档口径只有 1/4、1/2、1、多军力＝军力数；实测 `reSize = 7` / `0` 放行）、`:66` 的 `id` 格式（CODE_SPEC §4 的 `<国籍>-<兵种>-<番号>` 未校验）、`arrivals.schema.ts:74` 与 `map-config.schema.ts:41,44` 的 `z.record` 键（实测 `"Ebtry K"`、`"Entry ZZ"` 放行——键打错＝这批单位永远不抵达且无提示）。

**改法**：

- grid / matrix 加 `.superRefine` 断言行数与列数；CRT 断言 15 × 13。
- `ar` 加 `.max(5)`；`ma` 加合理上界；`barrage` 统一为整数或显式声明可分（与 `attack/ar/ma` 的 int 口径一致）。
- `reSize` 改 `z.union([z.literal(0.25), z.literal(0.5), z.number().int().positive()])`。
