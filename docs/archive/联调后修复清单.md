## 0. 本清单怎么用

### 0.1 批次纪律（沿用 `修复方案.md` §0.1）

一次只做一个批次，每批独立过门禁、独立可交付；批内按 ①②③ 顺序执行（后面的依赖前面的）。

| 批次   | 目标                                         | 影响面               | 风险 | 前置             |
| ------ | -------------------------------------------- | -------------------- | ---- | ---------------- |
| **R1** | 联调遗留：派生账本单一化 + preTurn 段闸      | 全部规则（会算错局） | 中   | 无（**最先做**） |
| **R2** | 已接线能力的**强制**缺口（引擎有钩子没生效） | 后勤 / 战斗          | 低   | R1               |
| **R3** | 未接线的能力（按"打不完一局"排序）           | 功能可用性           | 高   | R1               |
| **R4** | 战斗规则补缺（原 B6）                        | 战斗 / 轰炸          | 中   | 无               |
| **R5** | 交互与渲染（原 B7）                          | 界面                 | 低   | 无               |
| **R6** | 门禁与数据（原 B0③ / B8 / 建库缺口）         | 构建期 / 数据契约    | 低   | 无               |

R4/R5/R6 与 R1–R3 无耦合，可并行；**R1 必须最先做**（它的两条会让一整局的账本与段闸算错）。

### 0.2 三条硬约束（沿用，仍然有效）

1. **不改 `src/data/*.json` 的数值**；数值改动一律经 `scripts/`，且必须先过 `scripts/overwrite-guard.mjs` 护栏。
2. 三个 sync 脚本（`sync-scenarios` / `sync-charts` / `sync-map-layers`）**重跑前先确认护栏在位**：本工程**不是 git 仓库**，没有回退网。当前三脚本重跑均报 `unchanged`，可安全重跑。
3. 每批改动前先 `xcopy` 一份 `src/` 到 `D:\OCS\备份\修复前_R<n>_<日期>\` 作回滚点。

### 0.3 每条的固定收尾

1. **四条判据自检**（可达 / 强制 / 留痕 / 可玩通）——缺任何一条不算做完；
2. `npm run check` 四关全绿（注意：本机**串联命令只能用 `&&`，不能用 `;`**，否则后续命令会被拼进前一条的 argv，给出误导性的"测试全挂"）；
3. 端到端用例进 `tests/flows/` 或 `tests/stores/`（不是只跑在临时目录）；
4. 回写 `docs/程序目录与清单.md`（新增入口的文件联动）；
5. 用范围文档的标尺复述一遍："这一步能不能让人少翻一次规则书"——不能则视为未完成。

## 1. R1 联调遗留（最先做）

联调确立了「会话 store 是唯一权威，其余一律只读投影」的口径，并把**剧本号 / 流程钟 / 地图覆盖层**三处统一了。但复核发现：**统一的是"号"本身，不是"号派生出来的账本"**，于是漏出两条。

### ① 派生账本随剧本重取：从"入口各自刷新"改为"看权威"

**落点**：`src/stores/workbench.ts`（账本段与 `setScenarioId`）、`src/stores/session.ts`（`setScenarioId` / `loadNow`）、`src/stores/containers.ts:928`、`src/stores/setup.ts:575`

**现状（实测证据）**：剧本 3 存档 → 新实例（默认剧本 1）读档 ⇒ 四处剧本号都变 `3` ✓，但

| 账本                         | 读档后实际 | 剧本 3 应有 |
| ---------------------------- | ---------- | ----------- |
| `constructionMarkers`（3.5） | **3**      | **0**       |
| `convertedRailHexes`（1.2）  | **2 格**   | **10 格**   |

- 后果是规则性错误：剧本 3 里苏军本不能建工事（`constructionMarkers: 0`）却能建 3 个；轴方铁路只放行剧本 1 的 `1.3/2.2`，剧本 3 的三段走线（`01.03→2.02`、`01.19→4.18`、`01.07→4.07`）没进账本 ⇒ **12.6a②/13.3c 的铁路补给判定全错**。
- 可达路径：`components/save/SaveLoadDialog.vue` 的读档（界面可达）；`containers.setScenario`（联调把它当"入口三"，当前无按钮）同样不刷新。
- 根因：`session.setScenarioId` 与 `loadNow` **只写会话**；而「随剧本重取的盘面账本」那段写在 `workbench.setScenarioId` 里，三个入口中只有 `setup.selectScenario` 会调它。

**改法**（二选一，推荐前者）：

- **A（推荐）**：把那段账本重取改为**对 `scenarioId` 的 `watch`**（`workbench.scenarioId` 是投影，权威一变即重取）——此后任何写会话的路径（读档 / 容器盒 / 初设面板 / 未来的新入口）自动覆盖，不再依赖"谁记得调我"。注意 `immediate: true` 要在 store 内 `scenarioId` 声明之后注册。
- **B**：在 `session` 里发"剧本已变"信号（版本号 ref），`workbench` 订阅；语义更显式，但多一层间接。

需要重取的账本清单（一次列全，避免下次再漏）：`arrivalHexOverrides`、`supplyCacheHoldings`、`constructionMarkers`、`victoryLastControl` / `victoryError`、`printedHedgehogOwners`、`convertedRailHexes` + `gaugeConversionsThisPhase`、`specialPending`。

**验收**：`tests/stores/integration-sync.test.ts` 增两条 ——（a）剧本 3 存档 → 新实例读档 ⇒ 逐项断言上表两列**相等**；（b）`containers.setScenario('7')` ⇒ `convertedRailHexes.length === 86`（剧本 7 四段走线 2+34+39+11）。另加一条 `setup.selectScenario` 的对照，钉住三条入口**结论一致**。

**风险**：`watch` 会在读档瞬间触发一次全量重取，若某账本被玩家手工改过（裁判订正），会被覆盖。⇒ 手工订正类账本（`convertedRailHexes` 的清空/逐格转换）要么在重取时先告警，要么从"权威"里派生（见改法 A 的延伸）。这条风险要在批次说明里写清。

### ② preTurn 的段投影：从"沿用本地值"改为"无段"

**落点**：`src/stores/workbench.ts` 的 `consolePhaseOf`（投影函数）与 `phase` 计算属性

**现状（实测证据）**：`session.startGame()` 后 `records.phase === 'preTurn'`，而 `workbench.phase` 投影为 `'movement'`（本地缺省值）⇒ 点地图选中单位**可走 38 格**。对照：切到 D 补给段后**可走 0 格** ⇒ 段闸本身有效，唯独 preTurn 被兜底放行。

- 2.2 的 pre-turn 只有天气与先手判定，**没有行动段**；当前等于"天气/先手还没判完就授权移动"。
- 触发面：对局台开局后（共识勾选之前）地图可点（`GameTableView.vue` 无条件渲染 `MapCanvas`，且 `mapView.onHexClick` 直通 `workbench.clickHex`）。

**改法**：`consolePhaseOf` 对 `preTurn` 不再返回 `null`，而是让 `phase` 进入一个**显式的"无段"态**（例如新增 `ConsolePhase | null` 的内部表示，或加一个 `actionsAllowed` 门）。所有段闸动作在"无段"下一律拒绝并给 `2.2`。注意别把 `turnEnd`（现归 `cleanUp`）一起改掉——收束动作确实发生在 H 段。

**验收**：新增用例 ——（a）`startGame()` 后 `workbench.phase` 不表示任何可行动段；（b）此时点单位的可走格数为 **0**、`isLegal('move')` 被拒且 `rule === '2.2'`；（c）步进到 A 段后同样的动作**通过**（证明挡的是段闸而不是别的）；（d）无会话时仍可自由演练（保住既有口径）。

**风险**：低。但要顺带检查所有读 `phase` 的界面分支是否有 `null` 分支（`vue-tsc` 会强制处理，属安全带）。

### ③ 第三套钟：`Records.phase` 与 SOP 步指针的相互关系要写进口径

**落点**：`docs/接线执行方案.md`（口径）+ `src/stores/session.ts` 的 `patchRecords` 注释

**现状（实测）**：停在 A 飞机整备 → `workbench.setPhase('movement')`（`records.phase` 变 movement）→ `session.stepNow()` ⇒ `records.phase` 被流程按**自己的步序**改成 `supply`，手动切的那段被抹掉。也就是除"会话记录轨 / 操作台本地值"之外，还有**第三套钟：SOP 步指针**，只有流程条知道它。

**改法**（口径问题，不一定改代码）：二选一并在文档写死——

- **A**：明确"手动切段是**临时**覆盖，下一次步进即以流程为准"，并把这条写进 `patchRecords` 的文档注释（当前注释只说了"写回记录轨"，没说会被步进覆盖）；
- **B**：让 `patchRecords` 改段时**同步推进步指针**到该段的第一步（需要引擎暴露"按段找步"），语义更强但改动大。

**验收**：把选定口径写成用例（当前行为 = A）：手动切段 → 步进 → 断言回到流程的段，且注释与用例同源。

**风险**：选 B 会触碰 `session-flow` 的步进语义，影响面比看起来大；建议先按 A 固化口径，等 R3 的补给/战斗阶段接完之后再评估。

## 2. R2 已接线能力的**强制**缺口（引擎有钩子，没生效）

共同特征：引擎函数写好了、甚至被别的引擎模块调用了，但**调用方没把事实注入**或**没有入口**，于是判据恒真/恒假——这正是范围文档 §26「强制」判据的反面。

### ① 5.8b 战略模式须停在有追溯补给的格（一条 if，永远进不去）

**落点**：`src/stores/workbench-model.ts:396` 的 `buildMoveContext`

**现状**：引擎 `src/engine/rules/move.ts:423` 写着

```ts
if (mustEndMoveInSupply(state) && context.traceSupplyAt !== undefined) {
  if (!context.traceSupplyAt(to, unit.side)) mustEndMove = true
```

但 `buildMoveContext` 的入参里**没有 `traceSupplyAt`**（当前只给 `units / activeSide / phase / safeEdgeHexesBySide`），全仓也没有第二处构造 `MoveContext` ⇒ `context.traceSupplyAt === undefined`，那个分支**永不进入** ⇒ 战略模式单位可以随便停在断补格，5.8b 完全不强制。

**改法**：`buildMoveContext` 增可选入参 `traceSupplyAt?: (hex, side) => boolean`，由 `workbench` 侧用 `createTraceSupplyAt(supplyFacts.value)` 注入（与 9.14d 的 `hasTraceSupplyAt` 同源——同一份 `supplyFacts`，不要另建）。缺口只在"操作台没有 traceSupplyAt"这一步。

**验收**：`tests/flows/` 增用例 ——战略模式单位走到一个**没有追溯补给**的格上 ⇒ 移动合法但**该轮移动强制结束**（`movementEnded === true`）并给 `5.8b`；格上有补给时**不**强制结束。

**风险**：低。可能让若干既有移动用例变红（战略模式单位停在断补格上的那些），逐个复核是"用例本身没考虑 5.8b"还是"新判据有误"。

### ② 12.10a 部队储备动用（`canUseInternalStocks` 零消费）

**落点**：`src/engine/rules/supply.ts` → `src/stores/workbench.ts` 的补给付款处

**现状**：`canUseInternalStocks` 在 `src/` 内**零调用**（只有测试用）。用户裁定："只有在无法获得图上补给的情况下，单位才能使用部队储备。参见 12.10。" ⇒ 当前**被围的单位仍不能攻击**（12.10 的用途拿不到入口），而它本可以用部队储备付战斗补给。

**改法**：在 12.4 战斗补给的付款分支加一条**兜底**：图上来源（12.3a ∪ 12.3b）全不可用时，才允许用部队储备支付，并按 `canUseInternalStocks` 校验；付款后按 12.10 扣减 `internalStocks`（单位状态里已有 `internalStocks` 字段）。

**验收**：新增用例 ——（a）有图上补给时**不得**用部队储备（`canUseInternalStocks` 拒绝，给 12.10）；（b）图上补给被切断时**可以**用，且 9.5 的消耗公式（攻方 Σsteps×1T、守方 Σre≤1?1:2T）不变；（c）账本闭合：动用的储备量等于引擎结论。

**风险**：中。付款路径刚在 B5① 重整过（`planSpPayment` + 原子校验），新分支要接进同一处，别开第二条付款路。

### ③ 12.10e 部队储备恢复（强制项）与 12.11a 补给站销毁

**落点**：`src/engine/rules/supply-phase.ts`（`planInternalStocksRecovery` / `internalStocksReplenishCost` / `planDumpDestruction` / `canAttemptDumpDestruction`）→ 补给阶段面板

**现状**：四个入口在 `src/` 内零消费；补给阶段没有"储备恢复"与"补给站销毁"两步。

**改法**：随 R3① 的补给阶段总计划一起做（同一段的两步），**储备恢复按范围文档第 24 项是"强制"而非选项**——不得做成"要不要恢复"的勾选。

**验收**：补给阶段一回合的端到端用例覆盖这两步；`planSupplyPhase` 的步骤清单里它们的 `done` 为真。

**风险**：低。

## 3. R3 未接线的能力（按"打不完一局"排序）

缺口总表 24 项里，**已接 11 项**（12.6 逐单位评估、13.3f 轨距转换、20.0a/b 拆分、13.9 合并、3.4b 的 SP 平分、12.8e 的 `canBreakout` 判定、2.4 缓慢动员、9.14 特殊战斗结算、14.9/14.10 空运空投、3.3b 治安检查、13.3c/13.3f 的铁路补给判定），**仍缺 13 项**。按"打不完一局"的判据排序：

### ① 12.1–12.2 补给阶段总计划（`planSupplyPhase`）

**现状**：引擎有 13 个导出，`src/` 内零消费 ⇒ 补给阶段没有"总计划"这一步，玩家只能逐项手工走（断补处置已有，但 12.11 的损耗骰、12.10e 恢复、12.11a 销毁都在这个计划里）。

**改法**：store 动作 `planSupplyPhaseNow()` + 面板（步骤清单 + 逐项确认），复用已有的 `supplyStepChecklist` 呈现方式。**这一步会把 12.8b 的损耗骰一起落地**（P1-2 的原目标）。

**验收**：`tests/flows/` 一个完整 D 段：进入补给阶段 → 计划 → 逐项确认 → 阶段结束，账本闭合（消耗 T + 剩余 T === 分配前可用 T，按方分别核算）。

**风险**：中高。这是 R3 里最大的一件，建议拆成"计划骨架 → 损耗骰 → 恢复/销毁"三个子批。

### ② 9.14d 移动阶段的**主动**崩溃入口（规则第 2 条）

**现状**：`resolveExtenderCollapse` / `extenderDisplacementCandidates` 已被 `special-combat.ts` 使用（9.14d 的**被动**路径在），但"移动阶段主动用崩溃流程替代常规移动"这一条**完全没有入口**（`specialPending` 只从特殊战斗产生）。

**改法**：store 动作 + 地图入口，落在**移动阶段**；位移落点已走 `setSpecialDisplacement`（9.14d 的落点条件在 B4⑤ 已修）。

**验收**：移动阶段主动崩溃的端到端用例（含"无合法落点 ⇒ 原地 + 夺取判定"第 7 条）。

**风险**：中。

### ③ 13.3 铁路运货全链 + 13.2c 运输点数合并拆分

**现状**：`validateRailMovement` / `transportPointLoadCost` / `validateTransportPointLoad` / `validateTransportPointUnload` / `mergeTransportPoints` / `splitTransportPoint` / `railCapacityCost` / `createRailFacts` **在 `src/` 内全部零消费** ⇒ 13.3 整章（运货）未接；铁路容量轨从未被真实扣减。

**改法**：store 动作 + **容量账本**（`containers.railCapacityLedger` 已有 state，但没有任何动作消费它）+ 地图选路（登车格 → 铁路路径 → 卸货格）。运量费用侧**只用** `railCapacityCost` 的破坏区与"全程多轨"两条地形修正；**轨距不参与费用**（轨距管谁能用，已在 B5③ 接进补给线）。

**验收**：整回合内完成一次铁路运输 + 一次轨距转换（每阶段 ≤ 4 格）的端到端用例；容量真实扣减并有超容量拒绝。

**风险**：高。需要 `createRailFacts` 的完整注入（控制 / 轨距 / EZOC / 敌方单位 / 可卸货格 / 破坏区六项），建议单独一批。

### ④ 12.7 延补队双向转换（两个方向都没有动作）

**现状**：`canConvertTransportToExtender` / `planConvertTransportToExtender` / `planFlipExtenderToTransport` / `extenderCreationCost` 在 `src/` 内零消费 ⇒ 玩家不能用运输点数**造**延补队，也不能把延补队**翻回**常规运输点数。12.7a 说延补队"唯一作用是创造一个新的追溯补给位置"，造不出来就等于这条规则没有入口。

**改法**：两个 store 动作 + 入口（各自消耗一半 MA，12.7c 锁链天然由 BFS 支持，见 `rail-supply.ts` 的注释）。

**验收**：造一个延补队 ⇒ 它接续的铁路段变为可达（`railSupply.usedExtenderHexes` 含它）；翻回 ⇒ 该段失去连接。两个方向各一条用例。

**风险**：中低。

### ⑤ 12.8e 突围的**结算**（只有判定接了）

**现状**：`canBreakout` 已接（用于断补图标），但 `resolveBreakout` / `resolveBreakoutAttempt` / `resolveBreakoutReturn` 零消费，`workbench.ts` 内连 `breakout` 的动作名都没有 ⇒ 玩家能"宣布突围"却**结算不了**（12.8e 的条件 A 路径搜索也仍是引擎缺口）。

这类不是"缺功能"，而是"同一判据有两份代码"，一旦两份漂移就会算错——正是 12.7b（B5④）修过的那一类，也是这次联调"单一权威"主题的遗漏面。

### 9.4 C 类：纯辅助谓词（**不需要接线**，列出以免误判）

以下符号"零调用"是**正常的**——它们是给调用方与测试准备的便利谓词，产品路径内联了等价判断。**不建议**为它们造入口：

`isSuccess` / `isFailure`（产品侧直用 `outcome.ok`）、`nextFloat` / `rollDie`、`modifierTotal`、`legalityFailure`、`isMobileUnit`、`isBefore` / `isAfter`、`movementMpValue` / `attackMod` / `terrainKind` / `tecFeatureNames` / `isHexTerrain` / `isHexsideTerrain`（TEC 单元格读取器；TEC 面板另走数据）、`hasReachedSupplyStep` / `hasReachedBarrageStep` / `hasReachedAirInteractionStep`（步骤到达判定）、`extenderBridgesRailLines`、`describePlacement` / `columnsFor` / `resultTextOf` / `parseResultCell`（文本与解析辅助）。

**建议**：R6① 的架构扫描门禁里加一条"零调用导出清单白名单"——白名单内的允许零调用，白名单外的新增零调用导出即红灯。否则这份清单下次还得人工重扫。
