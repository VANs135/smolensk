## 2. 复审发现

### P1-1（结构）切片宽度失控，解构正在生产新的单体

- 证据：air 3,379 行 / 76 端口；barrage 1,478 / 51；move 40。
- 机理：**端口不是"域的大小"，是"域与外界共享的东西"**。76 项里包含 `pushLog`、`recordSettlement`、`units`、`phase`、`turn`、`activeSide`、`rng`、`selectedId`、`supplyFacts`、`barrageFacts`、`railMoveFacts` 这类**每个域都会用到的公共面**；每切一个域就重抄一遍，端口自然越切越多。
- 后果：切片"可脱离 Pinia 单测"的卖点，被 76 项手工装配抵消；新人改一处要先读 76 行接口。

### P1-2（空军）"域收口"没真收口：状态在切片、原语在 facade

- 证据（facade 声明 ↔ 切片端口）：`acceptAir`（facade 15,939 ↔ `workbench-air.ts:163` 端口）、`setAirStatus`（15,950 ↔ :164）、`markAirMissionFlown`（15,969 ↔ :165）、`drawAir2d6` / `drawAir1d6`、`clearAir`（:237）、`airMissionJoinChoices`（facade 16,285 ↔ :202）。
- 含义：空军域**自己的状态机原语与派生**仍住在 facade，再当端口喂回切片。这就是 76 项的主要来源之一；而 `tasks.md` 记的"空军域六批全部完成"只对"动作块"成立，对"状态归属"不成立。
- 影响：**在拆分 air 之前必须先收口这 24 个残留符号**，否则拆分会把残留分散到两个新切片，端口数据更乱。

### P1-3（防线）spec §8 的机器闸一项都没落地

- 证据：全仓 `max-lines` / `no-restricted-imports` 匹配 **0 处**；`scripts/check-tdz.mjs` **不存在**；`ReinforcementPanel.vue` **1,756 行**（> spec 的 1,600）已既成事实。
- 后果：现在"不回升"靠每批 DoD 的人工纪律；一旦有人赶工，workbench.ts 立刻回涨，且没有红灯。

### P2-1（模型层）`workbench-model.ts` 正在变成新的集散地

- 证据：4,208 行，**105 个 `export function`**；import 了 `@/data`、`@/engine/rules`、`@/render/token-images`；所有切片都 import 它。
- 风险：它同时承担"类型契约 + 纯函数工具 + 资源映射"，下一步很容易变成"什么都往里塞"的第二个 workbench。
- 建议：拆成 `workbench-types.ts`（interface/type，≤1,000）与 `workbench-shared.ts`（纯函数，≤800）；`tokenImageUrl` 这类渲染耦合项回 `@/render`。

### P2-2（流程）每批最贵、最容易错的一步是"回补/解构/`return` 插键"

- 证据：`tasks.md` 里连续三批记了同源事故——TS1117（重复键）、TS6133（解构失效）、漏回补（`beginAirBarrageNow` / `settleAirMissionNow` 只在公开面出现）；`return` 字面量 1,155 行、公开面 1,013 键且测试**精确相等**。

### B3-2b16：搬走 `function` 之后的第三种早读解法 —— **转发箭头**

13.8d「每名工程单位每移动阶段只能施工一次」这一族共 13 声明，物理上是**两段不连续**的代码（`constructionLedgers` … `pickConstructionPayDumpNow` 78 行，`constructionLegRangeTo` … `payConstructionFee` 104 行），中间夹着一个 `constructionInputs` —— 它被 B27a 的 `beginAirBaseHexPickNow` 早读（点地图写 `hexText`）、又是切片 deps 要吃的输入，按 b14 的招法**剪出来前移**（插在 `} = hedgehogsDomain` 之后），facade 保留声明、切片按端口收，端口 21 = 8 依赖 + 13 返回。

本批的难点在**反方向**：这 4 个函数（`engineerExecutorFor` / `constructionGateNow` / `noteConstruction` / `payConstructionFee`）是 C8f（`createHedgehogsDomain`@≈1765）的 deps 实参，而本切片的装配点在 C8b banner 之前（≈2152）。搬走前它们是 `function` 声明（提升 ⇒ 早引用天然安全）；搬走后 facade 侧变成 `const { … } = constructionDomain` 解构，**提升消失** ⇒ `vue-tsc` 直接报 TS2448/TS2454 八条。

两种解法都不要踩：

1. **getter 不行**。`get engineerExecutorFor() { return engineerExecutorFor }` 能让 typecheck 全绿，但单测整片炸——`createHedgehogsDomain` 是**建域时按值取** deps（切片头部 `const { …, engineerExecutorFor, … } = deps`），getter 在 1765 那一刻被立即求值，此时 const 还没赋值 ⇒ `ReferenceError`（首次 `npm run check` 得 2,313 条**用例**失败（361/624 个文件））。
2. **正解是转发箭头**：`engineerExecutorFor: (engineer, target) => engineerExecutorFor(engineer, target)`（其余三项同形，按 `HedgehogsDeps` 的签名逐参转发）。deps 取到的是箭头本身，闭包引用留到调用期解析 ⇒ 零 TDZ、零行数损失（4 行 getter 变 4 行箭头 + 2 行说明注释）。

**判别口径（第三种早读解法，按代价排序）**：早装配点 × 晚声明 `const` × **调用期才消费** ⇒ 转发箭头；若 deps 在**建域时就要调用**（不是存起来），箭头也救不了，回到 b14 的前移装配点；再退一步才是 b10/b12 的留项。

索引与对拍的两处坑：① `constructionInputs` 的注释是**单行** `/** … */`，按"向上找 `  /**` 起行"会落到上一段的 banner，随后 12 行窗口扫不到尾 ⇒ 定位一律用语义标记（`/** 15.3 / 15.2A 的玩家输入`）；② R1 归一化要额外做两件事——head 侧把 4 行转发箭头还原成 4 行简写、删装配段时**从 banner 行起删**（不可连它前面的空行一起删，否则基线整体错位 1 行，差异会假报成上万条）。

### B3-2b13：只 return「别人要用的」，内部 helper 留在切片里

C8e 的 7 个声明里，`convertibleTransportPointsAt` 与 `extenderRecordFor` 只被切片内部的
`convertTransportToExtenderNow` 调用（全仓库再无第二个消费者）⇒ 它们**不 return、facade 也不解构**，
端口宽度与公开面都不受影响。判别口径：搬移后逐个查"块外是否还有消费者"，没有就不要往 return 里塞。

同批的写入式端口：9.14d 主动崩溃要把**整个待办对象**写进 `specialPending`（facade 里是晚于本域装配点的
`ref`），这属于 b11 那条"晚声明 `ref` 只要函数体里出现赋值就走回调"的第二种形态（b11 是整体重置成
`{}` / `[]`，这里是整体写入一个对象）⇒ 端口给 `setSpecialPending(value)`，切片内把
`specialPending.value = {...}` 改成 `setSpecialPending({...})`（同一对象、同一时机，R1 里作为唯一允许差异记 2 行）。

### B3-2b12：区块里可能只允许搬一部分（留项占位、其余照搬）

C8d 是 253 行的连续区块（含 banner 与前后两个空行；纯声明区 250 行），但 8 个一级声明里

`retreatResolutionInput` 同属"被早读者"。**处理**：把它**留在原位**（facade 仍声明它，早读者零改动），
切片通过端口反向收一个 `transportKindOf: (unit) => string`；于是区块被搬成两段，实搬
**246 行 = 声明区 250 − 留项 4**（`transportKindOf` 的注释 + 函数），函数体**零改写**。

判别顺序因此固定为：**先按"是否被早读者占用"逐声明筛一遍，再切区块** —— 不要先按 banner 切块、
后面才发现某个 helper 必须留。b12 的 `transportRecordFor` 虽然也被 C8e（12.7 延补队转换）在 3 处调用，

### B3-2b11：`ref` 被**写穿**时不能给 getter，要给回调

C8 的 SP 账本整块（265 行）里，三个晚声明状态本可按 b10 的招法制裁，但只有 `panzerGroupRulesOn`
（3.4b 段的 computed）是"只读"，照旧给 getter + 切片内 `computed(() => deps.xxx())` 包装即可。
另外两个是 `ref` 且本块**不是只读而是整体重置**：

- `spDumpPanzerGroups`（同段，`Ref<Record<string, PanzerGroup>>`）—— `resetSpDumpPanzerGroups` 里 `= {}`；
- `pendingSpGroupAssignment`（同段，`Ref<string[]>`）—— `resetPendingSpGroupAssignment` 里 `= []`。

getter 交出去的是**值**（`Ref<SpDump[]>` 的 `.value` 快照或只读包装），赋值写不回去；`computed` 包装更不行。
**结论（新招法）**：给回调 —— 装配处写 `resetSpDumpPanzerGroups: () => { spDumpPanzerGroups.value = {} }`，
切片里把 `spDumpPanzerGroups.value = {}` 改成 `resetSpDumpPanzerGroups()`。回调在**调用时**才求值，
所以晚声明不构成 TDZ。判别口径加一条：**晚声明 `ref` 只要函数体里出现赋值，就走回调而不是 getter**。

同批的第二条硬约束：装配点必须**前移到 C8 段开头（air 域装配之前）**。因为 `addSpAtHex` 是 air 域的
端口、`setSpDumpHoldings` 也被紧随其后的一个域收走 —— 这是 b10 反向端口的镜像情形：**被更早的建域点
收走的函数，本域必须排在收它的域之前**。凡这类前移，切片头注释要写清"为什么装配不在 7xxx"。

口径说明：本节的定位一律按**符号名**（`const airDomain = createAirDomain`、`function requireAction`、
3.4b 段的 `computed`/`ref`），不写裸行号 —— 行号随每批搬移漂移（b11 自身就带 +37，b12 又带 −455）。

### B3-2b10：被建域点"之前"读取的函数只能留在 facade（反向端口）

9.12 的三件本可按 10334–10543 整块搬，但 `retreatResolutionInput`（10379）被 facade **3258/3268**
的 computed（9.12e 承受者候选预演）读取 —— 那些 computed 远早于任何建域点。一旦把它搬进切片、
而切片又要在 7xxx 建域，computed 就落到 TDZ。**结论**：这类"被早读者"不能搬，只能把切片切成
两段不连续区块（b5+b6 的同款手法），并把留在 facade 的函数**反向**当端口传进去（20 项里的一项）。

同批固化两条口径：

1. **`ref` 晚声明 vs 函数晚声明**：`specialPending`（14466，`ref`）只能给 getter 并在切片内
   `computed(() => deps.specialPending())`；`confirmCombatAdvance`（10573）、
   `settleOverrunAdvanceIfRequired`（14888）是函数声明 ⇒ 直接按值传。
2. **接收者改写要记账**：A1 末尾 `fireResolution.scheduleRetreatCrossings(...)` 改成端口调用；
   端口是装配处的闭包，仍打同一个 `fireResolution` 实例。凡"为不吃整个对象而只传一个方法"的改写，
   必须在切片头注释逐条写明，R1 断言时把它作为**唯一允许的差异**。

### B3-2b9：装配顺序成了硬约束（端口在切片之前建域）

b8 把 `confirmCombatOptions` 当端口收进 `combatIgnoreDomain`。b9 把它搬进 `combatSettleDomain` 后，
