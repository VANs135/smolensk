# 并发冲突治理方案（2026-11-21）

> 目标不是「让 workbench.ts 变小」，而是「让两路并行改动不再撞在同一处」。
> 本文的所有数字都是在 `refactor/workbench-decouple`（HEAD `51f9c9b`）上实测的。

## 0. 一句话结论

冲突不是由「文件 23,000 行」引起的，而是由「**每次改动都要在同一份 1,005 键的 return 列表、同一处装配点上登记一次**」引起的。实测：最近 60 个提交中改过 facade 的 feat/fix 共 **21 个**，其中 **14 个（67%）动 return 区**、8 个（38%）动装配区。而 return 里 **722 个键（71.8%）根本不是任何域的产物**，是 facade 本地状态 —— 所以「return 改成 spread」只能覆盖 28.2%，不足以解决冲突。本方案改为**把域落成独立的 Pinia store，facade 退化成兼容投影层**，让功能改动落在各自文件。

## 1. 证据

### 1.1 冲突落点（近 60 提交 / 改过 facade 的 21 个 feat-fix）

| hunk 落点                  | 命中提交 | 占比 |
| -------------------------- | -------- | ---- |
| return 区（`≥21000` 行段） | 14       | 67%  |
| 装配区（`<3200` 行段）     | 8        | 38%  |
| 中间业务区（3200–21000）   | 17       | 81%  |

典型样本（按 hunk 计）：

- `b63fbca`（1.6c 改独立掷骰）：9 个 hunk，**9 个全在 return 区**，中间区 0 个 —— 这个提交几乎只做了一件事：给 store 加新入口。
- `c25cfc5`（全局撤销）：36 个 hunk，10 个在 return 区。
- `76842d6`（结束移动即提交）：25 个 hunk，9 个在 return 区。

即：**「新增一个入口」这个动作本身，就要回到公共列表里插一行**。两路并行做不同功能时，各自都要插一次，冲突不可避免。

### 1.2 return 区构成（脚本口径）

| 项                                        | 数量             |
| ----------------------------------------- | ---------------- |
| return 键（脚本识别的逐名行）             | **1,005**        |
| 其中来自 `createXxxDomain` 解构           | **283**（28.2%） |
| 其中 facade 本地定义（ref/computed/函数） | **722**（71.8%） |

本地键样例：`activeSide`、`phase`、`turn`、`units`、`log`、`rng`、`selectedId`、`moveInteraction`、`battleTarget`、`pendingRecord`、`saveBlockedReason` …

> 口径差异说明：公开面快照测试记的是 1,013 键，脚本逐名行只识别到 1,005（另有 8 项以别名/展开形式书写）。差异待 P0 用映射表逐项对齐，不影响本方案的判断。

### 1.3 结论的推论

1. **继续把 air 从 63 压到 40 对冲突零收益**：air 的内部行数不在冲突路径上；在路径上的是「新动作要在 return 区登记」。
2. **只改 return 为 spread 也不够**：最多省掉 283 行，仍剩 722 行本地键在同一列表。
3. 真正的串行点是：**新增/改名一个键，必须编辑同一份公共列表**。要消除它，只能让「键不再集中登记」。

## 2. 新方案：域级 store + 兼容投影（渐进、可回滚）

### 2.1 结构

```
src/stores/root-store.ts     # 根状态：activeSide / phase / turn / units / log / rng / selectedId …
src/stores/air-store.ts      # 空军（内部继续调用现有 createAirDomain 等工厂）
src/stores/move-store.ts     # 移动
src/stores/combat-store.ts   # 战斗
src/stores/supply-store.ts   # 补给
...
src/stores/workbench.ts      # 兼容投影层：逐键 getter 转发 + 既有导出不变
```

- **域间只允许单向读根**：`air-store` 的 action 内部 `useRootStore()`（惰性调用，避开 b20 那类 TDZ 事故）；**禁止域 store 之间互相 import**，确需跨域读就走根状态或回调注入。
- **兼容投影**保留 `useWorkbenchStore()` 的全部语义：组件、引擎测试、6,257 条用例一行不用改。

### 2.2 兼容投影的两种写法（建议前者）

- **显式 getter**（推荐）：`get airState() { return airStore.airState }`。类型可推断、可单测、可 grep。
- `Proxy`：省行数但丢失静态类型与可读性，不推荐。
- 投影层还应提供 `$patch`/`$reset`/`storeToRefs` 的等价路径（Pinia 的 `storeToRefs` 直接作用于域 store，组件侧不受影响）。

### 2.3 阶段划分（每阶段一个 commit，均可单独回滚）

**P0 账本（0.5 天）**

- 产出：迁移顺序表（按「键数 × 改动频率」排序，air/move 优先）。

**P1 试点（2–3 天，选 air）**

- `workbench.ts` 把 air 相关键改为 getter 转发；air 的 63 项 deps 逐步换成「域 store 内部直接 `useRootStore()`」，**端口棘轮就此冻结，不再下调**。

## 3. 立即停止做的事

1. **不再为「端口 ≤40」硬拆 air**——已证明不在冲突路径上，且会把语义边界切碎。

### 4.4 P1 设计定稿：三个硬约束（实测，不可绕过）

开工前实测确认了三条会让「air 直接变 Pinia store」当场失败的事实。它们决定了 P1 必须拆成 a/b/c 三步，不能一步到位。

**约束 1：Pinia store 解构会丢响应性。**
`defineStore` 返回的实例是 reactive 代理，读属性时自动解包 `.value`。facade 现有写法是 `const { airState, airError, ... } = airDomain`（155 行逐名解构）。一旦 `airDomain` 换成 store 实例，这 155 行拿到的全是**当前值快照**，`airState` 不再是 ref，watch/模板全部失效。
⇒ 只能二选一：要么改为 `storeToRefs(airDomain)`（155 行全改），要么全部改为 `airDomain.airState` 直引（facade 内所有引用点，量级上千）。
⇒ 结论：**P1 不得让 `airDomain` 变成 Pinia 实例**，否则整个 facade 的解构区必须同时重写，无法单独回滚。

**约束 2（P1-c 已修正）：spread 的响应性代价只对 Pinia store 成立。**
初稿曾断言「`...airDomain` 展开同样丢响应性、不能用 spread 简化 return 区」，那是把约束 1 的结论错套到了普通对象上。air 域返回的是**普通对象**、其值是 ref，spread 得到的是**同一批 ref 引用**，响应性不丢、`ReturnType` 推断也不退化。P1-c 即用一行 `...airDomain.publicSurface` 落地，公开面快照（1,013 键）与 6,257 用例全绿。
只有当域被包成 `defineStore` 实例时，读属性才会解包成值快照，那时才必须 `storeToRefs` 或逐名直引。⇒ **P2 模板：域保持普通对象 + 域内 `publicSurface` 清单 + facade 一行 spread。**

**约束 3：Proxy 转发会丢掉 1,013 键的类型。**
用 `new Proxy` 让 return 动态转发各域，确实能做到「新增域键无需改 facade」，但 `typeof store` 会退化为索引签名，组件与 6,257 用例的类型检查资产一并失效。⇒ 已否决（与 §4.1「不用 Proxy」一致，此处补充了类型维度理由）。

**由三个约束得出的正确顺序（P1-a / P1-b / P1-c）：**

- **P1-a（先行，低风险）**：新建 `src/stores/root-state.ts`，用**普通模块工厂**（`createRootState()` 返回含 ref 的普通对象，**不是** `defineStore`），先搬 3 个纯根 ref：`units` / `selectedId` / `pendingRecord`。facade 里删掉这 3 行声明、改为 `const { units, selectedId, pendingRecord } = rootState`——普通对象解构得到的就是**同一个 ref 对象**，读写与响应性零变化，6,257 用例应全绿。
  目的：验证「根状态搬出 facade、靠引用共享维持语义」这条路本身成立，而不引入任何 Pinia 语义风险。
- **P1-b**：把 air 的 63 项 deps 里来自根状态的部分（`activeSide`/`phase`/`turn`/`units`/`rng`/`pushLog`/`selectedId`…）改为从 `root-state` 取；air 仍由 facade `createAirDomain(ports)` 建域，**ports 形状不变**，只是取值来源换了。此步对 facade 的 return 区零影响。
- **P1-c（唯一动响应性的一步，必须独立 commit + 独立回滚）**：air 才变 `defineStore('air')`；同时把 facade 的 155 行逐名解构改为 `airDomain.x` 直引或 `storeToRefs`，并用 `tests/stores/workbench-public-surface.test.ts` 快照核对键集合不变（1,013）。

**验收**：a/b/c 每步单独 `npm run check` 全绿、单独 commit。任一步不绿即回滚，不带病前进。

**本轮基线（已确认）**：`npm run check` 全绿——`Tests 6257 passed (6257)`、`架构扫描通过：组件 58 / 样式 62 / 源码 973`、退出码 0。此前连续 EPIPE/OOM 失败的真因是 C 盘可用空间耗尽（84 MB），清理后一次通过。

### 4.5 根状态的边界：纯本地 ref vs session 投影（P1-b 实测）

搬第二批时逐行查了 `workbench.ts` 795–945 的声明，结论推翻了我自己写在 §4.3 的假设：「根状态」里看着像纯状态的那批，实际全都会话投影。

- `activeSide`：`computed({ get: () => session.records?.activeSide ?? localActiveSide.value, set: … session.patchRecords({ activeSide }) })` —— 读写都过 session。
- `phase`：同上，外加 `consolePhaseOf()` 把 `turnEnd` 折成 `cleanUp`。
- `turn` / `date`：同上；`date` 由 `turn` 派生（`turnDateOf`），不是独立状态。
- `seed` / `rng` / `drawCount`：读 `session.session.state.rng`，写走 `session.setSessionRng`；`rng` 的 setter 还要 `detectDraw()` 把本次推进还原成骰子塞进 `pendingRolls`。
- 真正纯的：`units` / `selectedId` / `pendingRecord` / `tool` / `log` / `lastStep` / `lastBattle` —— 纯 `ref`，无会话耦合，已全部搬入 `root-state.ts`（7 项，P1-a 3 项 + P1-b 4 项）。

由此得到三条改变排期前提的结论：

1. **`root-state` 能承接的只有纯本地 ref，且已经搬完。** 它不是「82 键的家」，只是一个 7 项的小容器。
2. **`session` 适配层是第二个不可拆的核心**（第一个是 facade 装配点）。`activeSide`/`phase`/`turn`/`seed`/`rng` 必须与它同域，不能独立成 store。⇒ P2 里 `root(82)` 这一批要按此口径重估：真正可搬的远少于 82，大部分是会话投影与根级函数，实际只能整块留在 facade 或整体抽成 `session-domain`。
3. **air 的 63 项 deps 中来自根投影的那批不能改指向 `root-state`。** P1-c 之后，air 仍须由 facade 注入这些端口。因此 `air-store` 必须走**端口注入**（facade 先 `setAirPorts(...)` 再 `useAirStore()`），**不得**在 air 内部 `useWorkbenchStore()`——否则 workbench ↔ air 形成 store 循环依赖，Pinia 初始化时拿不到对方。这点写进 P1-c 的硬约束。
