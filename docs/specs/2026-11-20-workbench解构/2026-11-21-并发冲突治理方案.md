# 并发冲突治理方案（2026-11-21）

> 目标不是「让 workbench.ts 变小」，而是「让两路并行改动不再撞在同一处」。
> 本文的所有数字都是在 `refactor/workbench-decouple`（HEAD `51f9c9b`）上实测的。

## 0. 一句话结论

冲突不是由「文件 23,000 行」引起的，而是由「**每次改动都要在同一份 1,005 键的 return 列表、同一处装配点上登记一次**」引起的。实测：最近 60 个提交中改过 facade 的 feat/fix 共 **21 个**，其中 **14 个（67%）动 return 区**、8 个（38%）动装配区。而 return 里 **722 个键（71.8%）根本不是任何域的产物**，是 facade 本地状态 —— 所以「return 改成 spread」只能覆盖 28.2%，不足以解决冲突。本方案改为**把域落成独立的 Pinia store，facade 退化成兼容投影层**，让功能改动落在各自文件。

## 1. 证据

### 1.1 冲突落点（近 60 提交 / 改过 facade 的 21 个 feat-fix）

| hunk 落点                  | 命中提交 | 占比 |
| -------------------------- | -------- | ---- |
| return 区（`≥21000` 行段） | 14       | 67%  |
| 装配区（`<3200` 行段）     | 8        | 38%  |
| 中间业务区（3200–21000）   | 17       | 81%  |

典型样本（按 hunk 计）：

- `b63fbca`（1.6c 改独立掷骰）：9 个 hunk，**9 个全在 return 区**，中间区 0 个 —— 这个提交几乎只做了一件事：给 store 加新入口。
- `c25cfc5`（全局撤销）：36 个 hunk，10 个在 return 区。
- `76842d6`（结束移动即提交）：25 个 hunk，9 个在 return 区。

即：**「新增一个入口」这个动作本身，就要回到公共列表里插一行**。两路并行做不同功能时，各自都要插一次，冲突不可避免。

### 1.2 return 区构成（脚本口径）

| 项                                        | 数量             |
| ----------------------------------------- | ---------------- |
| return 键（脚本识别的逐名行）             | **1,005**        |
| 其中来自 `createXxxDomain` 解构           | **283**（28.2%） |
| 其中 facade 本地定义（ref/computed/函数） | **722**（71.8%） |

本地键样例：`activeSide`、`phase`、`turn`、`units`、`log`、`rng`、`selectedId`、`moveInteraction`、`battleTarget`、`pendingRecord`、`saveBlockedReason` …

> 口径差异说明：公开面快照测试记的是 1,013 键，脚本逐名行只识别到 1,005（另有 8 项以别名/展开形式书写）。差异待 P0 用映射表逐项对齐，不影响本方案的判断。

### 1.3 结论的推论

1. **继续把 air 从 63 压到 40 对冲突零收益**：air 的内部行数不在冲突路径上；在路径上的是「新动作要在 return 区登记」。
2. **只改 return 为 spread 也不够**：最多省掉 283 行，仍剩 722 行本地键在同一列表。
3. 真正的串行点是：**新增/改名一个键，必须编辑同一份公共列表**。要消除它，只能让「键不再集中登记」。

## 2. 新方案：域级 store + 兼容投影（渐进、可回滚）

### 2.1 结构

```
src/stores/root-store.ts     # 根状态：activeSide / phase / turn / units / log / rng / selectedId …
src/stores/air-store.ts      # 空军（内部继续调用现有 createAirDomain 等工厂）
src/stores/move-store.ts     # 移动
src/stores/combat-store.ts   # 战斗
src/stores/supply-store.ts   # 补给
...
src/stores/workbench.ts      # 兼容投影层：逐键 getter 转发 + 既有导出不变
```

- **域间只允许单向读根**：`air-store` 的 action 内部 `useRootStore()`（惰性调用，避开 b20 那类 TDZ 事故）；**禁止域 store 之间互相 import**，确需跨域读就走根状态或回调注入。
- **兼容投影**保留 `useWorkbenchStore()` 的全部语义：组件、引擎测试、6,257 条用例一行不用改。

### 2.2 兼容投影的两种写法（建议前者）

- **显式 getter**（推荐）：`get airState() { return airStore.airState }`。类型可推断、可单测、可 grep。
- `Proxy`：省行数但丢失静态类型与可读性，不推荐。
- 投影层还应提供 `$patch`/`$reset`/`storeToRefs` 的等价路径（Pinia 的 `storeToRefs` 直接作用于域 store，组件侧不受影响）。

### 2.3 阶段划分（每阶段一个 commit，均可单独回滚）

**P0 账本（0.5 天）**

- 脚本生成「1,005 键 → 归属 store → 迁移批次」CSV，落 `docs/specs/…/key-ownership.csv`。
- 在 `workbench.ts` 的 return 区按来源插入分段注释（域键 / 本地键 / 待定），不改逻辑。
- 产出：迁移顺序表（按「键数 × 改动频率」排序，air/move 优先）。

**P1 试点（2–3 天，选 air）**

- 新建 `air-store.ts`，内部复用现有 `createAirDomain` 等工厂（不重写逻辑）。
- `workbench.ts` 把 air 相关键改为 getter 转发；air 的 63 项 deps 逐步换成「域 store 内部直接 `useRootStore()`」，**端口棘轮就此冻结，不再下调**。
- 验收：air 相关用例全绿；公开面键集合零变化；`npm run check` 全绿。

**P2 批量（每域 0.5–1 天）**

- 按 P0 账本顺序迁移：move → combat → supply → fuel → barrage → 其余。
- 每批结束从 `workbench.ts` 删除对应逐名行，投影层同步补齐。

**P3 收口**

- `workbench.ts` 只剩投影（预计 <500 行），return 区消失。
- `max-lines` 大幅下调；`over40Exempt` 随「端口随域下沉」自然废止。

**P4 可选（服务体验优化）**

- 组件改 `useAirStore()` 直接取域视图，删投影层。这一步才是真正服务「优化玩家体验」的部分，放在最后做，避免与迁移混在一起。

### 2.4 与既有纪律的关系（需要明确改写）

| 既有纪律                                | 新方案下的处理                                                           |
| --------------------------------------- | ------------------------------------------------------------------------ |
| 公开面 1,013 键零漂移                   | **保留**，作为投影层验收硬指标（迁移期逐批比对）                         |
| 切片端口硬上限 40                       | **废止**为硬指标，改「只降不升 + 说明理由」；域 store 化后端口自然消解   |
| facade `max-lines` 每批下调（实测 + 5） | **保留**，但只对「确实减小」的批次下调；投影层行数会增加，需单独一档上限 |
| 每批单 code + 单 doc commit             | **保留**                                                                 |
| 注释/文档按符号名定位                   | **保留**                                                                 |

### 2.5 风险与对策

| 风险                                 | 对策                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 域 store 循环依赖                    | 只允许「域 → 根」单向；跨域读走根状态或回调，禁止互相 import；P1 用 `check-arch` 增加一条规则扫描 |
| 建域时 TDZ（b20/b21 事故同源）       | **域 store 的 setup 里不读其他 store**，只存工厂返回的域对象；读取一律在 action 内惰性调用        |
| 投影层与域 store 键不一致            | 新增测试：域 store 键集合 ∪ = 投影层键集合，双向断言（等价于现有快照测试的升级版）                |
| 6,257 用例依赖 `useWorkbenchStore()` | 投影层完全保留原签名与返回类型，用例零改动；P4 才动组件                                           |
| 双份状态（迁移期同时存在）           | 迁移期只允许一处为「真源」：域 store 持有，投影层纯 getter，禁止投影层写回                        |
| 性能                                 | Pinia 实例缓存 + getter 转发，无深拷贝；风险可忽略，P1 后跑一次全量用例即可确认                   |

### 2.6 验收判据（可量化）

1. **冲突面**：连续 5 个 feat/fix 提交中，改到「公共 return 列表」的数量 = **0**。
2. **并行度**：两路并行改动（同一周内两支分支）rebase 时无需人工重排 return 区。
3. **规模**：P3 后 `workbench.ts` < 500 行；每域 store 文件 < 1,200 行。
4. **闸门**：`npm run check` 持续全绿，用例数不减（6,257）。

### 2.7 排期

| 阶段                | 工期          | 产出                                    |
| ------------------- | ------------- | --------------------------------------- |
| P0 账本             | 0.5 天        | `key-ownership.csv` + return 区分段注释 |
| P1 air 试点         | 2–3 天        | `air-store.ts` + 投影 + 端口冻结        |
| P2 批量             | 每域 0.5–1 天 | 逐域迁移，facade 逐批瘦身               |
| P3 收口             | 1 天          | 投影层 <500 行，return 区消失           |
| P4 组件切换（可选） | 待评估        | 组件直连域 store                        |

## 3. 立即停止做的事

1. **不再为「端口 ≤40」硬拆 air**——已证明不在冲突路径上，且会把语义边界切碎。
2. **不再以「facade 行数下降」为目标**——装配与投影开销会抵消，行数不是维护成本的代理指标。
3. **不再把「新增 b2x 切片」当默认动作**——除非它同时能把对应键从公共列表里摘掉。

## 4. 已定决定与 P0 结果

- 试点域：**air**（155 键，体量最大、改动最频）。
- 投影层写法：**显式 getter**（类型可推断、可单测、可 grep）。
