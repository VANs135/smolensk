## 1. 语义等价核对（挑有风险的 8 处）

1. **`clearBarrage` 不清阶段账本**：函数体原样迁出，`barragedHexesThisPhase` / `barragedUnitIdsThisPhase` 仍只在 `resetSegmentTransient` 清 —— 守卫测试 ⑤ 与 ② 均绿。
2. **`acceptBarrage` 泛型**：`<T>(outcome: RuleOutcome<T>, action: string): T | null`，转发壳保留类型参数，`fireResolution` 的 `acceptBarrage` 端口按原签名接收。
3. **`applyBarragePatches` 用 `units.value.find` 就地改**：`units` 以 `Ref<ConsoleUnit[]>` 传引用（不是快照），语义不变。
4. **`barrageSupplyDumpId` 等 18 个账本/派生**：迁进切片后**是同一批 ref/computed 实例**（切片创建一次、facade 解构同一对象），所以 `return` 暴露的仍是同一个 `ComputedRef`，UI 侧 `workbench.barrageShellPreview` 的引用身份未变。
5. **`barrageAutoOpened`**：唯一"非 ref 跨切片状态"。改为 getter/setter 槽对象，`setBarrageActive` 里那一行改写成 `autoOpened.value = false`；facade 24625 / 24718 两处读法**未动**，语义（一次性裸标志、不进响应式）不变。
6. **域对象解构**：`barrageState` / `barrageError` / `barrageInputs` / `combatState` / `combatError` 从 `deps.fireResolution` 解构，`airError` 从 `deps.airMissionDomain` 解构 —— 切片不认识域，避免"轰炸切片 import 战斗域切片"的新环。
7. **装配顺序**：`const barrage = createBarrageDomain({...})` 落在 `return {` 前 2 行。实测 13 个依赖声明在 24k–29k 行（`segmentStep` 24,4xx / `segmentGateQuery` 24,4xx / `supplyCacheHoldings` 28,4xx / `trainbustingMarks` 28,6xx …），任何早于它们的装配都会在 setup 期读 `undefined`。
8. **转发壳与裸引用**：`createFireResolutionDomain` 在 1909/1917/1919/1921 把 `acceptBarrage` / `applyBarragePatches` / `applyBarrageFacilityPatch` / `barrageFacilityFacts` 及 2446 的 `deliverableDumpsFor` **裸传**。这 5 处是 setup 期立即求值的，因此这些动作必须留**提升的函数声明**（不能改成 `const {} = slice`，否则 TDZ）。这也是 B1 用 3 行壳而不用一行解构的原因。

## 2. 发现

### P2-1 类型环又宽了一点（B0 的 P2-1 现在有第二个消费者）

切片新增 `import type { ConsolePhase, BattleTarget } from './workbench'` —— 这两个类型只住在 facade 里（`workbench.ts:631` / `:809`）。
**这不是新问题，是同一笔债的第二次计息**：B0 的 `workbench-core.ts` / `workbench-gates.ts` 已经反向 type-import 了 `ConsolePhase` / `WorkbenchLogEntry` / `SettlementLock`。现在有 3 个切片在等同一件事。
**建议**：把「facade 自有的共享类型」一次性搬进 `workbench-model.ts`（`ConsolePhase` / `BattleTarget` / `WorkbenchLogEntry` / `SettlementLock` / `SettlementRecordInput` 一并），facade 侧 `export type { … } from './workbench-model'` 保持既有导入路径。约 60 行搬运、零行为变化，**建议排在 B2 之前**（B2 的空军切片几乎必然还要引 `ConsolePhase`）。

### P2-2 转发壳的行数成本随函数数线性增长（影响 B7 可行性）

B1 付出了 114 行壳（38 个动作 × 3 行）。按这个斜率，B7 的 162 个函数 ⇒ **486 行壳**，而 B7 的目标是把 facade 压到 ≤ 1,500 行级别——壳本身就会吃掉三分之一预算。
**可选优化（已写进 spec §6）**：只有被 setup 期立即求值的动作需要提升的函数壳（B1 实测只有 5 个），其余可以在装配点一行 `const { a, b, … } = slice` 集体绑定。函数数 < 40 时省不到 30 行，B7 能省 400+ 行。**建议从 B2 起就用这个做法**，B1 不改（已绿地、且改动会污染"纯搬移"的 diff）。

### P2-3 源码守卫从"钉文件"变成"钉文本顺序"

35 处 `readFileSync('src/stores/workbench.ts')` 已改成 `readStoreSource()`（facade + 全部 `workbench-*.ts`）。但守卫普遍是 `source.indexOf('function X')` 截函数体 —— **顺序敏感**：若 facade 排在切片前面，`indexOf` 会先命中 `function X(...) { return barrage.X(...) }` 这层壳，断言随之中假红（本次实测有 2 个用例这样红过）。
已在 helper 里把"切片在前、facade 在后"写成注释并说明原因。**残留风险**：将来若某个切片里的实现与 facade 里的另一个同名函数撞名，守卫会静默指向错误的那一处。彻底解法是让守卫按「文件 + 函数名」定位（`readStoreFunction('x')`），但那是 30 个测试的重构，留到有实际误伤时再做。

### P2-4 `BarragePorts` 51 项，超出 `AirMissionPorts`（17 项）的标尺 3 倍

一个 1,212 行的切片需要 51 个端口，说明**"按分节切"在超过千行时会逼近端口爆炸**。B7（6,738 行）若照此办理会需要 200+ 端口，根本没法维护 —— 好在 B7 的方案本来就是拆 4 个子切片（`segment-gate` → `placement` → `spec-rules` → `victory`），那 4 个各自只需要十来项。
**给 B3–B6 的判据**：单个切片的 `BarragePorts` 式端口若超过 **40 项**，就该考虑再拆一刀，而不是硬塞。

### P3

- **P3-1** `import type { createFireResolutionDomain } from './fire-resolution'` 只为 `ReturnType<typeof …>` 服务，读起来别扭（type-only 引入值再做 `typeof`）。等 P2-1 那批类型集中后，建议把这几个 `ReturnType<typeof 域工厂>` 换成由 model 层导出的具名类型。
- **P3-2** `bestDefenderTerrainLine` 现在只被切片内部用、但仍在切片的 `return` 里导出。留着没错（将来 UI 可能要它），但要知道 facade 已不再有这个函数名 —— 任何按名调 `workbench.bestDefenderTerrainLine` 的地方会静默 `undefined`（公开面测试只冻结 facade 的 `return` 键，这一项本来就不在 1,013 键里，所以测不到）。

## 3. 结论与下一批预测

- **B1 成立**：这次比 B0 更能说明模板可复制 —— B0 搬的是"服务"（6 个函数），B1 搬的是"一整个环节的 39 个动作 + 18 个账本"，调用点仍然**零改动**。
- **B2 预测**：section 10（560 / 16）+ section 11（999 / 22），逻辑函数约 38 个。按修正后的公式：1,559 − 3×38 − 60 ≈ **净降 1,385**，`workbench.ts` 应落在 **≈29,690 ± 100**。若 B2 采用 P2-2 的一行解构方案，可再省约 99 行（≈29,590）。
- **B2 之前建议先做 P2-1**（60 行类型搬运）：它不改变行数、不加端口，但能让后续 6 个切片不再往类型环里再加一笔。
