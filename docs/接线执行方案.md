## 1. 关键发现：接线被一个地基卡住

**12.6 追溯补给的「逐单位结论」在实机里从未被评估，因此 `hasTraceSupply` 恒为真。**

要说清"已经有什么、缺什么"，避免把工程量估错：

**已有（不要重建）**：

- `stores/workbench.ts:1837` 与 `:1858` 已经构造了追溯事实 `supplyFacts` / `zocOnlySupplyFacts`（经 `createSupplyFacts` → `engine/rules/trace-supply.ts` 的 `createTraceSupplyFacts`），素材取自 SP 账本（dumps）、摆好的 HQ、延补队、玩家声明的 12.6a① 源，以及 13.3c 派生的火车卸货格；
- 这些事实已被 **12.3a/b 的直接拖取与投递距离**可达性、以及 `railSupply` 派生所消费。

**缺的（本项要做的）**：

- `assessUnitSupply`、`hasTraceSupply(facts, …)`、`planOutOfSupply` 这三个**逐单位评估入口在 `src/stores/**` 与 `src/components/**` 里零调用**（已逐名核对）；
- 于是 `stores/workbench-model.ts:282` 的 `hasTraceSupply: true` 是**唯一的赋值来源**，全仓没有任何一处写入 `false`；
- `stores/workbench.ts:6271` 的 `hasTraceSupplyAt: () => true` 是同一问题的另一处表现。

也就是说：**事实层已经建好，缺的是"拿事实去问每个单位"这一步，以及把结论落盘。** 这比从零构造事实小得多。

**后果是一整片规则空转**，不只是"某一项没接线"：

| 依赖逐单位 `hasTraceSupply` 的规则         | 位置                                                                       | 当前实际行为                                                                                |
| ------------------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 12.8d 断补单位战斗值 ×½                    | `battle.ts:434`                                                            | 永不生效（永远"有补给"）                                                                    |
| 12.8d 断补单位不投射 ZOC                   | `zoc.ts:56-67`                                                             | 永不生效                                                                                    |
| 12.8a/12.8b 补给阶段断补清单与逐回合损耗骰 | `supply-phase.ts`                                                          | 永不出清单、永不掷损耗                                                                      |
| **12.8e 突围的前提**                       | `breakout.ts:143` `if (unit.hasTraceSupply) return fail(...)`              | **永远为真 ⇒ 突围永远不可能触发**（这才是"漏项"的真实程度：不是没接线，是逻辑上不可能发生） |
| 5.8b 战略模式须在有追溯补给的格结束移动    | `move.ts:414`                                                              | 钩子未注入 + 判定恒真 ⇒ 双保险失效                                                          |

**因此 P1 的第一项不是任何一个"功能"，而是把逐单位追溯补给评估接上。** 它一次性解锁上表七条，也是突围能被"真正实现"的前提。

## 4. 逐项定义完成

每项按 §0.1 四判据写清落点。下面给出 P1 四项的细则，P2/P3 在执行时按同一模板补。

### 4.1 P1-3 突围（唯一的 B 类，先补引擎）

**引擎缺的一环**：`canBreakout` 要求调用方传入 `conditions: { path: BreakoutPathFacts, nearestTracedCombatFriendDistance }`，但**没有任何地方计算它**。

- **12.8e-A 的路径条件**（"长度任意的路径，沿途无敌方战斗单位、无移动禁入地形〔按移动模式的 MA 类型〕、轮式另需无未被抵消的 EZOC"）需要一次专用搜索。**不能**复用 `move.ts` 的 `evaluateStepFrom`——那里有 MP 预算与阶段额度判定，而 12.8e-A 明确"长度任意"。
- 落点：`engine/rules/breakout.ts` 新增 `computeBreakoutConditions(...)`，复用既有原语 `map.terrainsAt` / `crossingBetween` / `selectMovementTerrain`（只取 prohibited 结论）/ `zoc.ts` / `hexDistance`；事实（敌方战斗单位占据、未被抵消 EZOC）由调用方注入，与 `TraceSupplyFacts` 同口径。
- **12.8e-B 的直线距离**：`hexDistance` 到最近**拥有追溯补给的友方战斗单位**，≤ 15（常量 `BREAKOUT_RANGE_HEXES` 已在 `supply.ts`）。注意条文明确"忽略敌方单位或敌方 ZOC"，故用直线距离而非路径距离。
- **首回合豁免**：`firstTurnOutOfSupply` 必须由**连续无追溯补给的回合计数**得出，且条文括注排除"吃图上补给（12.6c）/ 部队储备（12.10）/ 树皮汤之后"⇒ 需要一个每单位的状态位（与 P1-1 的落盘同一处写）。

## 7. 9.14d 崩溃：规则要素、性能根因与接线清单

> 本节依据规则原文（2026-09-14 用户提供）重写，纠正了此前两处判断偏差。

### 7.1 规则原文的要素（逐条落点）

| #   | 规则原文                                                                   | 接线落点                                                                                                      |

### 7.2 性能根因（纠正此前的"口径错"判断）

**纠正**：此前认为 `hexDistance ≤ rangeMp` 是"把 MP 当格数"的口径错。读原文后应修正——第 4 条
明文排除地形影响，故位移范围**不依赖地形成本**，"按步数计"是站得住的读法。
`extenderDisplacementCandidates` 的注释也自述这是有意简化。**该函数本身不是缺陷。**

**真正的根因只有一个**：引擎对**每个候选格**各做一次完整追溯搜索
（卡车 20 步半径 ≈ 1200 格 ⇒ 1200 次搜索），单次位移实测 **5 秒以上**，
`special-combat-flow` 的用例在 5 s 超时边界上时红时绿。

**也纠正"只校验点选格即可"的说法**：第 7 条要求"**若不存在合法格**"走夺取判定，
而判定"合法集合为空"本身就需要枚举整个集合 ⇒ 单纯只校验玩家点的那一格**不够**。

### 7.3 性能根因与修法：把「向源查」反转成「从源铺」

**实测成本结构（为什么是 5 秒）**：`traceSourcesFor(hex)` 对**单个格**要依次做——

- 每个**基础补给源**一次有界路径搜索（12.6a①②③ 的 5 MP 内）——本作剧本苏方有 20 余个源；
- 每个 **HQ** 一次 Dijkstra（12.3b 投递，各自的投递距离与机动类型）。

⇒ **单格约 30 次有界搜索**；崩溃候选约 1200 格 ⇒ **约 3.6 万次搜索**，实测 5 秒以上。
与"45 MA 卡车运输点的移动范围一点就出"的差别正在于此：移动范围是**一次遍历收整张集合**，
而这里是**对每个格反向查一次距离**。

**修法（配方）**：在 `trace-supply.ts` 增加"**该方有追溯补给的格集合**"，把方向反转：

| 源类型                    | 原实现（逐格向内查）          | 集合实现（从源向外铺）                                                         |
| ------------------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| 基础源 ①②③（12.6a，5 MP） | 每个候选格 × 每个源各一次搜索 | **每个源**一次 `runDijkstra`（预算 5 MP）⇒ 并集                                |
| HQ 投递（12.3b）          | 每个候选格 × 每个 HQ          | **每个 HQ** 一次 `runDijkstra`（预算＝印值投递距离、机动类型按投递颜色）⇒ 并集 |
| 12.3c 的"格或其相邻格"    | 入参 `selfAndNeighbors(hex)`  | 集合按**邻域膨胀一格**                                                         |

总量从"候选格 × 源数"降为"**源数 + HQ 数**"次有界 Dijkstra（约 30 次小搜索），候选格上只剩 O(1) 查表。

**关键：不新增成本模型**。`runDijkstra` 的文档已明确"不给 `stopAt` 则收齐整片预算内区域"
（C8 的投递/拖取可视化就用它），`supplyReachableHexes` 即其单源包装；集合版复用同一条 Dijkstra
与同一批条件（`sourceUsable` / `hqCanThrow`），避免出现"同一规则两套实现"。
**实现前先核实一处**：`stepMp` 的取费是否严格对称（目标格占用与地形取费）——
若不对称，集合版必须按"从源向外"的方向取费，不能复用向内查询的结论。

**收益不止 9.14d**：断补标记可在全场一致生效（B4② 的评估层）、补给面板覆盖显示、5.8b
（战略模式须停在有补给的格）都随之解锁；这也是 P1-1 的核心件。

### 7.4 一并做：B5④ 12.7b 拖取距离的两套口径

`rail-supply.ts` 的延补队回连距离用 `hexDistance`，而 `trace-supply.ts` 的拖取距离用 MP 沿路径计
（`countSupplyDistanceToAny`）。**同一规则两个实现且结论可相反** ⇒ 统一到 trace-supply 的实现
（或把"回连距离"作为事实由调用方注入）。注意：这与 7.2 无关——12.7b 的**补给**距离确实是 MP 沿路径，
而 9.14d 的**位移**范围按原文不看地形；二者不可混为一条口径。

### 7.5 结论：9.14d 的接线清单

1. 追溯条件（第 3 条）：随 7.3 的覆盖集接上；
2. 移动阶段的主动崩溃入口（第 2 条）：新增 store 动作 + 地图入口，作为独立子项；
3. "无合法格 ⇒ 原地 + 夺取判定"（第 7 条）：随 7.3 保留并加端到端用例；
4. B5④ 的拖取距离口径统一：与 7.4 一起做，勿与位移范围混口径。
