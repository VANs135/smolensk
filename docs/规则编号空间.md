## 2. 追溯顺序（约定）

1. **归属只看前缀，不看号段**：注释里的条款号必须写「专规 4.5」「通规 4.5」这类带归属形式；**裸写即缺陷**，由 `npm run audit:clauses` 列出。
2. **不能按号段推断**：`1.x`–`5.x` 里通规自身也有一整套（2.3 先手、3.4 通讯/补给、4.5 ZOC、5.0 模式），所以「看到 1.x–5.x 先查专规」是**错的**；只有 `6.0+` 可以按「专规不覆盖这一段」当作通规。
3. 15.1A/15.2A 一类「字母后缀」是**派生编号**：原文把子项写成独立的 `A)`/`B)` 行（不带号前缀），本仓库记作 `15.1A`；追溯按「15.1 的 A) 项」查（见 `条款号可追溯性核对-2026-11-22.md`）。

## 3. 已知做法与代价

- 代码里裸写专规号（如 `'5.0a'`、`'2.3e'`）是历史沿用，`rule` 值同时也进日志与 trace。若要彻底隔离（如加 `sop:` 前缀），会改动全部失败码与既有测试断言，收益不抵风险，**暂不做**。
- 已在 `src/engine/rules/victory.ts` 的常量处写明「这是专规 5.0，不是通规 5.0 模式章」。
- 新增条款号时：一律带归属前缀（`专规 1.4` / `通规 13.6`）；两处都不存在的号不要发明（先核对上面四份源文件）。
- **注释层门禁**：`npm run audit:clauses` 报告注释里裸写的 `1.x`–`5.x` 号（默认只报不拦，存量清完加 `--fail` 并入 `check`）。
- **文件头索引**：45 个规则模块（33 个「通规骨架 + 专规覆盖」+ 12 个专规专属）首部已固定「条文索引：通规 … / 专规 …」两块；新增条款先改索引再改正文。
